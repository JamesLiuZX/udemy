# 一人团队

Ola经营着一家小型非营利组织，每个季度她都要给以往的捐赠人寄送一封筹款信。这封信需要按顺序完成三件事：研究本季度的捐赠趋势，好让信的开头能引用一些应景的内容；围绕这项研究撰写正式的募捐信；再将成稿排版，用于邮件合并，让每封信都能带上捐赠人的姓名和上一次的捐赠金额，实现个性化。以前这三件事都是她自己做，慢慢做。后来她尝试把整条链条一次性委派给AI：先做研究，再据此撰写信件，再排版合并，一次性完成。

寄回来的信写得很漂亮。信的开头引用了一个听起来很具体的说法：四十岁以下的捐赠人中，按月捐赠的比例正在上升。整封信的情感诉求都是围绕这个趋势展开的，而且顺利合并生成了三百封个性化的信件。Ola差点就把信发出去了。她之所以发现问题，纯粹是因为一位理事会成员碰巧问起这个“四十岁以下”的统计数字是从哪里来的，Ola去查的时候，发现研究步骤自己的笔记里根本找不到这个说法。它是在研究和起草之间的某个环节里悄悄冒出来的，是对一个含糊得多的真实趋势的一种听起来言之有理的演绎。等它进入排版好、个性化、随时可以寄出的最终版本时，它看起来和周围所有真实的内容一样权威可信。

没有哪一个单独的步骤，是像第五章Devon的提案草稿那样，明摆着在一个明显的空白处塞进一个编造的数字，出了明显的错。每一个步骤，都在前一步产出的基础上，做出了看似合理的推进，而这恰恰就是问题所在：第三步完全信任第二步的产出，第二步完全信任第一步的产出，而人类也好，别的什么也好，从来没有人去看过任意两步之间的那道接缝。

## 为什么任务链比其中任何一步都更危险

单个被委派的任务，要么做对，要么做错，第四章讲的抽查纪律已经能拦住大部分要紧的问题。但一条任务链，环环相扣，前一步喂给下一步，它带来的风险不只是简单相加。它是复合叠加的，就像一台由好几个部件依次串联而成的机器，其可靠性取决于所有部件同时正常工作，而不是取决于表现最好的那个部件，也不是取决于平均水平。

[KEY-INSIGHT: 关于AI系统在不同长度和复杂程度任务上的表现，已有研究发现了一个一致的规律：随着任务需要更多连续步骤或更长时间才能完成，可靠性会急剧下降，即便模型的整体能力逐年都在提升，这个规律依然成立。2025年一项被广泛引用的研究测算了这一点，发现领先模型能够可靠地完成简短、简单的任务，但随着任务长度和步骤数量增加，它们在真实场景中的成功率会急剧下滑。研究者发现，这个差距一直在随时间缩小，但截至这项研究进行时，差距依然很大。 || Source: METR (Model Evaluation and Threat Research), Kwa, T., et al., "Measuring AI Ability to Complete Long Tasks," arXiv:2503.14499, March 2025（论文标题：《衡量AI完成长任务的能力》）.]

从算术的角度想想这意味着什么，而不只是凭直觉。如果单个步骤十次里能对九次，对于一项被委派的任务而言，这已经是个不错的比率，远高于第四章那种抽查纪律要低成本拦住剩下问题所需要的水平。把这样的三个步骤串联起来，中间没有人检查，三步全部做对的概率就不再是百分之九十了。它会接近百分之七十。串联五步，会接近百分之六十。不是每个步骤本身变差了，是这条链变差了，纯粹是因为长度的缘故，而最终排版完成的成品，不会给你任何视觉上的提示，告诉你真正的错误是从哪一步悄悄溜进来的，这和Ola那封邮件合并出来的信一模一样：无论底层那个说法是真是假，信看起来都同样光鲜体面。

[PULLQUOTE: 任务链失败，不是因为某一步变差了。它失败，是因为长度会让风险复合叠加，而一份光鲜的最终成品，不会给你任何线索，告诉你究竟是哪一步出了问题。]

## 解药是检查点，不是一个编程项目

有一点值得说清楚，因为人们很容易以为，多步骤流程的解药，是一条更精密、更自动化的流水线：不是这样的，这本书也不会因此变成一本讲自动化流水线的书。要修好Ola那封信出的问题，你不需要学会搭建一个自主智能体，不需要写代码，也不需要把各种工具连接起来。你只需要一件事：在每一步的产出变成下一步的输入之前，让人亲自看一眼，这就是第四章讲的那套抽查纪律，只不过这次要插入到链条里的每一道接缝上，而不是只放在最后。

先跑研究这一步。读一遍，特别留意任何读起来像是硬数字，或者是那种如果理事会成员追问你也要能站得住脚的说法。确认无误之后，才把经过审核的研究交给起草这一步。对照你已经核实过的研究去读草稿，专门留意Ola当初漏掉的那种偏移：某个说法听起来像是出自研究，但细究起来又对不上号。确认无误之后，才把经过审核的草稿交给排版这一步，这一步通常是三步里最安全的，因为排版很少会凭空造出新的说法，它做的只是把已有的内容重新排列。

三次简短的审核，每一次成本都很低，因为每一次都只是拿一个步骤的产出，去对照它对应的输入来检查，加在一起花的时间，比把成稿从头到尾读一遍还要少，而且它们能拦住那种成稿通读法最不擅长拦住的错误：一个错误，在被真正看到之前，已经多经过两道工序，被打扮成自信而连贯的文字了。

[KEY-INSIGHT: 软件工程领域被引用最多的发现之一是，在一个多阶段流程中，缺陷被发现得越晚，修复成本就会急剧上升，按经典数据估算，不同项目之间这个倍数从大约四倍到高达一百倍不等：在早期需求阶段修复很便宜，一旦进入设计或编码阶段就会明显更贵，一旦交付上线、在实际使用中被发现，成本又会再高出一大截。 || Source: Boehm, B.W., "Software Engineering Economics," Prentice-Hall, 1981 (data originally presented in Boehm, B.W., "Software Engineering," IEEE Transactions on Computers, C-25(12), 1976)（书名：《软件工程经济学》；原始数据发表于论文《软件工程》）.]

这个规律并不是软件行业独有的，这也正是为什么在每一道接缝处检查，会比只在最后检查更有效。一个编造出来的统计数字，如果在研究步骤就被抓到，Ola花三十秒把它划掉就行了。同样的数字，如果是在它已经撑起了整封募捐信的情感核心之后才被发现，代价就是要重写。如果是在排版和邮件合并之后才被发现，摆在三百封已经个性化的信件里，代价要么是一封尴尬的召回邮件，要么是永远都没被发现、只能自己承担的声誉损失。这个错误本身并没有随着阶段推进变得更离谱，它只是随着阶段推进变得更贵，因为在它上面又叠加了更多的工作。

## 知道在哪里该停止串联

不是每一个多步骤流程都值得在每个阶段都交给AI串联着做，第七章那份淘汰标准清单背后的那种直觉，放到这里同样适用，只是这次适用的对象是一个具体的步骤，而不是整个任务。比如，如果任务链里的某一步是个判断性的决策，比如研究该优先关注哪些内容，取决于你知道理事会这个季度真正在意打动哪些捐赠人，这样的一步或许该留给Ola自己来做，让AI在她做完这个判断之后，接手后续的起草和排版步骤，而不是试图替她做这个判断。

一条三步的任务链，每道接缝都有一个检查点，对几乎任何愿意多花几分钟在步骤之间读一读的人来说，都是可以驾驭的。而一条七步或八步的任务链，即便每道接缝都仔细检查过，花在审核上的时间也会开始超过起草环节省下的时间，这正是第四章讲过的那笔账，只不过这次是发生在一整个流程上，而不是一份文档上。当任务链变得那么长的时候，更好的解药通常不是加更多自动化，而是把任务链砍到那些真正能从委派中获益的步骤，剩下的自己做，这正是第七章已经教过你的那套分诊逻辑。

## 当问题出在任务链本身

有时候，解药不是加更多检查点，而是把任务链缩短。

Desmond经营着一家小型活动公司，他曾尝试把活动结束后给客户的总结报告，自动化成七个串联的步骤：拉取出席人数、汇总供应商反馈、起草“亮点”部分、起草“待改进”部分、把这些内容整合成面向客户的叙述、按公司模板排版、再生成一封引用这份总结的跟进邮件。他很尽责地按照本章的建议，在每一道接缝都加上了检查点，结果发现光是审核就要花掉将近一个小时一场活动，几乎和以前手写整份总结所花的时间一样长。

问题不在于哪一个检查点本身有多难，而在于七个步骤就意味着七个检查点，而第四章警告过的那笔审核时间成本，也随着任务链一起变长了，而不是保持低廉。Desmond把它砍成了三步：第一步把原始数据和反馈一起拉取出来，第二步根据审核过的数据起草完整的叙述，把“亮点”和“待改进”放在一起写，第三步排版。两个检查点，不是六个。他之前搭建的那个七步版本，并不是一个更周全的流程。它其实是一个真正的任务，披着一条长任务链的外形，好几个子步骤根本不需要分开，只是因为串联已经变成了默认的做法，而不是一个经过深思的选择。

## 本章不涉及的内容

本章不会告诉你，所有多步骤任务都不适合委派，也不会说串联是一种应该避免的手法。Ola那套三步流程，加上两个检查点之后，现在运作得很好，而且每个季度都比她自己从头写一遍这封信节省了实实在在的时间。真正的风险从来都不是任务链本身，而是让整条链跑完却没有人看过任何一道接缝，把一份光鲜的最终成品，误当成“背后每一步都做对了”的证据。

本章也不会假装，每道接缝都设检查点就能拦住一切。一个匆忙、疲惫，或者在某道接缝上检查错了地方的审核者，仍然可能漏掉那里真正出的问题。第四章讲过的那些局限，在任务链的每一道接缝上依然成立，不只是在最后一步。检查点这个习惯，能降低任务链悄无声息地复合叠加风险的可能性，但它取代不了第四章和第五章一路在建立的那种真正的判断力。

## 试一试：画出你的任务链

如果你已经在运行，或者正在考虑运行一个多步骤的委派流程，把实际的步骤按顺序写出来：

| 步骤 | 它产出什么 | 这里设一个检查点，值得花时间吗？ |
| --- | --- | --- |
| | | |
| | | |
| | | |

数一数步骤的数量。超过三四步之后，诚实地问问自己：是不是有相邻的两个步骤，其实是同一个任务戴着两个不同的标签，就像Desmond的“亮点”和“待改进”两部分那样。在你加上任何一个检查点之前，先把能干净合并的步骤合并掉。

[TAKEAWAYS]

- 一条委派任务链，比任务链里任何单独一步都更危险。错误会随着步骤层层复合叠加，就像任何一个依次串联的系统，其不可靠性会在各个部件之间复合叠加一样，即便每一个单独的步骤本身相当可靠。
- 一份光鲜、排版完整的最终成品，不会给你任何线索，告诉你错误究竟是从哪一步进来的。等你读到成品的时候，一个早期的错误已经被后面每一步都打扮成了自信满满的文字。
- 解药是在每一道接缝上设一个人工检查点，而不是搭一条更精密的自动化流水线。在每一步的产出喂给下一步之前先读一遍，能拦住那种端到端通读一遍通常会漏掉的偏移。
- 不是每一步都该交给AI。任务链里一个真正需要判断的决策，是留给你自己来做的候选项，这正是第七章那套淘汰标准背后的逻辑，只不过这次是一步一步地用，而不是用在整个任务上。

[/TAKEAWAYS]
