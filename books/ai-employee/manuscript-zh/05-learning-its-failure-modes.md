# 摸清它的失败模式

Devon 经营着一家一人咨询工作室，他把同一款AI工具用于两项完全不同的工作。每周一，它起草客户提案的初稿：范围、时间表，再加上从他自己过往项目里挑出的几个可比案例数字。每天，它还负责管理他的日程，在客户要求改期时挪动会议安排。

三周后，日程助手把一次客户通话和一次牙医预约排到了同一时间，因为客户写的是“3pm EST”，而 Devon 的日历设置的是太平洋时区，工具却不动声色地认定两个时间是一致的。Devon 当天早上发现了问题，改约了牙医，并从这次经历中得出一个笼统的结论：这东西会犯粗心的错误，所以必须时刻盯着。接下来的一个月里，他读每一份提案初稿时，都像是在防备日历上那种粗心错误重演。

结果从没发生过。提案初稿有一个完全不同的问题，他是三个月后偶然才发现的，当时一位客户发邮件问，提案里“平均节省40%时间”这个数字是从哪来的。Devon 认不出这个数字。他自己没写过，过往的项目报告里也没有。这款工具在案例研究部分遇到信息缺口时，编造了一个听起来可信的统计数字，用的是和真实数字一模一样的、流畅而笃定的语气。这个失误和时区毫无关系，时区那次失误也和编造统计数字毫无关系。同一款工具，两项任务，两种完全不相关的出错方式，而 Devon 却花了一个月的时间，在错误的任务上防备错误的问题。

## “AI会犯错”这句话里藏着的误区

“AI会犯错”这句话是对的，但几乎毫无用处，就像“员工有时表现不佳”是对的，却完全没告诉你是哪个员工、在哪项任务上、以什么具体方式出错。Devon 的失误不在于粗心。他把这款工具当成了一个整体，认为它只有一种失败模式，而实际情况是：他手上有两组完全独立的“任务加工具”组合，每一组都有自己特定的、可以学习掌握的、在很大程度上可预测的出错方式。日程任务在时区标注含糊时会出错。提案任务的出错方式，是在叙述出现缺口时编造具体数字来填补。这两种模式互不预示对方，把它们笼统地平均成一句模糊的提醒，“当心，它会犯错”，比毫无用处还要糟糕，因为它会把你本就有限的注意力，引向当下任务上错误的信号。

[PULLQUOTE: “AI会犯错”这句话是对的，但几乎毫无用处。它没有告诉你，是哪项任务、用哪款工具、以什么具体方式出错。]

同样的模式，在一项更为严谨、真正对此进行了测量的研究中，以大得多的规模再次出现。斯坦福大学的研究人员测试了几款AI法律研究工具，它们的营销诉求如出一辙：专为避免此前已让律师在法庭上出丑的AI幻觉引用问题而生。如果“AI会产生幻觉”是关于AI这个大类的普遍事实，而不是关于具体“任务加工具”组合的事实，你会预期这些工具在同类任务上的出错率大致相近。事实并非如此。

[KEY-INSIGHT: 研究人员测试了几款专为减少幻觉引用而设计的AI法律研究工具，发现 Lexis+ AI 在超过17%的测试查询中给出了错误或缺乏依据的答案，而 Westlaw 的AI辅助研究产品在同一类法律研究任务上的这一比例约为33%，几乎是前者的两倍。第三款工具，Thomson Reuters 的 Ask Practical Law AI，则表现出几乎完全不同的失败模式：问题不在于编造，而在于不完整，在超过60%的查询中给出的答案不完整。 || Source: Magesh, V., Surani, F., Dahl, M., Suzgun, M., Manning, C.D., & Ho, D.E., "Hallucination-Free? Assessing the Reliability of Leading AI Legal Research Tools," Journal of Empirical Legal Studies, 2025 (originally released as a Stanford RegLab/HAI working paper, 2024)（论文标题：《无幻觉？评估领先AI法律研究工具的可靠性》）.]

同一大类任务，三款专门打造的工具，三种不同的出错率，其中一款的出错方式和另外两款截然不同：不是编造，而是不完整。如果有人测试完 Lexis+ AI 后，得出一条关于“AI法律研究工具”的笼统结论，他就会把这个站不住脚的错误假设，原样带进 Ask Practical Law AI，而在那里，真正的风险根本不是自信满满的编造，而是一个听起来言之凿凿、实际上却漏掉了完整答案一半内容的回答。这个教训不只对律师适用。它和 Devon 用真金白银换来的教训一模一样：真正拥有失败模式的单位，是任务和工具的组合，而不是工具本身，更不是“AI”这个笼统的类别。

## 同一个矩阵的另一半

Devon 的故事展示的是一款工具、两项任务、两种不相关的失败模式。值得再看一看它的镜像情形：一项任务、两款工具，因为真正重要的单位是那个组合，而一个组合有两条轴线，不是一条。

Simone 为一家区域性连锁健身房负责营销工作，她在决定长期使用哪款AI写作工具之前，用同一项任务，也就是每周的会员通讯，测试了两款不同的工具。两款工具都把结构做对了：一条锻炼小贴士、一段会员故事、一条课程安排提醒。它们的差异之处则具体而稳定。第一款工具，运行五次，其中两次悄悄把课程安排提醒里的某个上课时间，改成了一个听起来合理但其实错误的时间，这种错误只有在你本就知道真实课表时才能发现。第二款工具在五次运行中一次都没碰过课程安排，但它在 Simone 的任务说明没有提供具体人选时，反复为会员故事部分编造出一个具体的会员姓名和一句具体的赞美之词，这是第一款工具从未出现过的编造问题。

同一项任务，同一份任务说明，同样的五次输入。却是两种真正不同的失败模式，一款工具一种。如果 Simone 只测试了第一款工具，就得出“AI通讯工具会把课程时间弄乱”的结论，她就会把这个错误的提防原样带进第二款工具，盯防一个那款工具根本不会犯的课表错误，同时错过它实际上出现过两次的编造会员语录问题。Devon 那个故事的教训，在这里换了个方向再次出现，从相反的角度得出同一个结论：无论是任务本身，还是工具本身，单独都无法告诉你失败模式是什么。只有具体的组合才能告诉你。

## 打造一份真正的绩效评估

一份真正的员工绩效评估，不会只说“有时会犯错”。它会说清楚是哪一类错误，出现在哪一类工作上，出现频率如何，以及在什么条件下发生，因为只有这种版本的信息，才真正有助于你判断下次该重点核查什么。要为一项委派任务打造出同样的东西，需要三样原料，而如果你已经完成了第三章的试运行和第四章的抽查，这三样你其实早就都有了。

**记录每一次失误的具体内容，而不只是失误的总次数。** 每当抽查发现问题，写下具体错在哪里，而不只是记下“出错了”。“编造了一个统计数字”和“搞错了时区”是两条不同的记录，哪怕你很想把两者都归到“出错了”这一栏里。

**在多次失误之间找规律，而不是在单次失误里找规律。** 一个编造出来的数字可能只是偶然。三个编造出来的数字，都出现在同一类缺口里，比如案例研究部分缺了一个数据点，那就是一种规律：这项任务，配上这款工具，往往在输入信息有漏洞时倾向于编造内容。这正是值得记下来、并在此后每一份草稿里加以核查的东西，正是第四章讲的“接缝”，如今被明确点出了名字，而不是每次都靠意外重新发现。

**把这种规律，同工具的整体口碑区分开。** 一款在排期上表现出色、却在编造统计数字上不靠谱的工具，既不是“一款好工具”，也不是“一款差工具”。它是一款在某项任务上表现出色、在另一项任务上需要专门、有针对性核查的工具。把这些统统合并成一个笼统的评价，正是让 Devon 白白错付一个月注意力的那个错误。

一旦你为某项任务做过几次这样的记录，你手上得到的东西，就更接近一份真正的人事档案，而不是一种模糊的印象：不再是“它会犯错”，而是“在提案初稿这项具体任务上，当输入数据存在缺口时，它大约五次里有一次会编造出一个用来支撑论点的数字，而它从没在日期或客户姓名上出过错”。后面这句话，准确告诉你下次该看哪里。前面那句话，从来做不到。

## 这份清单为什么应该短

一份有用的故障模式清单，每项任务通常只有两三条，而不是十条。一旦你开始追踪一项任务可能出错的十种不同方式，你就已经不再是在打造一份有针对性的核查清单，而是在重建第四章已经证明行不通的“事事核查、一概不信”的习惯，只不过换了个“尽职尽责”的说法。如果你的清单不断增长，超过三四条真实观察到的规律，诚实地讲，通常并不是因为这款工具真有那么多种不同的失败模式。而是这项任务本身太宽泛了，是好几份不同的工作披着一个名称，解决办法是把它拆分成它实际构成的那些更窄的任务，而不是为合并后的那项任务写一份更长的清单。

## 本章不涉及的内容

本章不会承诺给你一份一成不变的清单。今天还在编造统计数字的提案工具，可能在一次模型更新之后就不再这样做了，转而开始出现别的问题，也就是那种未经预告的版本变化却带来了实实在在的行为后果，正是本书在举例时刻意避免过度依赖的那类东西，因为它过时得实在太快。把每一份故障模式清单，都当作截至你最近几次核查为止的现状，而不是一劳永逸的定论。要像重新审视一份员工绩效评估那样，定期回顾它，而不是写一次就归档了事。

本章也不会告诉你，一份简短、具体的故障模式清单，就意味着这项任务可以完全不用再盯着了。它准确告诉你的是，接下来该继续盯防哪里，以及现在可以不必再那么用力盯防哪里，这比宣布整件事已经彻底解决，要小得多，也实在得多。

## 试一试：建立档案

挑一项你已经抽查过至少几次的任务。用大白话写下你能真正回忆起的每一次具体失误，而不是一种模糊的“它有时候不太对”的印象：

| 出了什么错 | 大致频率 | 在什么条件下 |
| --- | --- | --- |
| | | |
| | | |
| | | |

如果你列出的真实条目超过三四行，那不是这项任务的失败，而是一个信号，说明这项任务其实是好几项任务披着同一个名字。标出哪些行可以干脆利落地拆成一项独立的任务，把它当作一个标记，留到你下次按第三章的方法界定一次试运行时再处理，而不是今天就要解决的问题。

[TAKEAWAYS]

- “AI会犯错”这句话是对的，却毫无用处。真正的分析单位，是一项任务配上一款工具：每一种组合都有自己特定的、可以学习掌握的失败模式，一种组合的规律，很少能预示另一种组合的规律。
- 即便是为完全相同的目的打造的工具，出错率和出错方式也可能各不相同。测试过一款AI法律研究工具，几乎不能告诉你任何关于另一款为同样工作打造的工具的信息。
- 根据你实际做过的抽查，整理出一份简短、具体的清单：出了什么错、频率如何、在什么条件下发生，而不是一种笼统的印象，认为这款工具“还不错”或者“有点不靠谱”。
- 一份故障模式清单如果有超过三四条真实条目，通常说明这项任务实际上是好几项任务被硬拼在了一起。应该把它拆开，而不是写一份更长的核查清单。

[/TAKEAWAYS]
