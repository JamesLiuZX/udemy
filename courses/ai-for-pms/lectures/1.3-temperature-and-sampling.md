@slide statement
kicker: Section 1 · Temperature
## Last lecture I simplified one thing on purpose. It doesn't always pick the single most likely word.
lead: It picks from a range of likely words, and temperature decides how wide that range is.

@narrate
Last lecture, I said the model predicts the single most likely next word,
over and over. That was true enough to build the mental model on, and
it's not quite the whole story. Time to fix it.

At each step, the model actually computes a whole list of plausible next
words, each with a likelihood attached, not just one winner. Then it
draws one, weighted by those likelihoods. Most of the time the top
candidate wins anyway, because it usually is by far the most likely. But
not always, and that "not always" is precisely why the same prompt can
give you two different answers on two different runs.

Temperature is the dial that controls how often it draws something other
than the top candidate.

This isn't a footnote to last lecture, it's the answer to a question you
were probably already asking. If it's really just predicting the obvious
next word, why doesn't the same prompt come back identical every time?
Now you know: because "obvious" is a probability, not a certainty, and
the dial decides how strictly it sticks to it.

## What the dial actually changes

::: cols
:: card
### Temperature near zero
- "Ship smarter, not harder."
- "Ship smarter, not harder."
- "Ship smarter, not harder."
:: card
### Temperature near one
- "Ship smarter, not harder."
- "Faster launches, fewer surprises."
- "The roadmap that writes itself."
:::

@narrate
Same prompt, five separate runs, asking for one product tagline. Watch
what changes.

Near zero, it's almost always the same answer, run after run, because
the dial is telling it to take the top candidate essentially every time.
Reliable, a little safe, occasionally repetitive.

Near one, the same prompt produces genuinely different taglines across
runs. Same input, real variety, because the dial is now telling it to
draw from further down that ranked list more often.

Neither setting is "better." They're tuned for different jobs, and the
mistake is picking one without asking which job you're actually doing.

Notice, too, that even at zero, the first tagline could still have been
the wrong one to lead with. Consistency tells you nothing about whether
the answer it kept repeating was actually good.

@slide definition
kicker: Naming it precisely

::: definition Temperature
A number, usually zero to two, that controls how often the model picks
something other than its single most likely next word. Low: consistent,
safe, occasionally repetitive. High: varied, occasionally strange.
:::

::: example Try this yourself
Run your own feature's prompt five times at whatever temperature it's set
to now. Count how many genuinely different answers you get. That count is
the actual setting, not the number in a config file.
:::

@narrate
That's the term, and notice the definition doesn't say "creative" or
"smart." It says how often the model picks something other than the top
choice. That's it. Everything else people say about temperature is a
description of what that one mechanical change tends to produce.

The exercise is the fastest way to feel a setting you've probably never
actually looked at. Run your feature's real prompt five times, at
whatever temperature is already configured, and count the genuinely
different answers. Most people are surprised by what they find, in both
directions.

@slide table
kicker: Which setting for which job
## A rough default, not a universal law

| Feature type | Rough setting | Why |
| --- | --- | --- |
| Support summaries, data extraction | Low | The same ticket should summarise the same way twice |
| Code generation | Low | You want the boring, working answer |
| Brainstorming, marketing copy | Higher | Variety is the entire point of asking |

@narrate
Here's a rough default, and I mean rough. Treat it as a starting point to
argue with, not a rule.

Anything where consistency itself is the feature, summarising the same
ticket the same way every time, extracting the same field reliably, wants
a low setting. Code generation too: you want the same, boring, working
answer, not an inventive one.

Anything where variety is the actual point, brainstorming names, drafting
several marketing angles to choose between, wants it higher. You're not
asking for one correct answer. You're asking for options.

If you don't know which one your feature is, that's worth answering
before you argue about the number. And if a single feature does both, a
support tool that drafts a reply and also suggests three subject lines,
it may genuinely need two different settings for two different calls, not
one compromise value for both.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
Temperature is not a correctness dial. ==A low setting makes answers
consistent, not accurate==, and a model can confidently repeat the same
wrong answer five times in a row just as easily as the right one.
:::

@narrate
Say the honest caveat, because this is the misunderstanding that actually
costs people.

A low temperature setting does not make the model more correct. It makes
it more consistent. If the most likely answer happens to be wrong, a
temperature of zero will give you that same wrong answer, confidently,
every single time. Consistency and correctness are two completely
different properties, and turning this dial only touches one of them.

Whether it's actually right is a question for the golden set and rubric
you'll build in Section four, not for this dial. This dial has never been
able to answer that question, at any setting.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Check what temperature your feature is actually set to
2. Match it to the job: consistency or variety, not habit

@narrate
Two things before you move on.

Find out what temperature your feature is actually running at right now.
Most people building on top of these models have never checked, and it's
usually a default nobody chose on purpose.

Then match the setting to the job you're doing, consistency or variety,
rather than whatever the example code happened to ship with.
