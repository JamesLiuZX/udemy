@slide statement
kicker: Section 7 · The number users actually feel
## p95 latency is a number on a dashboard. What a user feels is whether the wait matched what they expected.
lead: The same total wait can read as fast or broken, depending on nothing but what happened on screen while it passed.

@narrate
Section seven's own scorecard put a p95 latency number on the table two
lectures ago, right next to pass rate and cost, and moved on without
explaining what that number actually means to the person waiting on the
other end. Here's what it means, on its own: not very much.

A user doesn't experience milliseconds. They experience whether the
wait matched what the interaction led them to expect. Three point two
seconds feels instant for a request that visibly involves real work.
The same three point two seconds feels broken for something that looks
like it should be immediate.

That gap, between the measured number and the felt one, is where this
lecture lives. Managing it is a real skill, separate from the modelling
work you've done all section, and it's cheaper to fix than most teams
assume, once you know which of the two problems you're actually solving.

@slide table
kicker: Match the budget to the interaction
## Different interactions carry a different tolerance for the same wait

| Interaction | What users tolerate | Why |
| --- | --- | --- |
| Inline autocomplete | Under 300ms | Reads as broken typing, not a wait |
| Chat reply, streaming | A few seconds to first token | Visible progress resets the clock |
| Multi-step agent task | Up to a minute or two | Only if it narrates its own steps |
| Overnight batch report | Unbounded | Nobody is watching it happen |

@narrate
Set your budget from this table before you set it from a benchmark,
because the same model call that's comfortably fast for a chat reply is
unusably slow for autocomplete, and needlessly rushed for a report
nobody's watching get generated.

Inline autocomplete sits at the strict end for a specific reason: it's
competing with the user's own typing speed, not with their patience.
Miss that budget and the feature doesn't feel slow, it feels broken,
because a suggestion that arrives after the word's already been typed
manually isn't late, it's pointless. No amount of clever UI rescues a
suggestion that missed its moment.

A multi-step agent task can tolerate far more real time than a single
chat reply can, but only under one condition: it has to narrate what
it's doing while it does it. A silent minute reads as a hang. The exact
same minute, spent visibly checking three things in sequence, reads as
thorough. The batch row exists for a reason too, and it's the direct
echo of last lecture's batching discount: when nobody's watching, the
budget stops being a design constraint at all.

Notice the table has no single "fast enough" number anywhere on it.
That's deliberate. A budget copied from a different feature's
interaction pattern is a guess wearing a benchmark's clothing, and it
will be wrong in exactly the direction that costs you users.

@slide two-col
kicker: Two different problems, easy to confuse
## Shrinking the real number and shrinking the felt one are different jobs

::: cols
:: card bad
### Chasing the measured number alone
- Swap models, tune infrastructure, shave the p95 figure down
- Real engineering cost, often for a second or two of actual gain
- The user experience barely moves if nothing on screen changed
:: card good
### Fixing what the user actually feels
- Stream the first token instead of waiting for the full reply
- Narrate an agent's steps instead of showing a blank spinner
- Often cheaper than the infrastructure fix, and the felt gain is bigger
:::

@narrate
Walk through the refund agent from Section six one more time, because
this is exactly where its latency shows up. Checking the account,
checking the refund policy, issuing the approval: three tool calls in
sequence, adding up to real seconds that no amount of model swapping
removes, because the time is spent waiting on tools, not on the model
thinking.

A blank spinner for those seconds reads as a hang, and a user who's
seen a hang before starts wondering whether to refresh the page. The
identical wait, spent showing "checking your account, checking policy,
approving refund" as each step completes, reads as a system doing
visible, trustworthy work. Nothing about the actual latency changed.
Everything about the felt latency did.

That's not a trick, it's honest information delivered progressively
instead of withheld until the end. The user was always going to wait
those seconds. The only choice was whether they'd spend that wait
informed or wondering if something broke on the other end.

Model routing from two lectures ago earns a second mention here,
because it's one of the few techniques that moves both numbers at
once. Send an easy step in that same three-call chain to a faster
model and the actual wait shrinks, not just the felt one. That's worth
checking before you reach for narration alone: sometimes the honest
fix is both, not a choice between them.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
Streaming and progress narration fix the *felt* wait. ==Past a certain
point, the actual latency is the problem==, and no amount of polish on
the waiting experience saves an interaction pattern that's simply too
slow for what it's asking the user to do.
:::

@narrate
Say the honest caveat plainly, because it's tempting to treat
perceived-speed techniques as a substitute for the real fix rather than
a complement to it.

They aren't a substitute. An inline autocomplete suggestion that takes
three seconds is broken, full stop, and no streaming animation turns
three seconds into three hundred milliseconds. When the actual number
blows through what the interaction pattern can tolerate, the fix is a
faster model, a routing decision, less work happening per call, or
sometimes admitting honestly that the interaction pattern was wrong for
what the feature needs to do in the first place.

Reach for perceived-speed fixes when the actual latency is close to
budget and the remaining gap is about what happens on screen while it
passes. Reach for the real fix, the harder one, when the actual number
is nowhere close, no matter how good the waiting experience looks on
top of it. Confusing which situation you're in is how teams ship a
beautifully animated spinner over a feature that's still too slow to
use.

@slide definition
kicker: Naming it precisely
::: definition Latency budget
The maximum wait a specific interaction pattern can tolerate before it
reads as broken rather than working, set from the interaction itself,
then allocated across every model call, retrieval step, and tool call
inside it.
:::

::: example Try this yourself
Measure your own feature's time to first visible token against its
total completion time. If the gap between them is large and nothing
streams, that gap is free latency you're currently not collecting.
:::

@narrate
That's the term worth carrying forward, and the definition's order
matters: set the budget from the interaction first, then check whether
your architecture fits inside it, not the other way round, and not from
whatever number the current build happens to produce.

Run the measurement on something real. Most teams have only ever
measured total completion time, the number that mattered for last
lecture's scorecard, and have never separately measured how long a user
waits before anything visible happens at all. That second number is
usually the one actually shaping whether the feature feels fast, and
it's often measured nowhere on the dashboards anyone actually looks at.

If your feature streams already, check whether the first token arrives
fast enough to matter. Streaming a reply that still takes two seconds
to start doesn't buy you anything over a spinner, because the user
spent the same two seconds staring at nothing either way. The saving
only exists if the first visible sign of progress arrives close to
instantly, and it's worth timing that specific number directly rather
than assuming streaming alone solved it.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Classify your feature's interaction pattern and read its real budget off the table
2. Separate your actual latency number from what a user currently sees while they wait

@narrate
Two things before you move on.

Classify the interaction first. Autocomplete, chat, multi-step agent,
or batch job, because the budget you're building toward depends
entirely on which one you're building, and a budget borrowed from the
wrong row will quietly mislead every decision after it.

Then look honestly at what a user currently sees during the wait. If
the answer is nothing, a blank screen or a generic spinner, that's the
cheapest fix available to you this section, cheaper than any model
swap, and it's worth shipping before you spend a single hour chasing
the measured number down instead.

Next lecture is the workshop: bring this section's cost model, model
selection scorecard, and now a latency budget together into one unit
economics model for a feature of your own, the artifact this whole
