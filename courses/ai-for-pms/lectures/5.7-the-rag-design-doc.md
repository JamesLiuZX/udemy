## Six lectures on retrieval, assembled into one document an engineer can actually build from.
lead: Every decision you've made this section has a home here. This is where they all go at once.

@narrate
You've made six real decisions across this section: whether the
problem is even a missing-fact problem, what stages the pipeline
needs, how to chunk each content type, what retrieval quality actually
means, which production failures apply, and how permissions and
freshness get handled. Here's where all six become one document.

This is A06, attached to this lecture. Open it now and fill sections in
as we walk through them, the same way you did with the PRD template in
Section three.

Think of this document as sitting inside the PRD, not replacing it.
The acceptance criteria section from Section three still names the
threshold your feature has to clear. This design doc is what makes
that threshold achievable in the first place, by specifying the
retrieval system underneath it properly. One document sets the bar.
The other explains how the system actually reaches it.

## Six sections, and where each one came from

| Section | What it must contain | From |
| --- | --- | --- |
| Why RAG | Confirms this is a missing-fact problem, not reasoning | 5.1 |
| Pipeline stages | Which of the seven stages are built, and why | 5.2 |
| Chunking strategy | Per content type, not one default applied everywhere | 5.3 |
| Retrieval targets | Hit rate, rank, and precision thresholds | 5.4 |
| Failure coverage | Which production failures apply, and the mitigation | 5.5 |
| Permissions & freshness | The access model and the re-index cadence | 5.6 |

@narrate
Read the first row before any of the others, because it's the one
that decides whether the rest of this document should exist at all.
Section two's decision tree already gave you the test: is this
actually a missing-fact problem. If a design doc can't answer that
cleanly, stop there. The other five sections are wasted effort on a
system solving the wrong problem.

Past that gate, the remaining five sections are exactly the
decisions this section walked you through, now written down in the
order an engineer building against this document would actually want
them.

Notice the order itself is deliberate. Why doesn't it match the order
this section taught the ideas in? Pipeline stages come before chunking,
because you can't decide how to chunk something until you know
whether re-ranking or query rewriting are even in scope. Retrieval
targets come before failure coverage, because you need a number to
know what counts as a failure worth naming in the first place.
Sequence the document for the reader building from it, not for the
order you happened to learn it.

@slide two-col
kicker: The same rewrite, applied to RAG
## From a sentence to a document that can be built

::: cols
:: card bad
### What most RAG docs say
"We'll use RAG to answer questions from our internal documentation."
:: card good
### What it should say
"Retrieval over the support and policy corpus, chunked per content
type, target hit rate 90% at k equals 5, precision 70%, permissions
checked live, re-indexed weekly, with a documented fallback when
nothing relevant is found."
:::

@narrate
Recognise this move from Section three: the same rewrite, aimed at a
different document. The first sentence describes an intention. The
second describes something a QA engineer could actually go and check.

Notice every clause in that second sentence traces back to a specific
lecture in this section. The scope is 5.2's ingestion decision. Per
content type is 5.3. The numbers are 5.4. Live permissions and a
re-index cadence are 5.6. The fallback is 5.5's silent-failure fix. None
of it is new information. It's this section's six decisions, in one
sentence instead of six.

Try the same disagreement test from Section three on both versions.
Nobody can push back meaningfully on "we'll use RAG to answer
questions," because there's nothing specific enough in it to disagree
with. Every clause in the second sentence is a place a reviewer could
reasonably say that number's too low, or that cadence is too slow. A
document built to survive that kind of pushback is doing its actual
job.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
A RAG design doc without an explicit "why not simpler" section hasn't
earned its own complexity. ==Retrieval is the expensive answer on
Section two's decision tree==, not the default one.
:::

@narrate
Say the honest caveat, because it's easy to skip the first row of that
table and jump straight to designing pipelines, because pipelines are
the interesting part.

Remember the tree from Section two: prompt first, retrieval only once
a missing fact genuinely requires it. A RAG design doc that never
justifies why a better prompt or a simpler answer wouldn't have done
is a document that assumed its own conclusion. Make the first section
argue for RAG specifically, not assume it, the same discipline as
naming a threshold before defending it.

This matters more than it sounds like it should, because a retrieval
system is genuinely expensive to build and maintain. It's an index to
keep current, a permission model to enforce, chunking decisions to
revisit, and a whole section's worth of failure modes to guard
against. Committing to all of that for a problem a better prompt would
have solved in an afternoon is exactly the kind of cost this section
keeps warning against.

::: example Why that section first

@narrate
That's today's instruction, not a suggestion for later: write the
justification before you write anything downstream of it.

It should feel slightly uncomfortable, the way the acceptance criteria
section did in Section three. If you can't finish that first section
convincingly, that's not a writing problem. It's the document
correctly telling you this feature might not need retrieval at all.

That outcome is a genuine success for this exercise, not a failed
attempt at it. A design doc that talks you out of building a retrieval
system you didn't need saved real engineering time. That's worth more
than five neatly filled sections defending a decision nobody actually
tested.
