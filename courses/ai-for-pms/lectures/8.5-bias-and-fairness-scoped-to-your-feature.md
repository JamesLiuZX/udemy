kicker: Section 8 · The third average that hides something
## A topic nobody can check, and a question you actually can

::: cols
:: card bad
### "Is it biased?"
- A single sweeping topic
- Sounds like due diligence, checks nothing
- Nobody can answer it, so nobody does
:: card good
### "Does the pass rate vary by group, measured?"
- One specific, checkable question
- Answered with a number, not a feeling
- The one this lecture actually teaches
:::

@narrate
"Bias" gets discussed as a single sweeping topic, which is exactly why
most teams never get past discussing it. Nobody can check a topic. You
can only check a specific, measured question, and this lecture gives
you the one worth asking about your own feature.

The question is narrower than it sounds, and more useful for being
narrow: does this feature's quality, measured the way Section four
taught you to measure it, vary systematically by some real dimension of
who's using it? Not whether the model is biased in the abstract.
Whether your feature's pass rate holds steady across the people who
actually use it.

You've already met this shape twice. 2.5 showed you p95 hiding inside
an average latency number. 7.5 showed you a margin crossover hiding
inside a blended number. This is the same trap, one more time, wearing
a different topic.

Treat "is it biased" the same way 6.6 taught you to treat "the model is
smart enough": a sentence that sounds reassuring and settles nothing,
because reassurance was never actually the question. The question is
whether you have a number, and whether that number was measured with
enough resolution to mean anything.

@slide table
kicker: The same aggregate trap, a third time
## One pass rate can hide a very different second one

| Segment | Pass rate | Gap vs overall |
| --- | --- | --- |
| Overall | 91% | n/a |
| Formal, native-English phrasing | 95% | +4 |
| Informal or non-native phrasing | 74% | -17 |

@narrate
Ninety-one percent looks like a healthy number sitting on its own, the
same way 7.5's blended margin looked healthy sitting on its own. Read
the next two rows and the healthy number turns out to be an average of
two very different experiences.

Whoever phrases a request the way the eval set already expects gets a
genuinely strong result. Whoever phrases it differently, less formally,
or in a second language, gets a result seventeen points worse, and
nothing in the overall ninety-one percent hints that gap exists. Nobody
built this gap on purpose. It's what happens when a golden set gets
assembled from whichever real tickets were easiest to find, which
quietly means whichever tickets look most like the majority of the
team's own writing.

This is precisely why 4.2's coverage requirement mattered as much as it
did. A golden set that's accidentally narrow doesn't just under-test
edge cases. It can systematically under-test one entire group of real
users, and produce a pass rate that's honestly reported and
substantively misleading at the same time.

@slide two-col
kicker: You can only find what you measured for
## Same feature, two different golden sets

::: cols
:: card bad
### Built from whatever was easiest to find
- Pulled from the most recent hundred tickets in the queue
- Skews toward however the team itself tends to phrase things
- A real gap has nowhere to show up in the pass rate
:: card good
### Built to measure the dimension on purpose
- Deliberately includes enough cases in each segment to score separately
- A phrasing gap becomes a visible row, not an invisible average
- The same fifty-case discipline from 4.2, aimed at one more thing
:::

@narrate
This is also precisely the kind of number 8.4's high-risk tier expects
you to have on hand. A hiring or credit-scoring feature landing in that
tier isn't just asked whether it works. It's asked whether it works
evenly, and a single blended pass rate is not an answer to that
question, however good the number looks on its own.

Notice the good column doesn't ask for a bigger golden set, it asks for
a deliberately structured one. The size 4.2 already taught you to hit
is enough, as long as enough of those cases actually represent the
segment you're worried about.

Pick the dimension before you build the slice, not after. Phrasing
style is this lecture's example, and it's a genuinely common one for a
text feature, but your own feature might split more meaningfully by
something else entirely: request complexity, device type, account age.
The method is identical regardless of which dimension turns out to
matter for your specific feature.

Ask the people closest to the traffic which dimension they'd guess
first, the same instinct 5.8's workshop leaned on for a support corpus
owner. A support lead who reads real tickets daily often already has a
hunch about which phrasing gets misread more often. That hunch is a
legitimate starting point for choosing a slice, not a substitute for
actually measuring it.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
A clean aggregate pass rate is not evidence of fairness. ==It's often
just evidence nobody measured with enough resolution to find the
gap==, which is a very different claim.
:::

@narrate
Say the honest caveat plainly, because "we haven't found a problem" and
"there isn't one" get treated as the same sentence far too often, and
they aren't.

A feature that's never been segmented by any real dimension hasn't
passed a fairness check. It hasn't taken one yet. That's not a reason
for alarm, it's a reason to run the check honestly, the same way an
unmeasured cost or an unmeasured latency budget earlier in this course
was a gap to close, not a crisis to announce.

This cuts both ways, worth saying plainly. Finding a gap doesn't mean
the feature is unusable, and it doesn't mean abandoning the segment
that struggles. It means you now have a specific, fixable target: a
prompt that handles a wider range of phrasing, a preprocessing step, a
retrieval query rewritten before it searches. A measured gap is the
first step toward closing it, not a verdict.

@slide definition
kicker: Naming it precisely
::: definition A fairness slice
A golden set segment with enough cases to score separately, chosen for
a dimension where a gap would genuinely matter for this feature, not a
generic demographic checklist borrowed from somewhere else.
:::

::: example Try this yourself
Pick one plausible dimension for your own feature. Check whether your
current golden set has enough cases in each segment to measure a gap
at all.
:::

@narrate
That's the standard worth holding your own eval to, and most people
running this exercise for the first time find the honest answer is no,
not yet, which is exactly the finding this lecture is built to surface.

That's a fine place to start from. A feature with an honestly
unmeasured fairness question is in a completely different position than
one with a measured, hidden gap nobody addressed. The first is a todo.
The second is a register row overdue for an owner.

Choose a dimension you can actually act on if a gap turns up, not one
that would merely be interesting to know. A slice you'd genuinely fix a
prompt over is worth building. A slice you'd only ever write a
paragraph about in a report is a much lower priority than the ones
ahead of it in your register.

@slide bullets
kicker: Before you move on
## One thing worth doing now

Name one plausible dimension your feature's quality might vary by, and check whether your golden set can currently measure it

@narrate
One thing before you move on.

Name the dimension honestly, the one you'd half-expect if you actually
looked. Most people already have a guess, and the guess is usually a
reasonable place to start measuring. Then check your current golden set
against it. If you don't have enough cases in each segment to say
anything, that's today's finding, worth its own row in 8.1's register.

Both steps together take an afternoon, and they turn a genuine unknown
into either a clean result worth trusting or a specific problem worth
fixing, which is a far better place to stand than an unmeasured guess
in either direction.
