@slide statement
kicker: Section 8 · The last row
## A server that's down is obvious. A feature that's quietly wrong looks exactly like one that's working.
lead: Traditional incident response was built to detect the first kind. Most teams don't yet have a way to detect the second.

@narrate
What does "the feature is down" actually look like? Ask an engineer
and they'll describe it precisely: errors spiking, latency climbing, a
dashboard turning red. Every one of those signals exists because
something stopped responding correctly at the transport level.

An AI feature can fail without moving a single one of those numbers. It
returns a response, quickly, with no error, that happens to be wrong,
or unsafe, or quietly worse than it was yesterday. The server is fine.
The feature isn't. Nothing in a traditional monitoring stack was built
to notice the difference.

That gap is what this lecture closes, and it's the last row on 8.1's
table for a reason: everything else in this section is about preventing
a specific kind of risk. This one is about what happens the day
prevention wasn't enough.

This isn't a hypothetical gap either. It's the direct product of
everything Section seven and this section have already taught you: a
feature can pass its launch scorecard, clear its risk register, and
still degrade quietly in production, the same way 7.5's margin trap hid
inside a healthy-looking dashboard. Detection was never automatic. It
has to be built.

@slide table
kicker: Two different kinds of broken
## The signals that catch a traditional outage don't move for this one

| | Traditional outage | AI quality incident |
| --- | --- | --- |
| What moves | Error rate, latency, uptime | Usually nothing at all |
| Looks like | Clearly broken, alarms fire | A normal, confident, wrong answer |
| Caught by | Existing monitoring | Only a signal built specifically to catch it |

@narrate
Read the bottom row, because it's the entire argument in one line.
Existing monitoring genuinely does catch the left column, reliably,
which is exactly why it's tempting to assume the same dashboards cover
the right column too. They don't, and assuming they do is how a quality
incident runs for days before anyone notices.

The signal that actually catches the right column has to be about
quality specifically: a spike in thumbs-down feedback, a jump in
support escalations from this feature, a sampled review that finds
several outputs failing 4.5's rubric in a row. None of these are
infrastructure metrics. All of them require someone to have decided, in
advance, that this is worth watching continuously, not just checking at
launch and forgetting.

Picture the refund agent one more time, well into production. Its
error rate stays flat, its latency stays flat, every infrastructure
graph looks exactly like it did on launch day. And yet a model update
upstream, or a subtle shift in the kind of tickets arriving, could be
quietly pushing it toward approving refunds it shouldn't, at a rate
nobody's watching for, because nothing wired to page anyone was ever
built to watch for it.

@slide two-col
kicker: What a plan actually needs
## Built for downtime, and built for a quiet quality failure, side by side

::: cols
:: card bad
### A plan built for downtime only
- "We'll know if it breaks, the dashboard will show it"
- No named owner for a quality-specific alert
- No way to disable the feature without a full deploy
:: card good
### A plan built for both
- A quality signal watched continuously, not just uptime
- A named on-call who owns quality incidents specifically
- A tested kill switch: a fast, safe way to turn it off
:::

@narrate
Notice the good column's third row, because it's the one teams skip
most often. A kill switch nobody has actually tested is a kill switch
you're discovering the failure mode of during the incident itself, at
the worst possible moment to learn it doesn't work cleanly.

Test the fallback the way you'd test anything else that matters:
before you need it, not during. Turn the feature off, or revert it to a
simpler, safer version, as a drill, on a quiet Tuesday, and fix
whatever breaks then. The incident is a bad time to discover the kill
switch itself has a bug.

A named owner matters here for the same reason 8.1 insisted on one for
every register row. "The on-call rotation will catch it" answers a
different question than "who specifically reviews the quality-alert
queue." The first is about infrastructure paging. The second is a role
nobody fills by default, and it stays empty until someone deliberately
assigns it.

Test the kill switch on a schedule, too, not just once at launch. A
fallback verified working six months ago, against a version of the
feature that's since changed twice, is a fact about the past, not a
guarantee about today.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
A postmortem document is not the actual output of an incident. ==The
real output is a new case in 4.2's golden set==, so the same failure
gets caught automatically next time.
:::

@narrate
Say the honest caveat plainly, because a well-written postmortem feels
like closure, and it can quietly be the end of the learning instead of
the useful part of it.

A document explaining what went wrong helps the people in the room that
day. A new golden-set case, built from the exact input that triggered
the incident, helps every single build after it, forever, automatically,
every time the regression suite runs. One of these scales. The other
one is read once and archived.

Close every incident the same way: the specific failing input becomes a
permanent eval case before the postmortem doc is considered finished,
not as a follow-up task that quietly never happens.

This is also the fastest way this section's tools compound instead of
sitting separately. A stronger golden set makes 7.4's scorecard more
trustworthy the next time a model gets re-evaluated. A wider fairness
slice, discovered through an incident, makes 8.5's segmented pass rate
catch more next quarter than it does today. Nothing in this course is
really separate once it's actually running in production.

@slide definition
kicker: Naming it precisely
::: definition An AI incident plan
A quality-specific detection signal, a named owner, a tested kill
switch, and a rule that every real failure becomes a permanent eval
case, not just a document.
:::

::: example Try this yourself
Ask honestly: could you detect a quality-only incident on your feature
today, before a user complained about it. If the honest answer is no,
that's this lecture's finding.
:::

@narrate
That's the standard worth building toward, and the example question is
the one worth asking in the next team meeting, out loud, because most
people have never actually tested the honest answer.

Most teams discover, asking this for the first time, that their real
detection mechanism is a user complaining loudly enough, which is
detection, technically, but the slowest and most expensive version
available.

Ask it about the feature you're least confident in, not the one you're
proudest of. The proud one already gets attention. The quietly-shipped
one, the internal tool nobody's watching closely, is exactly where a
quality incident runs longest before anyone notices, precisely because
nobody built a signal for it in the first place.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Check whether you could detect a quality-only incident today
2. Test your kill switch once, deliberately, before you need it for real

@narrate
Two things before you move on.

Check the detection question honestly, the same exercise as every
register row this section has asked for: specific, not reassuring.

Then test the kill switch, for real, on purpose, before an incident
forces you to test it under pressure. If it doesn't exist yet, that's
today's finding, and it's a better one to have now than at two in the
morning during a real incident.

Both of these belong on the same afternoon as 8.1's first register row,
not a separate initiative for later. An incident plan with no detection
signal and no tested kill switch isn't a lesser version of a real plan.
It's the appearance of one, worth naming honestly rather than assuming
it covers you.

Next lecture is this section's workshop: red-team your own feature,
using everything from the risk register through today's incident plan,
against something you'd actually ship.
