@slide statement
kicker: Section 9 · Instrument before, not after
## The moment a suggestion appears on screen is the only moment you'll ever know exactly what it was.
lead: Miss it, and acceptance, adoption, and deflection stay permanently unanswerable for everything that happened before you started logging.

@narrate
A deterministic feature can afford to instrument late. The button did
the same thing in January that it does today, so a metric added in
March can still be reasoned about honestly for the months before it.

An AI feature doesn't get that grace period. The exact model, the exact
prompt version, the exact retrieved context behind a specific answer
exists for one moment, the moment it's generated, and then it's gone
unless something captured it. Add acceptance tracking three months
after launch and you haven't just missed three months of a number. You've
lost the ability to ever know what those three months actually looked
like.

That's the entire argument for this lecture existing before any other
analytics work: instrumentation is the one part of this section that
has to happen first, because it can't be reconstructed after the fact.

This is worth internalising before the engineering conversation even
starts, because instrumentation usually gets scoped by an engineer
working alone, without necessarily knowing which numbers this section
is about to ask for. Bring this schema to that conversation yourself,
before the sprint that ships the feature, not the sprint after.

@slide table
kicker: The event schema that makes it reconstructible
## Four events, one shared thread running through all of them

| Event | What it captures | Why it matters |
| --- | --- | --- |
| Shown | request_id, prompt version, model, timestamp | The exact configuration behind this specific output |
| Outcome | accept, edit, or reject, same request_id | 9.1's acceptance metric, computed directly |
| Escalation | whether a human took over, same request_id | 9.1's deflection metric, computed directly |
| Feedback | any explicit signal given, same request_id | Ground truth, when a user bothers to give it |

@narrate
Read the request_id column down the table, because it's doing the
actual work here. Every one of these four events shares the same
identifier, so any outcome traces back to the exact shown event that
produced it, and from there to the exact prompt version and model that
generated it.

This is the same discipline 7.2 already asked of your cost model: every
call identifiable, every number traceable to the request that produced
it, not aggregated into an anonymous total. If you're already logging a
request_id for cost, this schema mostly extends a pattern that already
exists.

Notice the feedback row is honestly the weakest of the four, and that's
fine. Most users never click thumbs up or down. Still worth capturing:
on the rare request where someone does, it's the closest thing to
direct ground truth this schema produces.

The escalation row deserves its own moment: it's the one most likely to
be missing on a feature that wasn't built with a human handoff in mind.
Take the refund agent from Section six. Does it hand a case like 4471
to a person? That's exactly what 9.1's deflection metric needs, tagged
with the same request_id as everything else, not reconstructed later
from a support ticket system never designed to connect back to it.

@slide two-col
kicker: The three months you can and can't get back
## Bolted on after launch, and planned before it

::: cols
:: card bad
### Instrumented after the fact
- Acceptance added in month three, no request_id on early events
- Can't tell which prompt version produced which outcome
- Three months of real user behaviour, permanently unanalysable
:: card good
### Instrumented before launch
- Every event carries the same request_id from day one
- Any outcome traces back to the exact version that produced it
- A prompt change's effect is visible the day it ships, not guessed at
:::

@narrate
Notice the bad column isn't a story about lazy engineering. It's what
happens by default when instrumentation gets treated as a launch
nice-to-have instead of a launch requirement, the same way a golden set
got treated as optional before Section four made the case for it.

The good column's real payoff shows up the first time you ship a
prompt change. With a request_id tying every outcome to a version,
acceptance before and after the change is two clean numbers you can
compare directly. Without it, you're left asking everyone in the room
whether the new version "feels" better, which is exactly the kind of
guess this whole course has been teaching you to replace.

Run the maths on what the bad column actually costs. Three months of
real usage, at whatever volume your feature actually sees, is the
single richest dataset you'll ever have about how real users respond to
real outputs. Losing it to a missing identifier isn't a rounding error.
It's the exact evidence a redesign conversation six months from now
will wish it had.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
Instrumenting everything is not the goal. ==Capture exactly enough to
compute 9.1's three metrics==, not a data lake nobody ever queries.
:::

@narrate
Say the honest caveat, because "log everything, decide what matters
later" sounds thorough and usually produces the opposite: a mass of
events nobody can query cleanly, with the four that actually matter
buried somewhere inside it.

Start from the metric, not the event. Adoption, acceptance, and
deflection each need a specific, small set of fields to compute. Build
to that list deliberately, and add more only when a real question needs
an answer this schema doesn't have yet.

This also has to run through 8.3's questions before a single event
ships. Whatever you log about a request is data you now hold, subject
to the same PII and residency questions as anything else this course
has covered. Log the request_id and the outcome. Think hard before
logging the full text of every request by default.

This is the same discipline as 9.1's acceptance metric turned inward on
itself: define the number first, then build only what computes it,
rather than collecting broadly and hoping a clean metric falls out the
other end. It rarely does. A broad collection effort with no metric
driving it tends to produce exactly the unqueryable pile this caveat is
warning against.

@slide definition
kicker: Naming it precisely
::: definition The instrumentation floor
Four events sharing one request_id: shown, outcome, escalation, and
feedback, sufficient to compute adoption, acceptance, and deflection
for any request, traced back to the version that produced it.
:::

::: example Try this yourself
Pick a request from last week. Try to answer honestly: was it accepted,
edited, or rejected, and which prompt version produced it. If you
can't, that's this lecture's finding.
:::

@narrate
That's the floor worth building before launch, not after, and the
example is worth running literally, on a real request, not as a
thought exercise.

Most teams running this for the first time discover the honest answer
is no, they can't reconstruct last week's request, because the
request_id thread was never actually connected end to end. That gap is
exactly what this lecture exists to close, before it costs three
months instead of one week.

Widen the exercise if the first attempt succeeds easily. Pick a request
from a month ago, then a quarter ago. The point where the honest answer
turns from yes to no is worth knowing precisely, because that's the
exact date this schema needs to have been live by, and probably wasn't.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Check whether a request_id currently connects your shown and outcome events
2. Confirm what you log respects 8.3's data questions before adding more

@narrate
Two things before you move on.

Check the request_id thread first. If shown and outcome events exist
but don't share an identifier, that's the single highest-leverage fix
available to you this section.

Then confirm, honestly, that what you're logging has already been
checked against 8.3's three questions. Add fields deliberately from
there, not by default.

Neither step needs new infrastructure to start. The request_id check is
a five-minute look at your existing event logs, and the 8.3 check is a
conversation you've already had once this course, applied to one more
system.
