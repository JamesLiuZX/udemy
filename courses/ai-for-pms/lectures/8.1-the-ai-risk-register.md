@slide statement
kicker: Section 8 · The tool
## One document, five categories, and a question borrowed straight from Section six: can it be undone, and what does it cost if it's wrong.
lead: Not a compliance checkbox. A register you actually update, with a name attached to every row.

@narrate
Two sections ago, 6.6 gave you a way to score one agent's action: can it
be undone, and what does it cost if it's wrong. This lecture applies the
identical question to everything else an AI feature can do, not just
the actions an agent takes.

That's the entire idea behind a risk register. Not a document that
performs caution with checkboxes and adjectives, a list of specific,
named risks, each one scored the same honest way, each one owned by a
real person, each one dated for its next review.

Five categories cover almost everything you'll actually find. The rest
of this section walks each one in depth. This lecture gives you the
register itself, and the map.

Build it before you need it, not after. Every one of these five
categories is cheaper to catch in a design review than in an incident
review, and a risk register's entire value is moving that discovery
earlier, back when a mitigation is still a code change instead of a
headline. Think about the feature you're closest to shipping right now
while you read the next slide. This works far better against something
real than against an abstraction, the same rule as every worksheet this
course has handed you.

## Five categories, one worked example each

| Category | Example risk | Blast radius | Covered in |
| --- | --- | --- | --- |
| Prompt injection | Untrusted input silently overrides an instruction | High: hard to trace, can act before review | 8.2 |
| Data & privacy | Personal data surfaces in a response or a log | High: can't be undone once seen | 8.3 |
| Regulatory | Feature falls under a rule you haven't checked | Medium: fixable, but costly if caught late | 8.4 |
| Bias & fairness | Quality or outcome varies by protected group | High: reputational, slow to detect | 8.5 |
| Operational | Nobody owns what happens when it breaks | Medium: fixable fast, if someone's paged | 8.6 |

@narrate
Read the blast radius column the same way you read it in Section six:
not a severity label someone assigned by feel, but the answer to two
specific questions, asked honestly, for this specific risk.

Data and privacy scores high for a structural reason worth naming. Once
a person's personal information has actually been seen, by a model
provider, a log, a support agent, undoing that is not a technical
problem you can patch. That's what makes it different from a regulatory
gap, which is real, and costly if caught late, but genuinely fixable
once you've found it.

Prompt injection scores high for a related but distinct reason: it can
act before a human ever reviews the output, the same category of
problem 6.1's workflow test was built to catch before anyone builds
around it. Bias and fairness earns its high score for close to the
opposite reason. It doesn't act fast, it hides well. A feature can run
for months producing a quietly unequal outcome before anyone notices
the pattern in aggregate, because no single case looks wrong on its own.

The operational row looks like the mildest one on the table, and for
most features it is, provided the "if someone's paged" clause actually
holds. An operational failure with no owner and no page isn't medium
risk any more. It's whatever the worst untreated version of that failure
looks like, running unattended for as long as it takes someone to
notice by accident.

The right column isn't decoration. It's telling you exactly where the
rest of this section goes deep on each category, in the same order this
table lists them. If a row here feels thin, that's the lecture to open
next, not a gap to guess your way through.

@slide two-col
kicker: What actually makes it a register
## A list of worries and a working risk register look similar. They aren't.

::: cols
:: card bad
### A list of worries
- "Prompt injection is a risk we should think about"
- Owner: the team, generally
- Reviewed: whenever someone remembers
:: card good
### A working register row
- The specific input path an injection could use, named
- Owner: one person, by name, not a team
- Reviewed: a real date, on a real calendar
:::

@narrate
Notice the bad column isn't wrong, exactly. Every sentence in it is true
and reasonable. It's just not a risk register yet, it's the version of
"important" the register exists to replace.

The same move you learned for a launch approver in 6.6 applies here
identically: a team can't be accountable for anything, because
accountability that belongs to everyone quietly belongs to no one.
"Legal" isn't a person who checks a date. A named person is, and that's
the difference between a register someone maintains and a document that
looked thorough the day it was written and stale by the next release.

Specificity is doing the same work here as it does everywhere else in
this course. "We should think about prompt injection" and "an uploaded
PDF's text can currently reach the system prompt unescaped" are not the
same sentence, and only the second one is a row someone could actually
close out.

This is also why the register belongs to product, not to legal or
security alone. The person who can name the actual input path, or the
actual feature behaviour behind a bias risk, is usually whoever wrote
the feature's spec in the first place, not a reviewer meeting the
feature for the first time in a compliance sync three weeks before
launch.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
"Legal will review it" is not a mitigation. ==Write the actual change
that lowers the blast radius==, not the name of whoever gets to worry
about it next.
:::

@narrate
Say the honest caveat, because "under review" is where risk register
rows go to quietly die.

A mitigation is a specific change: this input gets sanitised before it
reaches the prompt, this field gets redacted before logging, this
category of request gets a human in the loop. "Someone is looking into
it" describes a meeting that might happen. It doesn't lower a single
risk's actual blast radius, and a register full of rows like that gives
a false sense of coverage to anyone who skims it without checking.

If the honest mitigation today is "we haven't built the fix yet," write
that down exactly, with a date it's due, rather than dressing up an open
risk as a handled one. An honest, open row is worth more than a closed
one that isn't actually closed.

A stale register carries its own specific danger, close cousin to the
one 7.4 named for a stale scorecard. It doesn't just fail to help, it
actively reassures the wrong people. A launch reviewer who sees five
rows marked mitigated, dated eight months ago, reasonably assumes the
feature is covered. Nobody in that meeting is lying. The document is
simply no longer describing the feature as it currently exists.

@slide definition
kicker: Naming it precisely
::: definition A working risk register
Every real risk to the feature, scored by reversibility and cost like
6.6's blast radius, owned by one named person, with a specific
mitigation and a real review date, not a team and a hope.
:::

::: example Try this yourself
Open A11 and write one real row for your own feature, using the exact
input path or failure mode you already suspect, not a hypothetical one.
:::

@narrate
That's the standard worth holding every row to, and the definition's
order matters: scored, owned, mitigated, dated. Skip any one of those
four and the row is decoration, not risk management.

Write the one row you're already slightly worried about, specifically,
today. Most people opening this template for the first time already
know which risk they'd write if they were honest, and have simply never
had a document that asked them to name it plainly, with their own name
next to it.

That first row is usually the realest thing in the whole register.
Everything after it gets easier once the habit of writing a specific,
owned, dated row exists at all.

Run the exercise honestly rather than exhaustively. One well-scored,
well-owned row you'll actually revisit is worth more this week than
five rows copied from a generic checklist, because a generic row was
never scored against your feature's actual blast radius in the first
place, and it shows the moment anyone asks a follow-up question about it.

nobody will ever reopen.
