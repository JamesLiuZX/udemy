@slide quote
kicker: Section 7 · The model
attrib: The number your CFO actually asks about

> "Three multiplications turn a token count into the number that gets a launch review's attention."

@narrate
Last lecture gave you the mechanics: what gets billed, and why a long
conversation costs more per turn than the one before it. This lecture
turns that into an actual model, the one behind A09. Not a spreadsheet
trick: the same number, at three different scales, and each one tells
you something different.

You don't need a finance background for any of this. Every step is
multiplication, and the hard part was never the arithmetic. It's
knowing which number to multiply first, and being honest about which of
your inputs are measured and which are still a guess.

It's three multiplications, done in order. Tokens to a conversation
cost. Conversation cost to a monthly cost per user. Per-user cost to
total monthly spend. Each step looks trivial on its own. The gap
between what step one feels like and what step three actually says is
the entire point of building this properly instead of guessing at it.

Most teams stop at the first multiplication, because it's the one that
happens naturally while you're testing the feature. You run a
conversation, you check what it cost, you feel reassured, and you move
on. The other two multiplications only happen if someone deliberately
does them, and they're the ones that actually matter to anyone signing
off on a budget.

@slide table
kicker: The three levels
## Same conversation, three different questions answered

| Level | Calculation | Result |
| --- | --- | --- |
| Per conversation | (8,000 in tokens × 3/M) + (1,200 out tokens × 15/M) | $0.042 |
| Per user, per month | 0.042 × 4 conversations | $0.168 |
| All users, per month | 0.168 × 50,000 active users | $8,400 |

@narrate
Walk down that table the way you'd walk into the actual budget
conversation, because each row is the answer to a different question
someone in that room will ask.

The first row answers "does this feature work economically at all,"
and four cents a conversation usually sounds fine. The second row
answers "is this a rounding error for one user," and seventeen cents a
month usually still sounds fine. The third row answers the question
that actually matters, what this costs the company, and eight thousand
four hundred dollars a month is the number that gets someone's
attention in a way the first two never do. Same underlying cost. Wildly
different reaction depending which row you show.

Each multiplier deserves a second's thought too, not just the totals.
Four conversations a month is a real behavioural assumption about how
often someone actually returns to this feature, not an arbitrary round
number. Fifty thousand active users is wherever your product actually
is today, or wherever it's realistically headed in the window you're
budgeting for. Change either input and the bottom row moves by exactly
that proportion, which is worth demonstrating live in the room if
anyone pushes back on the number.

@slide two-col
kicker: Where the 8,000 and 1,200 actually come from
## One of these is a real number. The other is a guess wearing a real number's clothes

::: cols
:: card bad
### Estimated from a demo
- A few test conversations, run by the team that built it
- Naturally shorter and tidier than real usage
- The number that makes the launch deck look best gets kept
:: card good
### Measured from the golden set
- Section four's fifty real cases, run through the actual feature
- Includes the messy, long conversations real users produce
- The number is whatever it actually is, not whichever looks better
:::

@narrate
Notice this is the same discipline Section four spent an entire
section building, aimed at a cost model instead of a quality score.
Your golden set already contains real conversation shapes. Run token
counts against it instead of against the demo you'd show in a meeting.

What if you don't have a golden set yet for this feature? Name that as
a real gap, not a reason to fall back on the demo estimate anyway. A
rough token count from ten genuinely varied real-style conversations,
deliberately including the longest and messiest ones you can construct,
still beats five tidy ones assembled to look good in a review.

This matters because the gap between these two columns compounds
through all three rows of the table you just saw. A demo-estimated
token count that's thirty percent low doesn't stay a thirty percent
error. It's thirty percent low at the total-spend row too, and that's
the row someone actually budgets against.

There's a second reason the golden set specifically is the right
source, beyond honesty. It's already sorted by difficulty and shape,
because Section four made you choose it deliberately rather than grab
whatever was easiest to find. A demo reflects whichever conversation
the team happened to rehearse before the meeting.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
The token counts can be measured precisely. ==The usage assumptions,
conversations per user, active users, are guesses before launch==, and
the model is only as honest as those two numbers.
:::

@narrate
Say the honest caveat, because it's easy to present this model as more
certain than it actually is once the token maths looks this clean.

Four conversations a month and fifty thousand active users are the two
numbers doing the most work in that table, and before launch, neither
one is measured. They're informed guesses, and they deserve the same
treatment as the guessed retrieval targets back in Section five: write
them down, label them clearly as estimates, and revisit them the moment
real usage data exists. A model built on honestly-labelled guesses is
useful today. A model that quietly presents guesses as facts sets up
the wrong conversation the day real numbers arrive and don't match.

@slide example
kicker: Choosing where the estimate comes from
## Borrow from the closest real analogue, not from nothing

::: example The summariser's own conversations-per-user figure
The support-ticket summariser from Section two can borrow its
conversations-per-user figure from ticket volume on the channel it's
replacing, not invent one. A phone line nobody likes calling badly
understates a chat window open in the same tab as the work.
:::

@narrate
That's the general move: find the closest real number you already
track, rather than inventing one from nothing. A feature with no real
precedent at all is the honest exception, and there the right move is a
clearly labelled range, a low and a high case, rather than one
confident-looking number that happens to be a guess wearing better
clothes.

The friction gap in that example is the whole lesson. A phone call has
a hold queue and a script to fight through. A chat window is one click
from whatever the user was already doing, so it captures complaints a
phone line never would have heard about. Borrow across that kind of gap
and you understate real usage badly. Note which analogue you used
alongside the number itself, so anyone reviewing the model can judge
whether it's the right one.

@slide definition
kicker: Naming it precisely
::: definition Token cost model
A three-level calculation: measured tokens per conversation, to cost
per user per month, to total monthly spend, with every input number
labelled as measured or estimated.
:::

::: example Try this yourself
Build the three rows for your own feature. Use a real token count if
you have one, a clearly-labelled estimate if you don't. Notice which
row changes your reaction most.
:::

@narrate
That's the model worth keeping, and the definition's last clause is
doing real work: every number labelled as measured or estimated, not
presented as one undifferentiated fact.

Build it for something real, today if you can. Most people find the
same thing: the per-conversation number feels irrelevant, the per-user
number still feels irrelevant, and the total is the one that changes
how the room talks about the feature.

Keep the model after you build it, too. This isn't a one-time exercise
you file away once the launch review is over. The moment real usage
data exists, the estimated rows get replaced with measured ones, and
the model becomes something you check against reality on a schedule,
the same instinct Section five's corpus-drift lecture argued for
retrieval quality. A cost model built once and never revisited is
exactly how a feature quietly becomes unprofitable without anyone
noticing until the finance review asks why.

kicker: Before you move on
## Two things worth doing now

1. Download **A09, the token cost model**, and build all three rows for a real feature
2. Label your conversations-per-user and active-user numbers as measured or estimated

@narrate
Two things before you move on.

Download the template and fill in real numbers where you have them,
honest estimates where you don't. The structure matters more than
having every input finalised today.

Then go back and label the two usage assumptions specifically. If
you're presenting this model before launch, say so upfront. It's a far
stronger position than someone discovering later that a number they
assumed was measured was actually a guess all along.

Bring both versions to whoever owns the budget: the number as it stands
today, honestly labelled, and what it becomes if usage lands at the
higher end of your range. Both numbers earn more trust together than a
single confident figure ever does alone.
