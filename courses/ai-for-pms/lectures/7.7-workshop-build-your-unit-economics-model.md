The bar is identical too. Not perfect. Complete. Every number filled in
with something, even where that something is an estimate you'll refine
later, the same move as Section three, five, and six's workshops before
this one.

Cost and quality live on completely different spreadsheets in most
companies, and latency lives on a dashboard neither one ever opens.
This workshop's entire point is putting all three on one page, for one
feature, so the trade-offs this section named stop being abstract and
start being a number you can defend in a room.

That room is usually closer than it feels right now. A pricing review,
a roadmap prioritisation meeting, a CFO asking what a feature actually
costs to run at scale: this model is the document you'd want in hand
walking into any of those, built once instead of assembled under
pressure the night before.

@slide table
kicker: How to spend the twenty minutes
## Six lectures, five pacing blocks

| Minutes | Covers | Watch for |
| --- | --- | --- |
| 0-4 | Your real per-call cost, 7.1 and 7.2's model | Actual tokens counted, not estimated from memory |
| 4-8 | The quality floor and scorecard, 7.4 | Anything below the floor removed before cost compared |
| 8-12 | Which lever, if any, 7.3's traffic-pattern test | Only build the one your real traffic matches |
| 12-16 | Your own margin crossover, tier by tier, 7.5 | Use a real heavy user, not a blended average |
| 16-20 | The latency budget for this interaction, 7.6 | Set it from the interaction, not from today's number |

@narrate
Notice the first block leans on two lectures at once, because cost
never stands alone. 7.1 gave you the billing shape, tokens in and
tokens out, and 7.2 turned it into your own number. If you already have
A09 filled in from that lecture, this block is a five-minute copy, not
a rebuild.

The second block is where most people find the workshop's real value.
Running your own numbers through 7.4's floor first, before cost enters
the picture at all, usually disqualifies a candidate someone was
quietly already leaning toward for its price alone.

The third block moves fastest for most proposals. Check your traffic
against caching, batching, and routing's "earns its cost when" column
from 7.3, and if nothing matches yet, write down "none of these yet"
and move on. That's a legitimate finding, the same honesty 7.3 itself
asked for.

What's the exact tier where your feature's margin crosses zero? Minutes
twelve through sixteen ask for that number, not a feeling. If you don't
know your heaviest real user's usage, that's the finding this block
exists to produce, the same way it was in 7.5 itself.

The last block is the newest tool in the kit. Name your interaction
pattern from 7.6's table, read off its real tolerance, then check
whether today's build actually fits inside it.

@slide quote
attrib: The decision-reasoning line from 7.4's scorecard lecture

> "We picked flagship because the failure cost outweighs four times the spend."

@narrate
Recognise this shape. It's 7.4's own worked example of a decision
written down properly, and it's roughly what your workshop's final line
should sound like once all five blocks are actually filled in.

Notice what the sentence contains: a choice, a number, and the reason
the number was worth paying. Notice what it leaves out: no apology, no
hedge, no "we'll revisit this eventually" doing the work an actual
decision should do. That's the standard this workshop is asking you to
hit, not just for the model choice, but for the pricing and latency
lines sitting next to it.

Compare it against whatever you'd have written before this section
started. Most first attempts at justifying a model or a price point
sound like "flagship seemed like the safer choice," a sentence with no
number in it anyone could actually argue with. Twenty minutes from now,
yours should read closer to this one.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
The margin crossover block will feel like it's arguing against
launching at all. ==Compute it anyway, and write down the real
tier==, not the one that would feel better.
:::

@narrate
Say the honest caveat, because minute twelve is where people quietly
stop being rigorous, exactly where rigour matters most.

If your heaviest real user's actual usage produces a margin number that
makes you wince, that's not the model failing. That's the model doing
its job before a launch instead of during a finance review that catches
you off guard a quarter later. Write the real tier down, then decide
what to do about it: a usage-based add-on, a generous cap, or accepting
the loss deliberately because the tier is rare enough not to matter.

The same discipline applies to the latency block right after it. It's
tempting to write down today's measured number and call the budget
question answered. Set the budget from the interaction first instead,
the way 7.6 argued, and only then check whether today's build actually
fits inside it, rather than defining the budget as whatever the current
build happens to already hit.

@slide definition
kicker: Naming it precisely
::: definition A complete unit economics model
Cost per call, a quality floor cleared before cost is compared, the
tier where margin crosses zero, and a latency budget set from the
interaction, all for one real feature, on one page.
:::

::: example What to do when you finish early
Reread only the margin crossover block. If it names a real tier and a
real fix, not a rounded-off guess, the model is ready to bring to a
pricing conversation.
:::

@narrate
That's today's bar, stated as plainly as it was in every workshop
before this one: attempted, not perfected, and the one number most
likely to be quietly softened, the margin tier, computed for real.

If you finish with time left, don't polish evenly. Return to the margin
block specifically, the same instruction as always, because it's the
block most likely to be quietly incomplete or rounded toward comfort
rather than measured.

Resist the urge to smooth the cost and quality blocks instead, even
though they're the ones with the most satisfying numbers already filled
in. A tidy scorecard sitting next to an unchecked margin question is a
model that looks more finished than it actually is, and looking
finished is exactly the trap this course keeps warning you away from.

@slide bullets
kicker: Before you move on
## One thing worth doing now

Finish the model, with a real margin tier and a real latency budget, and send it to whoever owns pricing asking what surprises them

@narrate
One thing before you move on.

Finish all five blocks. Anywhere the honest answer is an estimate, label
it an estimate rather than letting it read as more certain than it is.
Then send it to whoever actually owns pricing for this feature, today,
and ask what number surprises them most. Expect it to be the margin
tier, not the cost per call.

That question alone is often worth more than the twenty minutes you
spent building the model. It's the same finding this course keeps
returning to: the person closest to a number sees the gap in minutes
that would take you a week to notice working alone.
