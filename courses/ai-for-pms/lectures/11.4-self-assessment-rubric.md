@slide statement
kicker: Section 11 · Grading your own work
## This isn't a grade you're waiting for. It's a checklist you run yourself, before anyone else sees this package.
lead: Every row here is a bar this course already argued for. Nothing on this rubric is new information, only a place to check you actually met it.

@narrate
Open your own capstone package next to this lecture, not after it. The
seven rows on the next slide are specific enough to check in the next
twenty minutes, and honest enough that a few of them will probably fail
on the first pass. That's the exercise working, not a bad sign.

Notice this rubric doesn't ask "is it good," the way most self-review
ends up working when nobody hands you specific criteria. Every row asks
something you can answer yes or no to, the same discipline 3.7 asked of
a PRD's own threshold. A checklist you can argue with yourself about
isn't doing its job yet.

This is also the last hands-on exercise in the entire course, which
makes it worth doing properly rather than rushing to the finish. Six
sections of workshops have been building toward the moment you check
your own work this closely. Treat it that way, not as a formality
between the capstone and the lecture that closes the course.

@slide table
kicker: Seven checks, one package
## Run each row against your own capstone

| Artifact | Passes if |
| --- | --- |
| PRD | The threshold is a number, not a vague goal |
| Golden set | It includes the exact boundary case and one adversarial case |
| Rubric | Two people would grade the same case the same way |
| Cost model | Every number is labelled measured or still projected |
| Model scorecard | A safety gate was applied before cost was compared |
| Risk register | All five categories have a real entry, not a placeholder |
| Metric tree | The North Star ties directly to the cost model's payoff claim |

@narrate
Read the golden set row against 11.2's worked example specifically:
the exact fifty-dollar boundary, and the exact injection sentence from
8.2, weren't decoration. They were what made that golden set pass this
exact row. If your own set only has clean, obvious cases, this is the
row that fails, and it's the cheapest one to fix before you call the
package finished.

Read the risk register row the same way. A placeholder like "no known
issues" in any of the five categories isn't a pass, it's an
unexamined category wearing a pass mark. 11.3's worked example gave
even prompt injection, the row already mitigated by design, a real
sentence explaining why. Every row deserves that same sentence, even
the ones that turn out fine.

@slide example
kicker: The two rows most first passes rush
::: example Quick isn't the same as clear
The PRD, rubric and model scorecard rows take seconds to check, which
is exactly why a threshold nobody could ever miss, or a safety gate
checked after cost instead of before, slips past them unnoticed.
:::

@narrate
Which of your own seven rows would you actually bet money still fails
on a second look? For most first-pass capstones, it's the last one. A
metric tree can look complete with a North Star and three branches
while having no real connection to the cost model two artifacts back.
If your North Star doesn't answer the specific question your cost
model's payoff claim depends on, the tree is decorative, the same
failure 11.1's coherence check warned the whole package against.

@slide two-col
kicker: Two ways to pass your own rubric
## Checking the box, and actually meeting the bar

::: cols
:: card bad
### Checking the box
- The cost model has a number in every field
- The risk register has five filled rows
- Passed, on a quick skim of your own work
:: card good
### Actually meeting the bar
- Every cost number is labelled measured or projected, honestly
- Every register row states a real mitigation, not just a risk name
- Passed, and could survive someone else reading it closely
:::

@narrate
Notice both columns can produce a package that looks identical from
across the room, every field filled in, every row present. The
difference only shows up when someone reads closely, which is exactly
why self-assessment is so easy to do badly without noticing.

Grade yourself the way 4.9 asked you to read an eval result: looking
for the reason you'd fail your own package, not confirming the reasons
it should pass. That's an uncomfortable habit to build against your
own work specifically, and it's the entire value of doing this exercise
seriously instead of skimming it.

Notice, too, that the box-checking column isn't dishonest on purpose.
It's usually just tired. By the time a capstone's sixth artifact is
finished, skimming your own work and calling it done is the natural
instinct, not a character flaw. Naming that instinct here is what
gives you a real chance of resisting it on this specific pass.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
This rubric checks form, not truth. ==It can confirm your cost model
has a number in every field. It can't confirm the number is right==.
:::

@narrate
Say the honest caveat, because a checklist this specific can start to
feel like more certainty than it actually provides.

Every row here checks that something exists and is labelled honestly,
not that the underlying judgement behind it was correct. Your cost
model can pass this rubric's row completely, every number labelled
measured or projected, while still resting on a volume estimate that's
wrong. That gap is exactly what 10.6's follow-up-question test and a
second reader are for, neither of which this rubric can substitute for.

Use this checklist for what it's actually good at: catching the
missing threshold, the placeholder risk row, the North Star with no
real connection to anything. Then find one other person and run 10.6's
test on the parts this rubric can't check.

@slide definition
kicker: Naming it precisely
::: definition A capstone that passes its own rubric
Seven specific criteria met honestly, not seven fields filled in, plus
one outside read this checklist alone can't replace.
:::

::: example Try this yourself
Run all seven rows against your own package right now. Mark each one
pass or fail, out loud, before you move to the next lecture.
:::

@narrate
Do this now, while your own package is still open, not as something to
come back to later once the feeling of being finished has already set
in.

Most people find one or two genuine fails on a first honest pass, most
often the golden set's boundary cases or the metric tree's connection
back to the cost model. Fixing either one usually takes under an hour,
which is a small price for a package that can survive more than a
skim.

One thing before you move on.

Run the checklist honestly, today, while the package is fresh enough
that you remember why you made each choice. Then fix what failed before
you're tempted to add a new artifact instead. A seventh artifact doesn't
rescue a package with one real gap in the six it already has.
