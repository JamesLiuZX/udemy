@slide statement
kicker: Section 7 · The levers
## Three ways to bring the total-spend row down, and only one of them fits most features.
lead: Each technique solves a specific shape of waste. Applied to the wrong shape, it's engineering effort with nothing to show for it.

@narrate
Last lecture ended on a question: which lever actually earns its
engineering cost for a feature like yours. Here are the three real
candidates, and the honest answer for each is "it depends on your
traffic," not "always" or "never."

None of these change what the model can do. They change what you pay
for the same output, and each one only pays off against a specific
pattern in how your feature actually gets used.

That distinction is worth holding onto through this whole lecture. Every
one of these three is invisible to the end user when it works. Nobody
notices a cache hit, a batched job that finished overnight, or a router
that quietly sent an easy question to a cheaper model. The entire value
shows up on an invoice, not in the product.

@slide table
kicker: The three levers
## Match the technique to the traffic pattern, not the other way round

| Technique | What it saves | Earns its cost when |
| --- | --- | --- |
| Caching | Repeated prefix tokens: system prompt, resent history | Traffic genuinely reuses the same context often |
| Batching | Per-request overhead, often a steep discount | The work can wait hours, not seconds |
| Model routing | Swaps to a cheaper model for easy queries | Query difficulty genuinely varies |

@narrate
Read the right column as a checklist, not a sales pitch, because
building any of these for traffic that doesn't match the pattern is
real engineering time spent on a discount nobody collects.

Caching is the direct fix for something you already met. Remember 7.1's
resent-history table: the same system prompt and growing conversation
history gets billed again, in full, on every single turn. Most
providers now discount tokens that repeat exactly from the previous
call, often steeply. That discount applies specifically to the
resent-history problem, not to genuinely new content, which is why
caching helps a long conversation far more than a short one.

Apply it to last lecture's own numbers and the shape becomes concrete.
Most of that eight thousand input tokens per conversation is system
prompt and resent history, the exact content a cache discount targets.
Only the newest turn's message is genuinely fresh each time. Cache the
repeated portion and the input side of that conversation's cost drops
by roughly a third, without touching a single word of what the feature
actually says to the user.

@slide two-col
kicker: Same lever, opposite verdict
## Batching earns its discount or wastes engineering time, on one question

::: cols
:: card bad
### Batching, misapplied
- Applied to live chat, where a user is watching the screen
- The discount exists, the latency it trades for kills the feature
- Saves money on a feature nobody will use once it's slow
:: card good
### Batching, applied well
- An overnight report generation job, nobody watching
- Same discount, and the extra hours cost nothing real
- The saving is free, because the wait was never the problem
:::

@narrate
Same technique, same discount, and the verdict flips entirely based on
one question: is anyone actually waiting on this response right now.

That single question sorts most of a feature's traffic faster than any
deeper analysis. A support chat, a live drafting tool, anything with a
person watching a cursor blink, rules out batching immediately,
whatever the discount looks like on paper. A weekly digest, a bulk
re-summarisation job, anything nobody's refreshing a page for, is
exactly what batching was built for.

Model routing has its own version of this question. It only pays off
if query difficulty genuinely varies, and varies in a way you can
detect cheaply before committing to the expensive model. A feature
where every single query needs your strongest model's reasoning gets
nothing from routing except the cost of building and maintaining a
router that always picks the same answer.

The trap with routing specifically is that the classifier deciding
"easy" from "hard" is itself a model call, and a badly built one can
misroute expensive queries to the cheap model and quietly tank quality
right where it matters most. Section four's whole discipline applies
here directly: you need an eval on the routing decision itself, not
just on the two models it's choosing between, or you won't know it's
wrong until a user notices before you do.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
All three levers add real engineering complexity. ==Build the one that
matches your actual traffic pattern==, not all three because each one
sounds individually reasonable.
:::

@narrate
Say the honest caveat, because it's tempting to greenlight all three at
once, since each one has a clean story on its own.

A cache that's rarely hit, a batch queue processing requests nobody was
willing to wait for, and a router constantly sending traffic to the
expensive model anyway are three real maintenance burdens for close to
zero combined saving. Pick the lever that matches a pattern you can
actually point to in your own usage, build that one properly, and leave
the other two for the traffic pattern that would justify them.

This is the same instinct as 6.4's guardrails lecture, aimed at
engineering effort instead of risk. Spend the budget where the pattern
is real, not evenly across every option that has a plausible-sounding
story. A team that ships one well-matched lever this quarter beats one
that ships three half-built ones nobody finishes maintaining.

@slide definition
kicker: Naming it precisely
::: definition The traffic-pattern test
Before building any cost lever, name the specific usage pattern it
depends on, and check your own feature against it honestly. No pattern
match, no saving, whatever the technique's reputation.
:::

::: example Try this yourself
Pick one lever and name your feature's actual traffic pattern against
its "earns its cost when" column. If you're guessing rather than
checking real data, that's this lecture's finding, not a detail.
:::

@narrate
That's the test worth keeping, and it's deliberately more boring than
the individual techniques, because boring and checkable beats exciting
and assumed.

Run it against real numbers if you have them. How often does the exact
same context actually repeat. How much of your traffic could genuinely
wait until tonight. How much does query difficulty actually vary,
measured, not guessed. Each answer points at exactly one lever, usually
not all three.

If you don't have real numbers yet, say so, the same discipline as
every guessed figure in this section. "I expect caching to help based
on how the feature is designed" is a legitimate starting point.
Presenting that expectation as a measured saving before anyone's
checked is where this exercise quietly turns into wishful thinking with
a spreadsheet attached.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Check how much of your feature's traffic repeats the same context
2. Name which single lever your actual usage pattern points to

@narrate
Two things before you move on.

Check the repetition question first, because caching is the lever most
features can adopt with the least new engineering, and it's the direct
answer to the specific waste 7.1 identified.

Then name one lever, not a wishlist of three. Say it plainly if the
honest answer right now is none of them, because your traffic doesn't
match any of the three patterns yet. That's a real finding too, and a
much better one than building a lever nobody's usage actually justifies.

not just cheap versus expensive, but which specific model actually
