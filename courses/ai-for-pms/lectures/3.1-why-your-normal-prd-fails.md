@slide statement
kicker: Section 3 · The diagnosis
## This PRD passed every review. Nobody could say what "done" meant, and nobody noticed until it shipped.
lead: Not a badly written PRD. A normal one, doing exactly what a normal PRD does, applied to something that isn't a normal feature.

@narrate
Every PM has written a PRD that sailed through review: clear problem
statement, clean user stories, a tidy list of acceptance criteria.
Engineering built it. QA checked the boxes. It shipped.

And then it was wrong, in production, in a way nobody in that review
had a sentence to point to. Not because the PRD was sloppy. Because a
normal PRD makes one assumption so basic nobody states it, and that
assumption is exactly the one an AI feature breaks.

The postmortem for that kind of launch almost never blames the writing.
It blames "we should have tested more" or "the model wasn't ready",
and both of those miss what actually happened. The document itself had
no place to write down what "ready" would have looked like. You cannot
test your way out of a specification that never defined what passing
means.

@slide table
kicker: The assumption that breaks
## What a normal PRD assumes, and what's actually true here

| A normal PRD assumes | An AI feature actually is |
| --- | --- |
| Same input, same output, every time | Same input, a range of outputs |
| A bug is present or it's fixed | A failure mode has a rate, not a yes or no |
| "Works" means it passes a checklist | "Works" means it clears a threshold, on a sample |
| QA can eyeball whether it's right | QA needs a rubric someone agreed on first |

@narrate
Remember the very first idea this course gave you: an AI feature is a
distribution, not a function. Here's where that stops being a slogan
and starts being the reason your PRD doesn't work.

A normal acceptance criterion assumes you can run the feature once and
get your answer: does it pass, or not. Run an AI feature once and
you've learned almost nothing, because the next run, same input, can
come back different. A single wrong answer isn't a bug to reproduce and
fix. It's one draw from a distribution you haven't measured yet.

That changes what "works" has to mean. Not a checklist item, a
threshold: clears some bar, on some sample, some agreed percentage of
the time. And QA can't verify that by eye. They need the rubric this
section is about to give you, not a gut feeling about whether an
answer looks right.

Look at that table's second row again, because it's the one that trips
up experienced PMs, not just new ones. A normal bug tracker assumes
every defect is a single, fixable thing: reproduce it, patch it, verify
the patch, done. A failure mode on an AI feature doesn't work that
way. It might never fully go away. The real question isn't "did we fix
it", it's "did we get the rate low enough, and do we know what that
rate actually is." That's a different kind of engineering conversation,
and it starts with a different kind of PRD.

@slide quote
"The AI should respond helpfully and accurately to customer questions."
attrib: An actual PRD acceptance criterion, quoted word for word

@narrate
Here's a sentence that passed a real review, and it's worth taking
apart, because every word in it feels reasonable and not one of them is
testable.

Helpfully, by whose judgment. Accurately, checked against what.
Customer questions, all of them, or the ones that happen to come up in
testing. There is no version of this sentence a QA engineer can run
against a feature and get a pass or fail out of. It isn't wrong
exactly. It just never was a specification. It was a hope, formatted to
look like one.

Here's how you can tell the difference for real, on any line in front
of you. Picture the worst plausible answer the feature could give,
something genuinely wrong, and ask whether this sentence would have
caught it before launch. "Helpful and accurate" doesn't catch anything,
because whoever's defending the launch can just as easily insist the
bad answer was helpful and accurate too. A real specification narrows
that argument down to a fact, not an opinion.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
The fix isn't a more detailed sentence. =="Extremely helpful and
highly accurate" is exactly as untestable as "helpful and accurate"==,
just longer.
:::

@narrate
Say the honest caveat, because the instinct once you spot this is to
add more adjectives, and that doesn't fix anything.

More detail in the same shape is still the same shape. What's actually
missing isn't better prose, it's a different structure entirely: a
dataset to test against, a rubric that defines the bar, a threshold
that counts as passing, and a plan for what happens on the cases that
don't. That's not a paragraph. That's the rest of this section.

@slide definition
kicker: Naming it precisely

::: definition The untestable criterion
An acceptance line no one could actually fail a build against, because
it names a quality instead of a measurement. If QA can't run it, it
isn't a specification yet.
:::

::: example Try this yourself
Pull up your team's current AI feature PRD. Find one acceptance
criterion and ask: could QA actually fail a build against this, today,
with what's written? Most can't.
:::

@narrate
That's the test worth applying to every acceptance criterion you've
ever written for one of these features, not just the plainly vague
ones.

Do it for real, on a document you actually own. Find one line, and ask
honestly whether it could fail a build. If you're not sure, that
uncertainty is the answer.

## Two things worth doing now

1. Find one untestable line in your team's current AI feature PRD
2. Notice what information would need to exist for it to be testable

@narrate
Two things before you move on.

Find one acceptance criterion in a real PRD that couldn't actually fail
a build. Then notice, specifically, what's missing: a sample to test
against, a definition of good, a threshold, anything concrete enough to
run.

Next lecture turns that gap into the fix: acceptance criteria written
as evaluation thresholds, the exact sentence that replaces "helpful and
accurate."
