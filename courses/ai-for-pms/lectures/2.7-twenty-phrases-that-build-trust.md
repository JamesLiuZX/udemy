## Twenty phrases, said at the right moment, change how the rest of a technical conversation goes.
lead: Not a script to recite. Every one of these only works because you now understand what's behind it.

@narrate
Here's the reward for the last six lectures: twenty specific things to
say, each one signalling, correctly, that you understand what you're
asking about.

None of these are magic words. They work because you now know what's
actually behind each one, the stack from lecture one, the retrieval
mechanics, the difference between an average and a p95. Say any of
these without that underneath, and the first follow-up question will
find the gap immediately.

Organised into four groups, matching the four things this section
actually taught you. Read through once, then go back and notice how
many of these are really the same move, applied to a different part of
the stack: ask what's actually true before agreeing with what's being
claimed.

@slide table
kicker: About the stack
## Group one: which layer is this actually in

| Say this | It signals |
| --- | --- |
| "Which layer is this actually in?" | You know there are five, not one |
| "Is this retrieval or the model itself?" | You've separated data from reasoning |
| "What's the fallback if the call fails?" | You're thinking past the happy path |
| "Did we prompt this, or fine-tune it?" | You know these aren't the same fix |
| "Does this hold context across turns?" | You know state is a real design choice |

@narrate
First group, straight from the stack diagram two lectures back.

"Which layer is this actually in" is worth leading with in almost any
debugging conversation, because it's the question that stops a vague
complaint from staying vague. "Retrieval or the model itself" does
similar work specifically for anything that looks like a wrong answer,
and it's usually the second question, right after the first one narrows
things down.

The fallback question is the one people skip under deadline pressure,
and it's worth asking even when the answer is obvious. If nobody's
thought about what happens when the call times out or errors, you've
just found the gap before a user does. And asking prompt versus
fine-tune, out loud, tells the room you know those are two different
costs, not two words for the same fix.

Notice none of these need you to write code. They're technical in the
sense of knowing where to point, not in the sense of being able to fix
it yourself.

kicker: About data and context
## Group two: what's actually feeding the answer

| Say this | It signals |
| --- | --- |
| "How are we chunking this?" | You know retrieval lives or dies on boundaries |
| "What's actually in the context window here?" | You'd check assembly before wording |
| "How fresh is the index?" | You know similar isn't the same as current |
| "What's our top-k?" | You know retrieval returns a shortlist, not one answer |
| "Is this grounded, or reasoning from memory?" | You separate lookup from recall |

@narrate
Second group is everything from inside the RAG box, and "how are we
chunking this" is the one worth memorising first.

It's a question most PMs never think to ask, and it's very often where
the actual bug lives: a badly split document, not a badly built model.
Asking it early tells the room you already know that.

"How fresh is the index" catches the other common failure, the
confidently wrong answer built from something true eight months ago.
And "is this grounded, or reasoning from memory" is worth asking any
time an answer sounds suspiciously fluent for something nobody actually
gave it. Fluent and grounded are not the same thing, and this question
is how you find out which one you're looking at.

kicker: About performance and evidence
## Group three: what the numbers actually say

| Say this | It signals |
| --- | --- |
| "What's the p95, not the average?" | You know the average hides the tail |
| "Is that benchmark representative of our task?" | You've read past the leaderboard |
| "What's our pass rate on the golden set?" | You expect a real eval, not a vibe |
| "Time to first token, or total time?" | You know perceived speed isn't total speed |
| "Does that hold under real concurrent load?" | You know a demo isn't production |

@narrate
Third group is where this section overlaps hardest with Section four,
and "what's our pass rate on the golden set" is the one that does the
most work.

It presumes a golden set exists. Asking it plainly, as if of course
there's one, is often the moment a room realises there isn't, and
that's a far more useful outcome than the question sounding rhetorical.

"Is that benchmark representative of our task" belongs right after
anyone cites a leaderboard number in a model comparison. And "does that
hold under real concurrent load" is the one question that catches a
demo before it becomes a promise. Ask it before launch, not during the
first busy Monday after.

@slide table
kicker: About risk and limits
## Group four: what happens when it's wrong

| Say this | It signals |
| --- | --- |
| "What's the blast radius if this is wrong?" | You've read the archetype chart |
| "Is there a human in the loop before this ships?" | You know act is not summarise |
| "What's the model's training cutoff?" | You know capability has a calendar |
| "How do we know it hasn't just memorised this?" | You know a good score can still be contaminated |
| "What would make us turn this off?" | You have an exit plan, not just a launch plan |

@narrate
Last group is the one nobody enjoys asking, and it's the one that
matters most.

"What would make us turn this off" is rarely asked before launch, and
it's exactly the disqualification checklist from Section one, asked one
more time, out loud, in the room where it can still change the plan.

"What's the blast radius" is worth asking about every feature, not
just the risky-looking ones, because the answer tells you how much
evaluation the feature actually owes you. And "how do we know it hasn't
just memorised this" is the quiet, technical way of asking whether a
benchmark score can be trusted at all, from two lectures back.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
These phrases only work if you can survive the follow-up question.
==Ask "what's our p95" and freeze when someone answers==, and you've
signalled the opposite of what you intended.
:::

@narrate
Say the honest caveat, because this list is easy to misuse.

Memorise the twenty phrases without the six lectures behind them, and
you'll ask a sharp question and have nothing to do with the answer.
That's worse than not asking, because it's now visible that the
question was borrowed, not understood.

Use these because you've earned them over this section, not instead of
earning them.

kicker: Before you move on
## Two things worth doing now

1. Pick three phrases you'd actually use this week, not all twenty
2. Say each one out loud once, with the follow-up you'd expect

@narrate
Two things before you move on, and keep this one small on purpose.

Pick three phrases from all twenty, the ones that fit a conversation
you can already see coming this week. Twenty at once is a performance.
Three, used naturally, is a habit.

Then say each one out loud, and imagine the actual follow-up question:
can you answer it? If so, you're ready to use the phrase for real.

That closes out the vocabulary itself. Next lecture recaps the section
and hands off to Section three, where you finally write a spec an
engineer actually trusts.
