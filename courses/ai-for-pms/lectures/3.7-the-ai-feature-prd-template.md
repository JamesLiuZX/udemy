## Six lectures, one document. Here it is, section by section, with nothing left as an exercise for later.
lead: Every clause you've written this section has a home in this template. This is where they all go at once.

@narrate
You've written pieces of this document across the last six lectures: a
threshold sentence, a dataset commitment, a rubric commitment, a
failure taxonomy, a degradation path, a human-in-the-loop pattern. Here
they all are, assembled into one template, in the order they actually
belong.

This is A01, attached to this lecture. Download it and follow along,
because the fastest way to learn a template is to fill one in while
someone walks through it, not to read it cold later.

Nothing in this template is new information. Every sentence you're
about to see was earned, specifically, in one of the last six
lectures. What's new is seeing all of it in one place, in the order an
engineer or a QA lead would actually want to read it, instead of
scattered across six separate insights you'd have to remember to
combine yourself.

That ordering matters more than it looks like it should. A reviewer
reading a PRD top to bottom builds trust or loses it section by
section. Open with a sharp threshold and a real dataset commitment,
and the failure taxonomy a few sections later reads as thorough
rather than paranoid. Open with vague acceptance criteria, and nothing
after it gets read as carefully, because the reviewer has already
learned not to trust the document.

## Eight sections, and where each one came from

| Section | What it must contain | From |
| --- | --- | --- |
| Problem & archetype | What it does, which of the seven archetypes | Section 1 |
| Acceptance criteria | The four-part threshold sentence | 3.2 |
| Golden dataset | Size floor, coverage, source, owner, deadline | 3.3 |
| Rubric | Where it lives, pass/fail mapping, calibration proof | 3.4 |
| Failure taxonomy | At least three distinct, named failure types | 3.5 |
| Degradation path | Disclaim, escalate, or decline, and when each applies | 3.5 |
| Human-in-the-loop | Which pattern, matched to blast radius | 3.6 |
| Ownership & review | Who updates the rubric and dataset, how often | 3.3, 3.4 |

@narrate
Read straight down that left column and notice something: the first
two rows are close to what any decent PRD already has. Everything from
row three onward is what this section actually added.

That's deliberate, and it's worth saying plainly before you fill in
your own. You're not throwing out what you already know about writing
a PRD. Problem, context, archetype, all of that stays exactly as
familiar as it's always been. What's new is everything underneath it:
the six sections that turn a hopeful description into something QA,
engineering, and a launch reviewer can all hold you to.

Walk the table again with one question in mind: which row would
someone in a launch review actually push back on? Almost never the
problem statement, everyone agreed on that weeks ago. It's the
threshold, the dataset, and the degradation path, the three rows
teams historically leave vaguest, precisely because they used to be
the hardest to write. They're not hard any more. You've already
written a version of each one.

::: cols
:: card good

- Problem statement and user stories
- Rollout plan and success metrics
- Anything that doesn't depend on the output being probabilistic
:: card bad
### What this section added
- A dataset, a rubric, and a threshold, not adjectives
- A failure taxonomy and a degradation path
- A named human-in-the-loop pattern, matched to blast radius
:::

@narrate
This split matters because a common reaction to this whole section is
to assume it demands a completely different way of writing a PRD.
It doesn't.

Everything in the first column is the PRD skill you already have,
untouched. What's genuinely new lives entirely in the second column,
and it's new because it answers questions a deterministic feature never
had to ask: what happens across a range of outputs, not one, and what
happens specifically when this one lands on the wrong side of the
range.

Notice, too, that the second column is shorter to list than it was to
learn. Three bullets, six lectures. That's not a coincidence, and it's
not this lecture cutting corners either. Each of those three bullets is
carrying an entire method behind it: a coverage strategy, a calibration
protocol, a taxonomy built from real failure modes. The template
compresses the method into a checklist. It doesn't replace the method,
and you now have both.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
Filling in every section is not the same as filling it in well. ==A
template completed with vague content fails exactly like the
untestable line from lecture one==, just now with better formatting.
:::

@narrate
Say the honest caveat, because a template can create a false sense of
completeness all on its own.

Write "the rubric is attached" in that section without an actual
calibrated rubric behind it, and you've reproduced the exact failure
this whole section opened by diagnosing. You've just hidden it one
layer deeper, behind a section heading that looks thorough. The
template is scaffolding for the thinking. It was never a substitute
for doing it.

A reviewer skimming eight completed sections will feel reassured
whether or not the content underneath is real, and that's exactly the
risk. The honest test isn't whether every box has text in it. It's
whether someone could act on that text: run the calibration check,
find the dataset, apply the threshold. If a section reads well but
nobody could actually do anything with it, it's not finished, it's
just well written.

@slide definition
kicker: Try this yourself

::: definition Right now, not later
Open A01. Pick the feature you're closest to. Fill in the acceptance
criteria section first, even roughly, before touching anything else.
:::

::: example Why that section first
It's the one every other section has to support. A weak threshold
makes the dataset, rubric, and failure taxonomy easy to skip. A real
one forces the rest of the document to actually hold up.
:::

@narrate
That's the instruction for the rest of today, not a suggestion for
sometime this quarter.

Start with acceptance criteria specifically, because it's the section
that exposes whether the rest of the document is doing real work.
Once you've written a threshold you'd actually hold a launch to, the
dataset and rubric sections stop being paperwork and start being the
thing that makes that threshold checkable.

Expect it to take longer than filling in the problem statement did,
and treat that as a good sign, not a delay. The problem statement was
never the hard part of any PRD. It never has been, for any feature,
AI or otherwise. The fact that acceptance criteria now takes real
thought is this section working exactly as intended.
