@slide statement
kicker: Section 10 · Building it yourself
## The fastest tool you'll ever ship is the one nobody reviewed. That's exactly why it matters who else ends up depending on it.
lead: Vibe-coding is a real PM skill now, not a shortcut to apologise for. This lecture draws the line precisely, instead of pretending it isn't there.

@narrate
A coding assistant that turns a described workflow into a working
script, a tool like ChatPRD that turns a rough idea into a structured
draft, a Workspace or Notion automation that used to need an engineer's
help: all of this genuinely changes what one PM can build alone, this
afternoon, without filing a ticket.

That's real, and this course isn't going to pretend otherwise. What it
won't do is stop there, because the interesting question was never
whether you can build it. It's what happens six weeks later, when the
small script you wrote for yourself is quietly the thing three other
people now depend on, and nobody ever asked whether it was built to
carry that.

None of this is really new in kind, only in speed. PMs have always
found ways to work around a full engineering queue: a spreadsheet
formula, a macro, a borrowed hour from a friendly engineer. What
changed is that the gap between having an idea and having a working
thing collapsed from days to minutes, and a gap that used to force you
to slow down and think no longer does that automatically.

@slide table
kicker: The same skill, four different blast radii
## Where vibe-coding is free, and where it isn't

| Use | Blast radius | Verdict |
| --- | --- | --- |
| A script summarising your own inbox | Low, just you | Build it freely |
| A prototype to bring into a PRD conversation | Low, throwaway | Build it freely |
| A tool your team now runs daily | High, others depend on it | Needs real rigor |
| Anything touching real customer data | High, real data | Route through 8.3 first |

@narrate
Read the blast radius column the exact same way 6.6 taught you to read
it for an agent's actions: can this be undone, and what does it cost
if it's wrong. Vibe-coding doesn't change that question. It only
changes how fast you can build something before anyone's asked it.

The top two rows are where this skill earns its reputation. A script
that summarises your own inbox, a rough prototype you'll throw away the
moment the real PRD conversation starts, cost nothing if they're wrong,
because the only person affected is you, and you'll notice immediately.
Build these constantly. This is the fastest feedback loop available to
a working PM.

The bottom two rows are where the exact same skill gets genuinely
dangerous, and it's dangerous for a reason specific to vibe-coding: the
tool got built fast enough that none of this course's earlier
discipline, a golden set, a risk register row, a named owner, ever had
a natural moment to attach itself. Slow, traditional engineering forced
those checkpoints by taking weeks. This doesn't, which means you have
to add them back in deliberately.

The last row deserves the most caution, because it's the one most
likely to feel like the first row while actually being the third. A
script that reads a spreadsheet of customer emails to send a
personalised follow-up feels exactly like the harmless inbox-summary
example, right up until you remember 8.3's three questions: where does
that data go, whose laws govern it, and did anyone agree the vendor
behind your coding assistant should ever see it. A prototype built to
prove an idea and a tool that now processes real customer data are not
the same category, even when they started from the identical five
minutes of typing.

@slide two-col
kicker: The moment nobody notices
## A personal script, and the same script after it quietly graduated

::: cols
:: card bad
### Still treated as personal
- Three teammates now run it daily
- No named owner, no documented failure mode
- Breaks silently, and whoever's on call didn't know it existed
:: card good
### Graduated on purpose
- The moment a second person depends on it, it gets an owner
- A real row in 8.1's register, blast radius scored honestly
- Documented well enough that its author being on holiday doesn't matter
:::

@narrate
Notice the trigger in the good column: a second person depending on it,
not a calendar date or a size threshold. That's the actual moment a
personal tool becomes a small piece of infrastructure, and it's a
moment worth noticing on purpose rather than discovering during an
incident.

This is 8.6's incident-response lecture in miniature, arriving earlier
than anyone expected. A tool with no named owner and no documented
failure mode is exactly the gap 8.6 warned about, just wearing a
smaller, friendlier shape because you built it yourself in an
afternoon instead of commissioning it from a team.

Ask the ownership question specifically, not generally. "Someone
should probably own this eventually" is the sentence that lets a tool
drift for months with no name attached. "I own this until a specific
date, then we decide together whether it graduates" is a sentence with
an actual deadline built into it, and deadlines are what turn a good
intention into something that happens.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
Vibe-coding lowers the cost of building something. ==It does not lower
the cost of it being wrong==, and the speed makes it easier to skip the
checks that used to be forced by how long building used to take.
:::

@narrate
Say the honest caveat, because the entire appeal of this skill, speed,
is also exactly what makes it easy to outrun your own judgement.

Traditional engineering used to impose discipline by accident: a script
that took three weeks to build got a code review, a second pair of
eyes, simply because three weeks felt like it deserved one. A script
built in twenty minutes doesn't get that for free anymore. You have to
choose to apply the same discipline deliberately, at a speed that no
longer forces it on you.

This is worth saying plainly because the framing around these tools, in
every product demo and every announcement, is speed as the entire
pitch. Speed is real and worth having. It was just never the same
thing as correctness, and conflating the two is exactly how a
confidently wrong five-minute script does as much damage as a
confidently wrong five-week project, just more often, because building
one got so much cheaper.

@slide definition
kicker: Naming it precisely
::: definition The vibe-coding line
Build freely for yourself and for throwaway prototypes. The moment a
second person depends on it, or it touches real data, it inherits the
same rigor as anything else this course taught you to ship.
:::

::: example Try this yourself
List every vibe-coded script or automation you've personally built.
Mark which ones a teammate now actually depends on.
:::

@narrate
That's the line worth drawing before the next script, not after
someone else is already relying on one you built for yourself.

Most people running this list for the first time find at least one
tool that quietly crossed the line months ago, still carrying none of
the ownership or documentation the crossing should have triggered.
That's not a confession. It's this lecture's actual finding, and it's
a cheap one to fix today compared to during an outage.

Most people are also surprised by their own list in both directions.
There are usually more vibe-coded tools quietly running than anyone
remembers building, and at least one of them is doing something with
real consequences nobody's checked on since the week it shipped.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. List your own vibe-coded tools and mark which ones crossed the line
2. Give each crossed-line tool a named owner and a register row

@narrate
Two things before you move on.

Make the list honestly, including the small ones you'd forgotten you
built. Most people have more of these than they expect.

Then, for anything a teammate now depends on, give it a real owner and
a row in 8.1's register, the same treatment as any other tool this
course has taught you to take seriously.

Neither step needs permission from anyone else to start today. The
list is yours to make honestly, and naming an owner for a tool you
already built is a five-minute conversation, not a project.

Next lecture is packaging your artifacts into a portfolio: turning
everything you've built across this entire course, including today's
list, into something you'd actually hand an interviewer.
