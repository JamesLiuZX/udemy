@slide statement
kicker: Section 2 · Latency and throughput
## The demo felt instant. Production, at lunchtime, did not. Same model, same code, different word for what changed.
lead: Latency and throughput are two different measurements, and the gap between a demo and production usually lives in the one nobody asked about.

@narrate
Here's a sentence worth understanding precisely, because it comes up in
almost every capacity conversation: "latency's fine on average, but p95
is rough."

Latency is how long one request takes, start to finish. Throughput is
how many requests the whole system can handle at once. They sound like
the same conversation. They're not, and mixing them up is how a feature
that tested beautifully in a quiet demo turns sluggish the moment real
users show up at the same time.

By the end of this lecture you'll know which question to ask when
someone shows you a latency number, and it's rarely "what's the
average."

Neither of these is a purely technical concern you can leave to
engineering and forget. Latency shows up directly in whether people
finish using your feature or give up halfway through. Throughput shows
up as a capacity bill and a ceiling on how many users you can serve at
once. Both are product decisions wearing an engineering vocabulary, and
that's exactly why the vocabulary is worth having yourself.

@slide table
kicker: Two different questions
## Latency answers one question. Throughput answers a different one.

| | Latency | Throughput |
| --- | --- | --- |
| Question | How long does one request take? | How many can the system handle at once? |
| Unit | Seconds, or milliseconds | Requests, or tokens, per second |
| A user feels it | Directly, every single time | Only indirectly, as things slow down |
| You improve it by | A faster model, less context, streaming | More capacity, batching, caching |

@narrate
Keep these separate, because the fix for one can make the other worse.

Latency is what a single person waiting for a single answer
experiences. Make the model faster, trim what's in the context, or
stream the response so something appears immediately, and latency
drops. Throughput is a system property: how many of those requests the
whole thing can process per second before it falls behind.

Here's where they collide. A common way to raise throughput is
batching several requests together before processing them. That's
great for the system's total capacity, and it often means one
particular request waits slightly longer before its batch is ready to
go. Improve throughput carelessly, and you can quietly make latency
worse for everyone in the batch.

One more distinction worth having: what a user perceives as fast often
isn't total completion time, it's time to first token. Stream the
answer as it's generated, and a five-second response can feel instant
because words started appearing after four hundred milliseconds. Show
nothing until the whole thing is ready, and that same five seconds
feels like a hang.

@narrate
Here's why engineers won't just tell you the average, and why they're
right not to.

Picture a hundred requests to your feature. Most land under a second,
and the average latency you'd calculate across all of them looks
great, comfortably under a second. But look at the shape, not the
average. A handful of requests, maybe one or two in a hundred, take
four, eight, ten seconds. Average them into the rest and they nearly
disappear from the number. They don't disappear from the person who
waited ten seconds.

P95 is the number that catches that. It's the response time slower
than ninety-five percent of requests, and faster than the worst five
percent. P99 is stricter still. Neither one is trying to be dramatic.
They're trying to describe the tail an average is specifically built to
hide.

This is why "average latency" is close to a red flag on its own when
it's the only number offered. It's not that averages are wrong,
they're answering a genuinely different question: what does a typical
request look like. P95 answers what an unlucky request looks like, and
for a feature people use daily, someone hits that unlucky case
regularly enough to notice.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
P95 isn't fixed, it moves with real traffic. ==A demo run alone at 2am
showing 400 milliseconds tells you nothing about lunchtime==, when a
thousand other requests are competing for the same capacity.
:::

@narrate
Say the honest caveat, because a fast demo is the single most common
way this number gets misrepresented, usually by accident.

Run a feature with no one else hitting the system, and latency is
close to the best case every time: no queueing, no contention, nothing
waiting on a batch to fill up. Run the same feature at lunchtime, with
real concurrent load, and p95 can move by an order of magnitude,
because throughput and latency were never actually separate
conversations. They just look separate until the system is busy.

Ask for p95 under realistic concurrent load specifically. A demo number
with nobody else in the room is closer to marketing than to a promise.

@slide definition
kicker: Naming it precisely

::: definition p95 latency
The response time slower than ninety-five percent of requests. Not the
average, and not the best case. What the unluckiest one in twenty
users actually experienced.
:::

::: example Try this yourself
Next benchmark table or vendor pitch you see, find the p95 number
specifically. If only an average is offered, ask for it before you
trust the comparison.
:::

@narrate
That's the number worth asking for by name, because "average latency"
and "p95 latency" can describe the same system and tell two completely
different stories.

The exercise is a habit, not a project. Every time someone shows you a
latency number from here on, notice whether it's an average or a
percentile, and ask for p95 specifically if it isn't already there.
It's a five-second question that heads off a much longer conversation
later.

## One thing worth doing now

Find your own feature's p95 latency, not just its average, and ask whether it was measured under real concurrent load

@narrate
One thing before you move on.

Find your own feature's p95, not the average, the actual p95. If nobody
can produce it, that's worth flagging on its own. Then ask the harder
question: was that number measured under real concurrent load, or in a
quiet moment that flatters it? The gap between those two answers is
usually the gap between the demo and production.
