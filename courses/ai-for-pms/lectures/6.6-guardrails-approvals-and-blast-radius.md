## The question worth asking instead

::: cols
:: card bad
### "Is this agent safe?"
- Answered by whoever built it, about their own work
- Sounds confident, decides nothing
- No action anyone could actually point to
:: card good
### "What's its blast radius?"
- Two questions: can this be undone, and what does it cost if not
- Forces specific actions onto the table
- An answer you can check today
:::

@narrate
"Is this agent safe" invites a vague answer, because safety isn't one
thing. "What's its blast radius" doesn't, because blast radius is
exactly two questions: can this action be undone, and how much does it
cost if it's wrong. Answer both, honestly, and you know precisely where
a guardrail actually needs to go.

Ask "is it safe" in a review and you'll get a confident yes from
whoever built it, because they're answering about the agent's
intelligence, not its consequences. Ask about blast radius instead and
the conversation moves to specific actions, specific numbers, and a
specific answer you can actually check.

This isn't abstract. It's the direct continuation of 6.2's
read-versus-write question and 6.4's escalate-to-a-human step, given
the actual framework that tells you which actions need which treatment.

Every lecture in this section so far has been building toward this one
without quite naming it. Tools and MCP gave you what an agent can
reach. The reliability maths gave you how often it goes wrong.
Guardrails are where those two facts turn into an actual decision about
where a human has to stand between the agent and the consequence.

@slide table
kicker: The framework
## Reversibility and cost, crossed, not dollar amount alone

| Reversible | Cost if wrong | Verdict |
| --- | --- | --- |
| Yes | Low | Autonomous, no gate needed |
| Yes | High | Autonomous with a spend cap, logged |
| No | Low | Autonomous, flagged for review after |
| No | High | Always needs approval before it happens |

@narrate
Read this table by the two questions, not by the dollar figure alone,
because dollar amount on its own misleads you in both directions.

A twenty-pound refund that's trivially clawed back if it's wrong doesn't
need a human standing between the agent and the action, whatever your
instinct about "money moving" says. An email to a journalist costs
nothing and is completely irreversible the moment it sends. That belongs
in the bottom row with the eight-hundred-pound refund, not the top one,
because reversibility, not price, is doing the real work in this table.

Most teams default to gating by dollar amount because it's the easiest
number to write into a policy. It's also the wrong axis on its own. A
five-pound action that posts publicly and can't be taken back deserves
more caution than a five-hundred-pound one your finance system can
reverse with one call. Ask both questions every time, not just the one
that's easiest to put a number on.

kicker: Where the framework actually lives
## A guardrail is a mechanism, not a feeling

::: cols
:: card bad
### "We review its work"
- Vague, applied inconsistently by whoever's on shift
- No specific action ever named as the gated one
- Easy to skip under deadline pressure
:: card good
### Named gates on named actions
- The exact actions from the bottom two rows, listed
- A specific approver, not "someone"
- The agent literally cannot execute that action without it
:::

@narrate
The difference between these two is the difference between a policy and
a feeling. "We review its work" describes an intention. A named gate on
a named action is enforced in the system itself, the same boundary 6.2
drew between what the model requests and what your system permits.

Build the gate so the agent cannot technically complete the gated action
without approval, not so that a reviewer is supposed to catch it after
the fact. A policy a tired reviewer can skip under deadline pressure
isn't a guardrail. It's a suggestion with a job title attached.

Test whether a gate is real with one question: can the action complete
if the approver is on holiday and nobody covers for them. If the answer
is yes, eventually, through a timeout or a default-approve setting
someone added for convenience, it was never actually a gate. It was a
delay with an expiry date.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
Gate everything and you haven't built an agent, you've built a slow
form. ==Reserve approval gates for the bottom two rows==, not every
action the agent takes.
:::

@narrate
Say the honest caveat, because the instinct to add a gate to everything
after seeing that table is understandable and it defeats the entire
point of automating the task in the first place.

What's the point of an agent whose every action waits on a human? None,
really. It isn't faster than doing the task yourself, and it quietly
trains the approver to click approve without reading, which is worse
than no gate at all. Reserve gates for
where this lecture's table actually puts them, the irreversible and the
expensive, and let the top row run on its own. That's not a compromise
on safety. It's what makes the safety on the rows that matter credible
instead of theatre.

Gate fatigue is the specific failure worth naming. An approver who sees
forty low-stakes approval requests a day stops reading any of them
carefully by request twelve, and the one genuinely dangerous request
that slips through on day thirty gets the exact same reflexive click as
the harmless thirty-nine before it. Fewer, better-chosen gates protect
people better than many indiscriminate ones, precisely because attention
is the scarce resource a gate is actually spending.

@slide definition
kicker: Naming it precisely
::: definition Blast radius
What an agent's action can damage, and how far, measured by whether it's
reversible and what it costs if wrong, not by how sophisticated the
agent's reasoning looked when it decided to take it.
:::

::: example Try this yourself
List every action an agent you're scoping can take. Sort each into one
of the table's four rows. If more than a couple land in the bottom row,
that's not a failure, it's the actual scoping finding.
:::

@narrate
That's the definition worth keeping, and the second half matters as
much as the first: blast radius has nothing to do with how impressive
the agent's plan looked in review. A beautifully reasoned plan that ends
in an irreversible, costly action still belongs in the bottom row.

Run the sort on something real. Most agents, once every action is
actually listed instead of described in general terms, turn out to have
one or two genuinely high-stakes actions hiding among several harmless
ones. Finding exactly which ones they are is the whole value of doing
this exercise before launch instead of after an incident.

Do the sort before the architecture is finalised, not after. It's far
cheaper to redesign an agent so its one irreversible action becomes a
proposal a human confirms, than to bolt a gate onto a system that was
built assuming full autonomy everywhere and now has to be pulled apart
to fit one in.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Sort every action of an agent you're scoping into the four-row table
2. Name the specific approver for anything that landed in the bottom row

@narrate
Two things before you move on.

Do the sort completely, not just for the action that worried you most
walking in. The ones you'd forgotten to mention are usually where the
real gap is.

Then name an actual person for every gated action, not a team or a
process. "The support team" is not an approver. A specific name who
knows they own that click, and what happens on the days they're out, is.
