@slide statement
kicker: Section 9 · The metric that lies
## The dashboard says engagement is up. That's either the best news you've had all quarter, or the worst.
lead: Most product metrics assume more usage means more value. An AI feature can break that assumption without anyone noticing.

@narrate
Picture a rising line on a dashboard: messages per session, up twenty
percent month over month. For most features, that line is an
unambiguous win. Ship it to the team, put it in the deck, move on.
Sound familiar?

For an AI feature, that same line has two completely different honest
readings. People might be getting real value and coming back for more.
Or the assistant might be getting it wrong on the first try often
enough that people are re-typing the same request three different ways
before it lands, and every one of those retries counts as engagement.

Generic product metrics were built assuming a feature does the same
thing every time it's used. An AI feature doesn't, and that single
difference is why this lecture exists: three metrics built specifically
for a feature that behaves differently every time it runs.

None of this means engagement is a useless number. It means engagement
alone was never built to answer the question you actually care about:
is this feature good, or is it merely being used. Those are different
questions, and only a probabilistic feature makes the gap between them
this wide.

@slide table
kicker: Three metrics, built for this
## Each one answers a question engagement can't

| Metric | What it actually measures | Why it survives |
| --- | --- | --- |
| Adoption | Of everyone who could use it, who actually does | Distinguishes real reach from a loud minority |
| Acceptance | How often a suggestion is kept, not edited or discarded | A direct proxy for quality, from production, not a golden set |
| Deflection | How often the feature resolves a need without a human | Ties usage directly to the cost this feature was built to justify |

@narrate
Read each one against what it replaces. Adoption replaces raw usage
counts, which a small group of power users can inflate while everyone
else ignores the feature. It asks the harder question: of everyone who
had this available, what fraction actually chose to use it.

That denominator is what teams skip most often. "Ten thousand people
used the feature" means something different depending on whether ten
thousand or two hundred thousand could have. Skipping the eligible
population is the same mistake as an average with no tail check
underneath it.

Acceptance leans hardest on production: the closest thing to a live,
continuous version of 4.2's golden set, scored by every real user
instead of fifty chosen cases. Someone keeping a drafted email as
written, or rewriting three of its five sentences, is a quality signal
arriving for free.

Deflection matters most for the feature this course keeps returning to:
the refund agent, handling a request that used to need a person. A
rising conversation count says nothing about whether it's working.
Deflection says exactly what matters: of the refund requests that
reached it, how many closed without a human touching the case. That's
the number 7.2's cost model and 8.6's incident plan were quietly
building toward, the one that finally says whether the automation
earned its keep.

@slide two-col
kicker: The same rising line, two different stories
## Read acceptance before you celebrate engagement

::: cols
:: card bad
### Engagement alone
- Messages per session up twenty percent
- Reported as a clear win in the weekly update
- Nobody checked whether people were retrying or thriving
:: card good
### Engagement plus acceptance
- Same twenty percent rise in messages
- Acceptance rate checked alongside it: down eight points
- The real story: more retries, not more value
:::

@narrate
Notice both columns start from the identical number. The only
difference is whether anyone checked a second metric before deciding
what the first one meant.

An engagement number alone can't distinguish delight from friction,
because both look identical in a raw usage count: more messages, more
sessions, more time in the feature. Acceptance is the metric that tells
the two apart, because a user delighted with a first answer doesn't
need a second one, and a user fighting the feature generates exactly
the retries that inflate engagement while acceptance quietly drops.

This is the same discipline 7.5 asked of a margin number and an
engagement number on the same page. Two metrics rising or falling
together tell a real story. One metric alone is a single data point
dressed up as an answer.

Notice, too, which team usually owns which column. Product tends to
watch the engagement number by default, because it's the one every
dashboard already has. Acceptance often has to be deliberately added,
by someone who specifically asked for it, which is exactly why so many
teams are flying with only the first column in view.

## What "up twenty percent" hides
figcap: Messages per session against acceptance rate, the same release. The rise is identical in both readings. Only one reading checks what it means.

```figure

  - {label: "Messages per session", values: ["+20%", "+20%"]}
  - {label: "Acceptance rate", values: ["not checked", "-8 pts"], highlight_cols: [1]}
```

@narrate
Put the two cards from the last slide into one grid and the point gets
sharper. The top row is identical wherever you look: messages per
session, up twenty percent, in both readings, because that number never
changed.

The bottom row is where the two readings stop agreeing. Read across the
first column and acceptance simply isn't there, because nobody pulled
it. Read across the second and it's down eight points, sitting right
next to the twenty percent rise it was hiding behind.

Same release, same underlying data, one column apart. The gap between
those two cells isn't a measurement error. It's the entire cost of
skipping a second metric before you write "clear win" in a weekly
update.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
A high acceptance rate isn't automatically good news either. ==Users
rubber-stamping a low-effort suggestion without reading it== looks
identical to genuine quality in the data.
:::

@narrate
Say the honest caveat, because it's tempting to treat acceptance as the
one metric that finally can't be misread, and it can be, in the
opposite direction from engagement.

A suggestion accepted without being read produces the exact same
acceptance event as a suggestion read carefully and judged genuinely
good. Low-stakes features, an autocomplete suggestion nobody's
scrutinising closely, are especially prone to this. High acceptance on
a feature where the cost of being wrong is low is weaker evidence than
the identical number on a feature people actually check.

This is 4.9's discipline again, aimed at a new number: don't trust one
metric in isolation, however good it looks. Pair acceptance with a
downstream signal where you can get one: did the accepted draft get
sent unedited, did the accepted suggestion actually get used five
minutes later, or did it quietly get undone.

The fix isn't abandoning acceptance as a metric. It's the same fix as
everywhere else in this course: pair a number with a second one before
trusting either alone, and be specific about what would make you doubt
the first number rather than simply believing it because it moved the
right direction.

@slide definition
kicker: Naming it precisely
::: definition The three-metric floor
Adoption, acceptance, and deflection, read together, not separately.
Each one catches a story the other two miss, and none of the three is
trustworthy completely alone.
:::

::: example Try this yourself
Pull your own feature's engagement trend and its acceptance trend side
by side. If they're moving in opposite directions, that's this
lecture's finding, not a coincidence to explain away.
:::

@narrate
That's the floor worth building before any other analytics work in
this section, and the definition's last clause is the one worth
remembering under pressure: none of the three, alone, is the whole
story.

Run the comparison on real numbers if you have them. Most teams have
engagement instrumented already and acceptance instrumented nowhere,
which is itself the finding: the metric this section calls the most
important is usually the one nobody's collecting yet.

Notice this floor doesn't require new infrastructure to define, only to
instrument, which is exactly next lecture's subject. Knowing what to
measure is the cheap half of this problem. Actually firing the event at
the right moment, for every user, is the part most teams underestimate.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Check whether your feature currently tracks acceptance at all
2. Compare your engagement trend against it, if you can

@narrate
Two things before you move on.

Check for acceptance first, honestly. If the answer is that no event
fires when a user keeps, edits, or discards a suggestion, that's
today's finding, and it's a bigger gap than a missing engagement metric
would be.

Then, if you have both numbers, put them side by side before trusting
either one alone. Two lines moving together are the closest thing to
real evidence this section can offer you.

Both of these are conversations you can start today, before any new
code ships. The instrumentation next lecture covers is what turns the
conversation into a number you can actually trust.

Next lecture is the instrumentation plan: exactly which events to fire,
and when, so acceptance, adoption, and deflection are numbers you have
on day one, not numbers you retrofit after someone asks for them.
