> "I am not doing this bucket math again on a Sunday night."

@narrate
Fair. Everything so far in this section has been judgement: choosing
cases, wording questions, checking agreement, and all of that stays real
work a spreadsheet can't do for you. But the table you tallied by hand
last lecture? That part can tally itself. This is the lecture where you
finally build something that runs on its own.

You need exactly two tabs. One where you enter scores, one that reads them.
No macros, no plugins, nothing beyond formulas you've probably used before.

By the end of this you'll have a working version of the exact breakdown
from last lecture, the one that caught a bucket collapsing under a flat
aggregate, except this one recalculates the moment you type a new score in,
instead of you doing it by hand on a Sunday night before a launch review.

If you've built a pivot table before, you already have every skill this
requires. Nothing here is more advanced than that.

Here's tab one, and it's almost exactly the two-column sheet from the
calibration lecture, just made permanent.

One row per case. A case ID, so you can find it again. The bucket it
belongs to, from the four you built. Then six columns, one per rubric
question, one for pass and zero for fail, entered by you or by your
validated judge.

Case C027 there is a shape you'll see constantly: five questions pass, one
fails, question three specifically. That's not a rounding error to wave
away. It's the exact case you'd pull up when someone asks why the
adversarial bucket dropped.

Fifty rows, nine columns. That's the entire tab. Nothing about scale here
is the hard part; the hard part happened already, in the two lectures that
taught you what belongs in columns C through H.

@slide code
kicker: The two formulas doing all the work
## Everything else is arithmetic a spreadsheet already knows

```text
Scores tab, column I (Overall), row 2:
=IF(SUM(C2:H2)=6,1,0)

Dashboard tab, Common path pass rate:
=AVERAGEIF(Scores!B:B,"Common path",Scores!I:I)
```

@narrate
Two formulas, and you're done.

The first lives in the Scores tab, one copy per row. It adds up the six
pass or fail columns, and if all six read one, the case passes overall.
Miss a single question and the row reads zero. No partial credit, on
purpose: the rubric said pass or fail, so the overall score respects that.

The second lives on the Dashboard tab, once per bucket. It's an
average-if: average the overall column, but only for rows where the bucket
matches, common path in this example. Since overall is just ones and
zeros, averaging them is exactly the pass rate. Same formula, four times,
once per bucket, and you have last lecture's table computing itself.

Change one bucket name in the criteria and the same formula works for any
of the four. You are not writing four different formulas, you're writing
one formula and changing one word, four times.

## Fifteen minutes, start to finish

::: split
:: main
1. Duplicate the template. Don't build from a blank sheet
2. Paste your case IDs and buckets into the Scores tab
3. Score each case: six ones or zeros per row, from your rubric
4. Overall and the Dashboard tab compute themselves
:: aside Where people lose time
Almost all of it is step three. The sheet takes fifteen minutes. Scoring
fifty cases against a rubric is the afternoon from two lectures ago, and
this sheet doesn't shorten that part.
:::

@narrate
Here's the actual sequence, because "build a spreadsheet" undersells how
little of this is spreadsheet work.

Duplicate the template rather than starting blank, so the formulas are
already sitting there waiting for data. Paste your case IDs and their
buckets into the Scores tab, one row each. Then score every case: six ones
or zeros, straight from the rubric you calibrated. Once that's filled in,
you're finished. Overall and the Dashboard tab were already computing
themselves the whole time.

Notice where almost all the real time goes: step three. The sheet itself
takes fifteen minutes to set up. Scoring fifty cases against a rubric is
the same afternoon of work from two lectures ago, and no formula in this
sheet makes that part faster. It was never meant to.

Here's the payoff, and it's smaller than people expect, which is the
point.

Two formulas, written once, copied down. Zero manual retallying, ever
again, for this rubric. And the dashboard updates the instant you finish
entering one score, which matters more than it sounds: it means the
four-bucket table from last lecture is live during the meeting where
someone asks "what if we pulled that one case", not something you promise
to rerun and send later.

One more thing this buys you almost for free: sort the Scores tab by
Overall, filter to zero, filter again to one bucket, and you're looking at
exactly the failing cases behind whatever number the dashboard just
showed you. That's the "go read those cases" step from last lecture's
release gate, and it's a two-click filter, not a search.

@slide callout
kicker: The honest trade

::: callout Be straight about this
A spreadsheet doesn't score anything for you. ==A human, or a validated
judge, still has to fill in every cell==, and past a few hundred rows,
formulas that scan whole columns slow down, and a typo in a bucket name
silently excludes a case from every average.
:::

@narrate
Say the cost plainly.

This sheet is bookkeeping, not judgement. Nothing here writes the pass or
fail columns for you. That's still the calibrated rubric and the validated
judge from the last two lectures, doing the actual work, one case at a
time.

And it has a ceiling. Past a few hundred rows, formulas scanning whole
columns get sluggish, and the failure mode is quiet: type "Common Path"
with a capital P in one row, when every other row says "Common path," and
that single case silently vanishes from the bucket average. Nobody gets an
error. The number is just wrong, and it looks exactly as confident as the
correct one.

@slide definition
kicker: Naming it precisely

::: definition Eval harness
Whatever repeatedly turns raw scores into a pass rate you can trust,
without you re-deriving the arithmetic by hand each time. A spreadsheet is
the simplest one that counts.
:::

::: example Try this yourself
Build the two tabs against your own fifteen calibration cases first,
before your full fifty. If the dashboard's number matches what you tallied
by hand, the formulas are right. If it doesn't, trust the hand tally and
go find the typo.
:::

@narrate
Notice the definition doesn't mention spreadsheets at all. A harness is
anything that does this reliably, and a spreadsheet is just the version
with the lowest cost to start.

The exercise deliberately reuses your fifteen calibration cases, the ones
you already hand-scored twice, back in the rubric lecture. You know what
the answer should be. Build the sheet against cases where you can already
check its homework, before you trust it with the other thirty-five you
haven't scored by hand yet.

This is also the cheapest way to catch a formula mistake. If your hand
tally said sixty percent and the sheet says ninety, the sheet is wrong, not
your feature, and you'll want to know that before it's the number in a
release review instead of a rehearsal.
