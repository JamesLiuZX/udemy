@slide quote
kicker: Section 5 · The two big ones
attrib: What kills more enterprise RAG pilots than bad chunking ever does

> "It showed someone what they shouldn't see, or it confidently cited something that had stopped being true."

@narrate
Chunking and retrieval quality get most of the attention in a RAG
project, and they're not what actually stalls enterprise deployments.
What stalls them is realising, usually late, that a document carries
information retrieval never checks: who's allowed to see it, and
whether it's still true.

Both problems share a root cause. An embedding represents what text
means. It has no opinion on access, and no opinion on the calendar.

That's worth sitting with. Why are both failures so easy to miss in
your own pilot? A pilot usually runs with one tester, who
has full access to everything, on a corpus that was indexed yesterday.
Neither failure mode has anywhere to hide under those conditions.
Both show up the moment the pilot becomes a real rollout: many users
with different access, a corpus that's now months old and still
growing.

@slide table
kicker: What naive retrieval assumes
## Four assumptions that don't survive contact with a real organisation

| Reality | The naive assumption | What's actually needed |
| --- | --- | --- |
| Permissions | Anyone who can query can see everything indexed | Filtered by the asker's real access, checked live |
| Permissions | Access is fixed at the moment of indexing | Promotions and offboarding must propagate immediately |
| Freshness | The index reflects the current document | The index is a snapshot from whenever it was last built |
| Freshness | An outdated version is harmless if it's still there | It competes on equal footing with the current one |

@narrate
Four assumptions, and every one of them holds fine in a demo and fails
quietly in production, because a demo runs with one user and a
snapshot nobody's had time to go stale.

The permission rows matter because your organisation's documents
were never written with one flat access level. HR policy, general.
Compensation bands, restricted. A draft strategy memo, leadership
only. Index all of it into one pool and ask a single retrieval system
to search across it, and the system has no idea it's supposed to treat
those three differently, unless someone explicitly built that
filtering in.

The freshness rows are the quieter risk, precisely because a stale
answer doesn't announce itself. A permission leak at least produces a
document someone can point to and say this shouldn't have shown up.
An answer built on a policy that changed three months ago just sounds
right. It reads exactly like a current answer would, because the
mechanism generating it doesn't know the difference between old truth
and current truth.

@slide two-col
kicker: Same index, two designs
## What changes when access is actually checked

::: cols
:: card bad
### One shared pool
- Every document sits in the same searchable index
- Retrieval returns whichever chunk is semantically closest
- A restricted document surfaces to whoever happens to ask the right question
:: card good
### Filtered at query time
- The asker's real access is checked before results return
- Restricted documents simply never enter that user's results
- Access changes today, not whenever the index next rebuilds
:::

@narrate
The difference is exactly one step, inserted at exactly one point:
before results go back to the user, not after.

Notice the second column doesn't require re-architecting retrieval
itself. It requires the retrieval step to ask a second question
alongside "what's relevant": what is this specific person actually
allowed to see, checked against their access right now, not their
access when the document was indexed months ago.

This is also exactly the kind of decision from Section three's PRD
template that belongs in writing before you launch, not discovered
during a security review after. Naming who owns the access model, and how
quickly a revoked permission actually takes effect, is a specification
question with a real owner, the same way the golden dataset and the
rubric were.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
Some content changes faster than any index can keep up. ==That's not a
document to retrieve, it's a live system to call==, and forcing it
into RAG anyway is the wrong tool for that specific content.
:::

@narrate
Say the honest caveat, because freshness has a limit that no amount of
engineering effort around RAG actually solves.

A policy that updates twice a year fits RAG comfortably: re-index
after each change and you're current. Live inventory, today's
exchange rate, a support ticket's status right now, changes faster
than any reasonable re-indexing schedule can track. That content was
never meant to be a document. It's a live answer from a live system,
and the right fix is a direct call to that system at the moment of the
question, not a retrieval index trying to keep up with something that
changes by the minute. Section six picks this up properly: giving a
model a tool to call, instead of a document to search.

This is worth checking against the decision tree from Section two as
well. "Needs facts that change" pointed you toward RAG. It's worth
adding the missing half of that sentence now: needs facts that change
slower than you can realistically re-index. Past that speed, the
honest answer isn't a better pipeline. It's a different box on the
tree entirely.

@slide definition
kicker: Naming it precisely

::: definition Permission-aware retrieval
Checking the asker's real, current access before results return, not
the access that existed when the document was indexed. Access changes
have to propagate immediately, not on the next re-index.
:::

::: example Try this yourself
Ask what happens in your own system the moment someone's access is
revoked. If the honest answer is "the index doesn't know yet," that's
a live risk, not a hypothetical one.
:::

@narrate
That's the definition worth holding onto, and notice the word doing
the real work is live. Checked now, not checked once.

The exercise is uncomfortable on purpose. Picture someone leaving your
company today. Ask, specifically, how long their old access lingers in
your retrieval system before it's actually gone. If nobody in the room
knows the answer, that's the honest finding, and it's worth surfacing
before an auditor finds it first.

@slide bullets
kicker: Before you move on
## One thing worth doing now

Find out how long a permission change actually takes to reach your retrieval system, and name one piece of content that changes too fast for RAG at all

@narrate
One thing before you move on.

Find the real answer to the access question, not the reassuring one.
Minutes, hours, or the next scheduled re-index are three very different
risk profiles wearing the same shrug. Then name one piece of content
that's genuinely too fast-moving for retrieval, the way live inventory
or a real-time status is. Flagging it now saves you from building a RAG
feature for something that always needed a tool call instead.
