@slide statement
kicker: Section 6 · The other checklist
## Section one gave you the test for whether AI belongs here at all. This is the second test, for whether it should act on its own.
lead: Four signals, each one something this section already taught you to check.

@narrate
Section one's disqualification checklist asked whether AI belongs in
this feature at all. Assume it passed that test. This lecture asks the
narrower, later question: given that AI helps here, should it act
autonomously, or should a human stay in the loop pulling the trigger.

Four signals answer that question, and you've already met every one of
them earlier in this section. This lecture just puts them in one place.

That's deliberate, not a shortcut. A checklist built from ideas you've
already tested against real examples is one you can actually defend in
a review, because you can point to exactly which earlier lecture backs
each row, instead of asserting caution and hoping it sounds credible.

@slide table
kicker: The checklist
## Any one of these is reason enough to stay manual, or stay a workflow

| Signal | Why it disqualifies |
| --- | --- |
| A workflow could specify every path in advance | Pay for autonomy only where branches genuinely can't be predicted |
| You can't build a guardrail for its riskiest action | Blast radius with no gate is just blast radius |
| The reliability math doesn't clear your bar, even checkpointed | More steps won't fix what the maths already ruled out |
| Nobody can meaningfully review its escalations | An escalation path nobody watches isn't a safety valve |

@narrate
Read down that left column and notice each phrase is a callback, not a
new idea. Row one is 6.1's test. Row two is 6.6's blast radius framework
finding nowhere safe to land. Row three is 6.3's table, applied honestly
instead of hopefully. Row four is 6.4's escalation pattern, checked for
whether it actually works in practice.

Do you need to fail every row for this to matter? No, any single row is
sufficient on its own. A task can pass three of these and fail the
fourth, and the fourth is still the one that matters. This isn't a
score to average. It's a list of independent reasons to stop.

Treating it as a score is the most common way this checklist gets
misused. "Three out of four, that's mostly fine" is exactly the
reasoning that ships the one row that was never negotiable. A task that
fails row two, no coverable blast radius, doesn't get rescued by acing
the other three. It gets rescued by fixing row two, or by not shipping.

@slide two-col
kicker: Run it on something real
## Same request, two different verdicts depending on the actual answers

::: cols
:: card bad
### "Auto-approve refunds under any amount"
- No cap means row three's maths never gets checked
- Escalations, if any exist, aren't reviewed in practice
- Fails rows three and four before row one is even asked
:: card good
### "Auto-approve refunds under $50, verified account, capped at 3 per day"
- A workflow could nearly specify this, but genuine edge cases remain
- Blast radius is small and bounded, row two clears
- The chain is short enough that row three's maths holds up
:::

@narrate
Same word, refund automation, and the checklist gives two completely
different verdicts because the actual answers are different, not because
one request sounds more cautious than the other.

Notice the good column doesn't pass every row for free. It passes
because someone did the work of bounding the amount, the account
status, and the daily count until the blast radius was actually small
and the chain actually short. The checklist doesn't reward caution as a
vibe. It rewards a request specific enough to check.

That specificity is also what makes row one, the workflow test, worth
re-asking on the bounded version. A refund under fifty dollars to a
verified account capped at three a day is close enough to fully
specifiable that a plain workflow might handle most of it, with the
agent's judgement reserved for the genuine edge cases a workflow's fixed
rules can't anticipate. Bounding a proposal often reveals how much of it
was never autonomy-shaped in the first place.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
This checklist will disqualify fewer tasks than it feels like it should.
==Most agent proposals fail on scope, not on the fundamental idea==, and
scope is fixable.
:::

@narrate
Say the honest caveat, because a section this focused on what goes wrong
can leave the impression that agents rarely clear the bar, and that's
not the honest finding.

Most proposals that fail this checklist fail on an unbounded version of
a perfectly reasonable idea: no cap, no gate, no defined escalation
path. Bound it the way the good column just did, and the same idea often
passes cleanly. The checklist's real job is forcing that bounding to
happen before launch, not after the version with no cap already shipped.

Genuine disqualifications, the idea itself being wrong rather than
under-specified, are real but rarer than they feel from inside this
section. A task with catastrophic, irreversible downside and no way to
add a checkpoint anywhere in its chain is a real row-two failure no
amount of scoping fixes. Most requests that land on your desk aren't
that. They're an unbounded good idea waiting for someone to do the
bounding.

@slide definition
kicker: Naming it precisely
::: definition The agent disqualification checklist
Four signals, each traced to an earlier lecture in this section: no
avoidable branching, no coverable blast radius, maths that doesn't
clear the bar, and no working escalation path. Any one fails the whole
proposal.
:::

::: example Try this yourself
Run an agent you're actually considering through all four rows, with
real numbers, not impressions. Name which row it would fail first if it
failed one.
:::

@narrate
That's the checklist worth keeping, and running it with real numbers is
the entire difference between this exercise and a vague gut check.

Most people can guess which row their proposal is weakest on before they
even finish counting. Counting anyway is what turns that guess into
something you can actually defend in the review where someone asks you
to justify it.

Write the failing row down specifically, not as a general worry. "Row
two, no way to cap or gate the refund amount" is something an engineer
can go fix this week. "I have a bad feeling about this one" is not, and
it's the version most unscoped concerns arrive in if nobody forces the
specific question first.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Run all four rows against one real agent proposal, with actual numbers
2. If it fails one, ask whether tighter scope fixes it or the idea is wrong

@narrate
Two things before you move on.

Run the full checklist, not just the row that already worried you. The
row you weren't watching is usually the one that fails.

Then ask the harder follow-up. A failure from unbounded scope is fixable
today. A failure baked into the fundamental idea, something no amount of
bounding rescues, is worth saying so plainly, and saying it now costs
far less than saying it after launch.

Before the workshop next lecture, where you'll scope one of these for
real, make sure you can tell the two failures apart on sight. That
distinction is most of what this lecture was actually teaching.
