@slide statement
kicker: Section 9 · The test that breaks its own assumption
## A/B testing assumes variant A does the same thing every time it runs. For an AI feature, it doesn't.
lead: That single broken assumption is why a standard A/B test calculator will quietly mislead you here.

@narrate
A normal A/B test compares two fixed things. Button colour one against
button colour two, each one behaving identically every single time a
user sees it. Whatever variance shows up in the results comes entirely
from the users, not from the thing being tested.

An AI feature breaks that from the first request. Variant A can produce
a genuinely different answer to the identical prompt on two different
occasions, because sampling a model isn't the same operation as
rendering a fixed button. Now the results carry two sources of
variance tangled together: real differences between users, and the
model's own inherent variation, and a standard test can't tell them
apart.

That's not a reason to abandon A/B testing. It's a reason to run it
with the two specific adjustments this lecture covers, because without
them the test is answering a question you didn't mean to ask.

This shows up in a specific, recognisable way: a test that looked
clearly positive in week one, and quietly evaporated by week three, with
nobody able to say whether the effect was ever real or whether early
noise happened to look like a signal. That specific pattern is usually
the two broken assumptions showing up together.

@slide table
kicker: What breaks, specifically
## Three assumptions a normal A/B test makes, and what happens to each

| Assumption | Holds for a button | Breaks for an AI feature |
| --- | --- | --- |
| Same input, same output | Always true | False, by design, every single call |
| All variance is user variance | True | False, some variance is the model's own |
| Required sample size is fixed | Correctly estimated | Underestimated, sometimes badly |

@narrate
Read the third row as the practical consequence of the first two,
because it's the one that actually costs you a wrong decision.

A standard sample-size calculator asks for an effect size and a
baseline rate, and returns a number of users. That number assumes
every unit of noise in the data comes from genuine differences between
people. Feed it the same inputs for an AI test and it will confidently
hand you a sample size that's too small, because it never accounted for
the model's own output variance sitting inside the noise alongside the
real user variance.

This is exactly the ground 4.8 already covered, applied to a new
question. That lecture taught you why a probabilistic feature needs
more cases to trust a pass rate at all. This is the same statistics,
aimed at comparing two variants instead of scoring one against a golden
set.

Temperature is the specific dial behind the first row, worth naming
plainly. Turn it down and outputs become more consistent, which can
shrink this problem without solving it, because zero temperature still
isn't the same guarantee a button click is. Some providers change model
versions underneath a fixed API name without warning, which reintroduces
the same variance from a completely different direction, one you can't
dial down at all.

@slide two-col
kicker: The two fixes that actually matter
## Randomize by user, and pin the version, for the whole test

::: cols
:: card bad
### Request-level, version drifting
- Each request randomly assigned, even from the same user
- Prompt gets tweaked mid-test because someone found an improvement
- Impossible to say which version produced which result
:: card good
### User-level, version pinned
- A user stays in the same arm for the entire test
- The prompt version is frozen until the test formally ends
- Every result traces back to a known, fixed configuration
:::

@narrate
User-level randomization matters because a single person bouncing
between arms on different requests contaminates both arms at once. Keep
one user in one arm for the test's duration, and you can aggregate
their multiple requests into a more stable read of that arm's true
performance, which is exactly what helps offset the model's own
per-request variance.

Pinning the version matters for a reason 9.2 already gave you the tool
for. Every event already carries a prompt version in a properly
instrumented feature. An A/B test simply holds that version fixed on
purpose, for both arms, for the test's full duration, so a
mid-test "improvement" doesn't quietly become a third, unlabelled
variant nobody accounted for in the results.

This is also why a test needs a defined end date agreed before it
starts, not a running check that stops the moment the number looks
good. Peeking at results daily and stopping the instant they cross
significance is a well-documented way to manufacture a false positive
out of pure noise, and it's a far easier trap to fall into when the
metric is also bouncing around from the model's own variance on top of
everything else.

@slide callout
kicker: The honest caveat
::: callout Be straight about this
Your sample size needs to be larger than a standard calculator says.
==The model's own output variance adds noise the calculator never
priced in==, and underpowering the test either way costs you.
:::

@narrate
Say the honest caveat plainly, because underpowering a test in either
direction is a real, specific cost, not an abstract statistical
technicality.

Too small a sample and a real improvement looks like noise, so you
throw away a genuinely better version. Too small a sample the other way,
and noise looks like a real effect, so you ship a change that did
nothing, or made things worse, believing the data proved it helped.
Both mistakes trace back to the same root: treating an AI feature's
sample-size math as identical to a button's.

Neither mistake announces itself at the time. Both look, in the moment,
like a clean result with a clear recommendation attached. The only way
to tell them apart from a genuinely well-powered test is to have sized
the test properly before it started, which is exactly why this is a
design decision made in advance, not a judgement call made after the
numbers come in and already look a certain way.

If you don't have a statistician to size the test properly, the honest,
conservative move is to run it longer than the calculator suggests and
to treat a narrow, borderline result with real suspicion rather than
declaring victory the moment the number crosses a threshold.

Both failure directions are expensive in the exact same currency this
course keeps returning to: a wrong decision made confidently, on a
number that looked precise enough to trust. A narrow, borderline result
deserves the same scepticism 4.9 already taught you to bring to a
single eval score, not extra credit for having a significance test
attached to it.

@slide definition
kicker: Naming it precisely
::: definition A valid AI A/B test
Randomized by user, not request. Prompt version pinned for both arms,
for the full duration. Sample size sized larger than a standard
calculator suggests, to absorb the model's own output variance.
:::

::: example Try this yourself
Check your last A/B test on an AI feature. Was it randomized by user or
by request, and did the prompt version stay fixed the whole time.
:::

@narrate
That's the standard worth holding every test to, and the example is
worth running on a real test you've already shipped, not just a future
one.

Most teams running this check for the first time find at least one
violation: a version that quietly changed mid-test, or randomization
happening at the request level without anyone deciding it should. That
finding doesn't necessarily mean the past result was wrong. It means
the result deserves less confidence than the dashboard gave it credit
for.

Apply the same standard to a test still running, not only a finished
one. If a live test is being randomized per request or running against
a prompt someone quietly edited last week, stop it and fix the setup
before trusting a single number it produces from here on.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Check your next A/B test's randomization unit and version pinning
2. Size the sample larger than the calculator suggests, deliberately

@narrate
Two things before you move on.

Check the randomization unit first. If it's per-request rather than
per-user, that's the fix to make before the next test launches, not
after.

Then pad the sample size on purpose, and say why, in writing, so
whoever reviews the result later understands it wasn't an arbitrary
round number.

Neither of these blocks a test from launching today. They change what
launching responsibly looks like: the same test, with a unit of
randomization and a version lock decided on purpose instead of left to
whatever the testing tool defaults to.
