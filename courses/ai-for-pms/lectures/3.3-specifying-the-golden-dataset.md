@slide callout
kicker: Section 3 · The golden dataset clause

::: callout Watch for this line in review
"Engineering will define an appropriate test set before launch." Five
words, and ==nobody owns it, dated it, or wrote down what it actually
has to cover==.
:::

@narrate
That line shows up in almost every AI feature PRD, usually in the
testing section, usually agreed to without objection. Who's actually
going to build it, and by when?

It sounds like a plan. It's actually a gap wearing a plan's clothes.
Nobody's named, so it belongs to everyone, which means it belongs to
no one until a launch date forces the question. Nobody's said how big
or what it has to cover, so whoever ends up building it under pressure
grabs whatever's fastest: ten cases from Slack, the ones already
sitting in a bug report.

The dataset doesn't need to be written into the PRD. The commitment to
it does.

Watch how this plays out on a real schedule. The line sails through
review because it sounds reasonable and nobody wants to be the person
who blocks a PRD over a testing detail. Then, in the third week before
launch, someone finally asks who's actually building it, and the
honest answer is nobody has started, because nobody was ever the
answer to that question. What should have been two weeks of unhurried
work becomes two days of panic, and panic is exactly the condition
under which a golden set gets built badly.

@slide two-col
kicker: The same gap, closed
## What the PRD actually needs to commit to

::: cols
:: card bad
### What most PRDs say
"Engineering will define an appropriate test set before launch."
:: card good
### What it should say
"A 50-case golden set, covering common path, known failures, edge
cases, and adversarial inputs. Owned by [name]. Frozen two weeks
before launch, versioned in [location]."
:::

@narrate
Same intention, and only one version survives contact with a slipping
schedule.

The second version has four things the first one doesn't: a floor on
size, a coverage requirement that rules out fifty happy-path cases
counting as done, a name attached to the work, and a date that sits
before launch, not on it. None of that is the dataset itself. It's the
commitment that makes the dataset someone's actual job.

Notice, too, that the good version is still short. It's one sentence
longer than the bad one, not a page. The goal here isn't length, it's
specificity: every noun in that sentence is something a project tracker
could hold someone to. "Appropriate" was never a word you could put a
deadline against. A name and a date are.

@slide table
kicker: What the PRD has to answer
## Five questions, answered on paper, before anyone starts building

| Question | Why it can't wait |
| --- | --- |
| How many cases, at minimum? | A floor stops "a few examples" from counting as done |
| What must it cover, not just include? | Rules out fifty cases that are all the easy ones |
| Where does the data come from? | Real transcripts, not invented examples, or say so |
| Who owns it, and by when? | Unowned work is nobody's job until launch week |
| How is it versioned once frozen? | An editable set stops being an instrument |

@narrate
Five questions, and notice none of them ask you to actually build
anything yet. They ask you to decide, in writing, what building it
correctly is going to require.

The coverage question is the one worth dwelling on. Fifty cases that
are all ordinary, everyday inputs will pass beautifully and prove
almost nothing, because they never touch the failure modes that
actually hurt you. The PRD doesn't need to enumerate every bucket,
that's real, deliberate work, and Section four walks through exactly
how to do it properly. What the PRD needs is the requirement that
coverage exists at all, so nobody can call fifty easy cases finished.

The source question matters almost as much, and it's the one people
skip fastest under time pressure. Real transcripts show you what
actually happens: the messy phrasing, the second language, the
question nobody anticipated. Invented examples show you what you
already imagined, which tells you nothing you didn't already believe.
If real data genuinely doesn't exist yet, because the feature hasn't
launched anywhere, say that plainly in the PRD rather than quietly
filling the gap with guesses dressed up as cases.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
The PRD is not the place to build the dataset. ==Fifty rows pasted into
a document nobody reopens is worse than a clear commitment and a linked
artifact==, because it looks done without being usable.
:::

@narrate
Say the honest caveat, because the opposite mistake is just as common
as the vague one: dumping fifty rows straight into the PRD to look
thorough.

A PRD is read once, argued over, and archived. A golden set gets
reused every release, edited under version control, argued about case
by case. Cram it into the document and you get the worst of both: a
bloated PRD nobody rereads, and a dataset that's awkward to actually
maintain. Commit to it here, build and version it properly elsewhere,
and link the two.

Think of the PRD as the contract and the dataset as the deliverable.
Nobody writes the deliverable inside the contract. They write what the
deliverable has to satisfy, and where to go find it once it exists.
That distinction is what keeps this section from turning into fifty
rows of stale examples nobody trusts by the second release.

@slide definition
kicker: Naming it precisely

::: definition The golden-dataset commitment
The paragraph in a PRD that names the size floor, the coverage
requirement, the source, the owner, the deadline, and the versioning
discipline, without containing the dataset itself.
:::

::: example Try this yourself
Find the testing section of your team's current AI feature PRD. If it
says anything like "engineering will define a test set," rewrite it
using the five questions from this lecture.
:::

@narrate
That's the whole shape of it: a paragraph, not an appendix, and every
sentence in it answerable by someone with a name.

The exercise is the rewrite itself. Take the vague line if your PRD has
one, and run it through the five questions. Where you don't have an
answer yet, write the question down instead of skipping it. An
unanswered question in a PRD is honest. A vague sentence pretending to
answer it isn't.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Rewrite your PRD's test-set line with an owner and a size floor
2. Note which coverage categories you genuinely don't have data for yet

@narrate
Two things before you move on.

Rewrite the line. Give it an owner, a number, and a date, even if the
date moves later. That alone closes most of the gap this lecture opened
with.

Then be honest about coverage. If you already suspect you have no real
examples of this feature failing badly, write that down now. It's a
better finding today than a silent gap in the golden set later.
