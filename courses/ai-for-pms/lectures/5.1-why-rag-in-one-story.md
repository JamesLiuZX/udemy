@slide statement
kicker: Section 5 · Why RAG exists
## The model didn't get smarter between version one and version two of this feature. It got access.
lead: One real story explains RAG better than the mechanism does, because the mechanism doesn't tell you why it mattered.

@narrate
A company built an assistant to answer employee questions about
benefits. Version one was a system prompt describing the company and a
capable model. It worked beautifully in the demo.

Then someone asked it a real question: how many vacation days do I get
after five years. The model answered instantly and confidently, a
tidy, plausible tiered schedule. It was completely wrong for this
company, and a manager approved time off based on that answer before
anyone caught it.

That's the story. Everything about why RAG exists is sitting inside
it.

Notice what makes this failure hard to catch in review, not just in
production. The wrong answer read exactly like a right one would have.
Confident tone, plausible structure, nothing about the phrasing gave
it away. That's the hallucination mechanism from Section one, and it's
worth sitting with for a moment before moving to the fix, because the
fix only makes sense once you've felt how invisible the failure was
from the outside.

@slide two-col
kicker: Same question, same model, same day
## What changed between version one and version two

::: cols
:: card bad
### Without retrieval
- States a generic, plausible tiered schedule
- The numbers were invented, not this company's policy
- A manager acted on it before anyone checked
:: card good
### With retrieval
- Retrieves the actual current policy document
- States the real number, with a citation to the source
- Same model, same question, same day
:::

@narrate
Look closely at what actually changed between those two columns,
because it's less than you'd expect.

The model didn't get retrained. It didn't get more capable at
reasoning, or better at maths, or more careful in any general sense.
What changed is that the second version had the actual policy document
sitting in its context when it answered, and the first version was
reasoning entirely from what vacation policies generally look like,
the mechanism from lecture one, doing exactly what it does when
nothing grounds it.

This is also why the fix couldn't have been a better prompt. No amount
of instructing the model to "be accurate about vacation policy" gives
it a number that was never in its training data and never will be,
because it's specific to one company's private document. Some
information isn't a phrasing problem. It's an access problem, and only
one fix on the whole decision tree from Section two actually solves
that particular kind.

@slide table
kicker: What actually moved
## Mapped onto the five-layer stack from Section two

| Layer | Version one | Version two |
| --- | --- | --- |
| Product | Same | Same |
| Guardrails | Same | Same |
| Orchestration | Same | Same |
| Foundation model | Same | Same |
| Your data | Nothing retrieved | The actual policy document |

@narrate
Here's the same story again, on the stack diagram from earlier in this
course, and it makes the point precisely.

Four of five layers didn't move at all. Same product, same guardrails,
same orchestration code, same underlying model. Exactly one layer
changed: the data layer went from empty to populated with the one
document that actually mattered. RAG isn't a smarter version of your
feature. It's the same feature, finally given the thing it needed to
answer honestly.

Keep this table in your back pocket for the rest of this section,
because it answers a question that comes up constantly once you start
designing one of these: which team actually owns fixing it when
something's wrong. If the fact was missing, that's a data-layer
problem, and it belongs to whoever owns the document, not to
engineering re-tuning the model. Naming the layer, the exact skill
from Section two, is what turns a vague "the bot is wrong" into
someone's actual Tuesday.

@slide callout
kicker: The honest caveat

::: callout Be straight about this
RAG fixes a missing-fact problem. ==It does nothing for a reasoning
problem==, feeding more documents to a model that's calculating
wrong won't fix the calculation.
:::

@narrate
Say the honest caveat, because RAG gets reached for as a universal fix,
and it solves exactly one kind of failure.

The vacation policy question was a missing-fact failure: the answer
existed, in a document, and the model simply didn't have it. Retrieval
fixes that completely. It does nothing for a feature that's
misinterpreting a chart, doing arithmetic wrong, or drawing a bad
conclusion from information it already had correctly. Handing that
kind of failure more documents doesn't touch the actual problem.

Watch for this specifically when a team proposes "adding RAG" as a fix
for a vague complaint like "it's not being smart enough." That phrase
almost never tells you which failure you're looking at. Ask for one
concrete wrong answer first, then diagnose it, before committing to a
retrieval system that might not even be the right layer.

@slide definition
kicker: Naming it precisely

::: definition Why RAG exists
To answer questions the model structurally can't know: private,
proprietary, or changing faster than any training run. It adds access
to facts. It doesn't add reasoning ability.
:::

::: example Try this yourself
Find a case where your own feature was confidently wrong. Ask whether
it was missing a fact it should have retrieved, or reasoning badly
about facts it already had. Only the first one is RAG's job.
:::

@narrate
That's the test worth carrying into every "should we add RAG here"
conversation from now on: was the fact missing, or was the reasoning
wrong.

Run the exercise on a real wrong answer from your own feature. If the
honest diagnosis is a reasoning failure, adding retrieval will make the
PRD look more sophisticated and change nothing about the actual bug.

@slide bullets
kicker: Before you move on
## Two things worth doing now

1. Find one wrong answer from your feature and diagnose it: missing fact, or bad reasoning
2. Name the one document that would have fixed it, if it was a missing fact

@narrate
Two things before you move on.

Pull up a real case your feature got wrong. Was the fact missing, or
was the reasoning bad? Run it through this lecture's test honestly,
rather than assuming you already know the answer.

Then push one step further if access was the culprit. If you can't
point to where the right answer actually lives, that's worth knowing
too, because no retrieval system can find a document that was never
written down.
