@slide bullets
kicker: How to pin your own test inbox
## Three steps, on the trigger node

1. Open the Email Trigger node and find "set mock data" under its output
2. Paste in a realistic array: a handful of promotional, internal and client emails
3. Save it. The pin icon turns solid, and every test run below it uses this data instead of a live inbox

note: TODO-IMG screenshots/section-3/n8n-mock-inbox-41-items.png (pinned 41-row inbox, Ravi's message buried midway down, pin icon solid)

@narrate
You do not need forty one rows to prove a workflow. You need enough
variety to catch a mistake: at least one email that should be flagged,
and several that should not be. If your test only ever contains obvious
urgent emails, you will never find out whether the agent also flags a
newsletter by accident.


@slide two-col
kicker: What this proves and what it doesn't
## The honest split

::: cols
:: card good
### What pinned testing proves
- The trigger's fields map correctly into the prompt
- The routing rule catches the right word
- Every node is wired to the next one correctly
:: card bad
### What it cannot prove
- Whether the model's judgement is actually good
- Whether a real inbox behaves like your test data
:::

@narrate
That right hand column is not a flaw in the method, it is the reason
Section 7 exists. Pinned data proves the machine is built correctly. It
cannot replace watching it run against a real week of real emails, which
is exactly what a trial task is for.


@slide callout
kicker: What actually happened in this build
::: callout One flag, out of forty one
Run against the pinned inbox, this exact workflow's job is to isolate
Ravi's message. That is the entire test: not "does it look busy," but
"does it find the one thing that mattered." A workflow that flags twelve
emails out of forty one has not passed, whatever the demo looks like.
:::
