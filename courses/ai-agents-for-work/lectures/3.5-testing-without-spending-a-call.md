::: example How this exact lecture got written
Before this course existed, this agent was tested against forty one
emails and a six-day-old question from Ravi Chandra. Not a hypothetical.
:::

@narrate
Every screenshot you have seen in this section came from a real build,
tested before a word of narration existed. The trigger's output was not
left to chance. It was pinned: forty emails of ordinary noise, and one
real question, buried on purpose, the way it actually was.

Why test against frozen mail instead of just switching it on? Because a
live inbox is the worst possible test bench. It sends you whatever it
feels like, never the tricky case you need twice, and every experiment
costs a real call and a wait. A pinned inbox is the same forty one
emails every single run, which means when you change one word of the
system prompt, any change in the outcome was caused by your word and
nothing else. That is the whole scientific method, borrowed for a
Tuesday: hold the world still, change one thing, look. You will fix
more agent problems with this one habit than with anything clever.


@slide bullets
kicker: How to pin your own test inbox
## Three steps, on the trigger node

1. Open the Email Trigger node and find "set mock data" under its output
2. Paste in a realistic array: a handful of promotional, internal and client emails
3. Save it. The pin icon turns solid, and every test run below it uses this data instead of a live inbox

@narrate
You do not need forty one rows to prove a workflow. You need enough
variety to catch a mistake: at least one email that should be flagged,
and several that should not be. If your test only ever contains obvious
urgent emails, you will never find out whether the agent also flags a
newsletter by accident.

Write your test emails yourself, from memory of your own real inbox,
rather than inventing generic filler: the value of the test is exactly
how much it resembles your Tuesday. The borderline one matters most.
Every inbox has a category that fools humans, and if yours is in the
test set, you get to watch how the agent handles it for free, forever,
before it ever handles the real one.


@slide table
kicker: The starter test set
## Six emails, six different traps

| The email | What it tests |
| --- | --- |
| A clearly urgent client message | Does the obvious flag actually fire |
| A borderline even you hesitate over | Where the judgement line really sits |
| A promotional blast | The conservative rule, doing its job |
| Internal chatter that mentions work topics | Topic words alone must not trigger a flag |
| A one-line "thanks, received" | Politeness is not urgency |
| One oddity: a forward, or a half-empty message | Strange input falls through safely |

@narrate
Six emails, and notice that only one of them tests whether the agent
flags well. The other five all test whether it refrains well, and that
ratio is correct: in a real inbox, almost everything is a thing to
ignore, so most of the ways your agent can be wrong are ways of
flagging too much. A test set that mirrors that lopsidedness is
testing the job. One that is all urgent drama is testing the demo.


@slide two-col
kicker: What this proves and what it doesn't
## The honest split

::: cols
:: card good
### What pinned testing proves
- The trigger's fields map correctly into the prompt
- The routing rule catches the right word
- Every node is wired to the next one correctly
:: card bad
### What it cannot prove
- Whether the model's judgement is actually good
- Whether a real inbox behaves like your test data
:::

@narrate
That right hand column is not a flaw in the method, it is the reason
Section 7 exists. Pinned data proves the machine is built correctly. It
cannot replace watching it run against a real week of real emails, which
is exactly what a trial task is for.

One check in the left column deserves its own minute, because its
failure is invisible. Fields mapping correctly means the email's body
actually arrives inside the prompt. When the mapping is wrong, nothing
goes red: the model receives a prompt with a blank where the body
should be, judges the blank, and answers SKIP with complete
confidence. Every box green, every answer wrong, the exact case
Section 2.3 warned about. The defence takes ten seconds: on any test
run, open the agent node and read the prompt as the model received it,
resolved, with the real subject and body sitting in it. Seeing the
actual words in the actual slots, once, is worth fifty green ticks.


@slide callout
kicker: What actually happened in this build
::: callout One flag, out of forty one
Run against the pinned inbox, this exact workflow's job is to isolate
Ravi's message. That is the entire test: not "does it look busy," but
"does it find the one thing that mattered." A workflow that flags twelve
emails out of forty one has not passed, whatever the demo looks like.
:::

@narrate
And if your pinned run flags two out of six instead of one? That is
not failure, that is the loop working. Read the agent's stated reason
for the extra flag, find the sentence in your system prompt that let
it through, tighten that sentence, run again. The run is free, the
inbox is frozen, so the only thing changing is your briefing, and most
prompts settle after two or three passes of exactly this. Tuning on
pinned data is where you learn the skill you will use for the life of
every agent you ever run: reading a wrong answer for the instruction
that permitted it.

With the wiring proven, the only thing left is the one step this course
cannot do for you: connecting it to a mailbox and a model that are
actually yours. That is next lecture, and it is where this agent
becomes real.
