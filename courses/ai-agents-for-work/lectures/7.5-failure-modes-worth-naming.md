@slide statement
kicker: Why naming a failure mode matters
## A mistake you already have a name for is a mistake you catch in seconds. An unnamed one costs you an afternoon.

lead: Five names, five safeguards, all of them already built into agents you have shipped.

@narrate
You have already met every failure mode in this lecture, once each,
across the last four sections. This is the moment they get names, so
the next time one shows up in your own work, you recognise it
immediately instead of starting from confusion the way you might the
first time.

Why do names matter this much? Because an unnamed failure gets
debugged from scratch. Picture the afternoon without the name: the
report is wrong, so you reread the prompt, tweak a sentence, rerun,
still wrong, add another sentence, and two hours later you have a
longer briefing and the same wrong report, because the cause was a
moved row and no briefing on earth reads a moved row correctly. Now
the same afternoon with the name: the report is wrong, the facts
check fails against the source, that is the drift signature, open
the sheet, find the edit, four minutes. A name is a compressed
checklist of causes. That compression is what this lecture hands
you, five times over.


@slide table
kicker: The five, named
## What breaks, and what already catches it

| Failure mode | What it looks like | What catches it |
| --- | --- | --- |
| Invention | A fact, name or date that was never actually given | The "never invent" ceiling, Sections 4 and 5 |
| Scope creep | An agent reaching data outside its job description | The scope line, checked in Section 1.3 |
| Drift | A moved row, a changed structure, a quietly wrong answer | Spot-check question five, Section 7.4 |
| Tone failure | Correct facts, wrong feel, for a client-facing message | The tone constraint, Section 6.3 |
| Silent over-trust | Nobody has actually read an output in months | The sampling rate itself, Section 7.4 |

@narrate
Notice the last row does not describe the agent failing. It describes
you failing to keep checking. That is deliberately on this list, because
it is the single most common cause of a small mistake becoming a real
one, across every industry that has ever automated anything.

Attach a first move to each name and the table becomes a repair
manual. Suspect invention: take the suspect fact and hunt for it in
the source, and if the hunt comes up empty you have your answer.
Suspect scope creep: stop reading outputs entirely and go read
access, the credential grants and the folders, because creep lives
in permissions, not prose. Suspect drift: open the source next to an
old output and compare shapes, headers, orderings, anything
structural. Suspect tone: read it aloud, the test that has not
changed since Section 6. Suspect over-trust: check one date, the
last time you actually read an output properly, and let the answer
embarrass you into a spot check. Five suspicions, five first moves,
none of them longer than ten minutes.

## Not every agent risks every failure equally

::: cols
:: card bad
### Highest exposure
Agent 3 (drift, because it reads a shared sheet) and Agent 4 (tone, because a client reads the output)
:: card good
### Lower exposure
Agent 1 (invention risk is low, it only flags) and Agent 2 (contained to one transcript at a time)
:::

@narrate
This is worth knowing before you spend your limited checking time. Spend
more of it on the agents whose failure modes actually cost something if
they slip through, not evenly across all four out of habit.

The pattern generalises to every agent you will ever adapt, and it
compresses to two questions about surfaces. Who else touches this
agent's input? A shared sheet, a team inbox, anything other hands
edit, means drift exposure, because other people's normal use moves
your agent's ground. And who reads this agent's output? The moment
the answer includes anyone outside your own desk, a client, a
director, tone and invention start costing real money. Input shared,
watch for drift. Output outbound, watch for tone and invention.
Neither, and you can afford the lighter end of every sampling rate
in C07. Those two questions, asked at design time, are how you place
your checking before anything has gone wrong yet.


@slide sidenote
kicker: A sixth name, on layaway
## Ambiguity: the failure Dev finds first

::: split
:: main
There is a sixth mode this table holds back, because the course meets
it properly in Section 10: ambiguity, where the input genuinely
supports two readings and the agent picks one without flagging the
choice. An action item assigned to "Alex" when two people in the
meeting share the name.
:: aside Why it is not invention
Nothing was made up. The fact was real and the reading was wrong,
which is a different repair: not a stricter ceiling, but input that
carries more context, like the attendees field from Section 4.2.
:::

@narrate
Hold the distinction loosely for now and let Section 10's story
plant it properly. The reason it earns a preview here is the pattern
it completes: invention fails by adding, drift fails by the world
moving, ambiguity fails by the input underdetermining the answer.
Three different repairs, which is the whole argument for names. And
expect a seventh, eventually, that no course named for you. When it
arrives, do what this lecture did: describe it precisely, name it,
attach a first move, and add the row. The taxonomy is a tool you
now own, not a list you memorised.

That is next section, and it closes the loop this course opened back

small assignment that makes this lecture stick: pick the one failure
