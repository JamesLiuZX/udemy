@slide statement
kicker: A different kind of question
## Agent 1 asked yes or no. This agent asks: which three sentences, out of two hundred, actually matter?

lead: Extraction is a harder judgement than classification, and your prompt has to work harder for it.

@narrate
Add an AI Agent node after your form trigger, attach a chat model the
same way you did in Section 3, and open the Prompt field. Set the User
Message to pull in your three form fields: meeting title, attendees, and
the transcript itself.

One assembly detail matters more here than it did for email: label
each piece as you drag it in, so the message reads Meeting title,
colon, the title, Attendees, colon, the names, Transcript, colon, and
then the text. Why? Because the model receives everything as one
stream of words. Unlabelled, the attendee names just dissolve into the
opening of the transcript, and the agent loses the one clue it needs
to turn "Sam will send the figures" into a real owner. Three little
labels, and each field arrives meaning something. It is the same
point-not-paste habit from Section 3, plus a name tag.


@slide example
kicker: The system message for this build
::: example Read it exactly as you would type it
"You are a meeting-notes assistant for Priya Malhotra. You are given a
transcript of a client renewal call. Extract only concrete action items:
things someone explicitly agreed to do. For each one, output a line:
[Owner] Action (due: date if mentioned, otherwise no date given). Do not
invent an owner, an action, or a date that was not stated. If there are
no clear action items, say so plainly. Ignore small talk."
:::

@narrate
Notice the shape of this prompt against Section 3's. That one told the
model what to ignore. This one tells it what it is not allowed to make
up. Both are the same habit, aimed at a different failure mode: an
inbox agent that over-flags is annoying, but a notes agent that
invents a deadline nobody agreed to sends someone chasing a promise that
was never made.

@slide table
kicker: The three load-bearing phrases
## Where the briefing earns its keep

| The phrase | The failure it forbids |
| --- | --- |
| "explicitly agreed to do" | Intentions dressed up as commitments |
| "otherwise no date given" | A tidy, invented deadline filling a silence |
| "if no clear action items, say so plainly" | Manufactured items justifying the run |

@narrate
Three phrases in there are carrying the load, and all three are
transplants from the job description. "Explicitly agreed to do" is the
line between commitments and intentions: calls are full of "we should
really look at that", and none of it is an action item until someone
says I will. The agent needed that boundary stated, because
politeness reads like agreement to anything that has never sat in a
meeting.

The other two are escape hatches, and they are the anti-invention
ceiling made mechanical. A model fills vacuums with plausible content
unless the honest empty answer has been given a legal shape, so you
give it one at the line level and one at the list level. Now "no
date" is a correct output, not a gap begging to be filled, and a
meandering call with no commitments comes back as exactly that,
instead of three manufactured items to justify the run. Write these
hatches into every extraction prompt you ever make. They cost a
sentence each and they retire the failure mode you are least likely
to catch by eye.


@slide two-col
kicker: Why the format line matters
## A loose instruction versus a strict one

::: cols
:: card bad
### "List the action items"
Some days you get a paragraph. Some days a table. You cannot build
anything reliable on top of an answer that changes shape.
:: card good
### "Output one line per item, this exact format"
Every run reads the same way, which means you, or a later automation
step, can trust it without checking the shape every time.
:::

@narrate
You are not being fussy by specifying the output format this precisely.
You are removing one more thing you would otherwise have to check by
hand, every single time this agent runs.

Where does the strictness stop, though? At the words themselves. The
format pins the shape of each line, never the phrasing inside it: the
agent still describes each action in whatever words the call used,
which is what keeps the list readable as English rather than a code.
Strict scaffolding, natural filling. That balance is worth copying
into every format line you ever write.

The owner-in-brackets convention has a quiet payoff too: a fixed
format is scannable. Priya reads Monday's list by skimming the
brackets, hers versus everyone else's, in about four seconds. And a
fixed format is what makes the next growth step possible without a
rebuild: the day you want these lines appended to a tracking sheet
instead of read from a screen, a shape that never varies is the
difference between one small node added and a parsing headache. You
will see exactly that pattern in the next section's build, where a
sheet is the whole point. Formats are boring. Boring is what
downstream steps can stand on.


@slide callout
kicker: What this agent deliberately does not do
::: callout No memory, no tool, same as Agent 1
Each transcript is judged entirely on its own. Nothing here remembers
last week's call or reaches out to check a calendar. That is not a
missing feature, it is the scope from your job description, held to on
purpose.
:::

@narrate
It is worth one beat on why these two absences are load bearing, not
laziness. Memory sounds like an upgrade until you picture its failure:
an agent that remembers last week's call can blend it into this
week's, and a commitment from a fortnight ago resurfaces on today's
list wearing today's date. Each transcript judged alone makes that
impossible by construction. A calendar tool sounds even more helpful,
and it is also this build's first step onto the trust ladder's higher
rungs: reaching into a second system is new blast radius, and it has
not been through a job description. Section 6 adds a tool to an agent
properly, on purpose, with the paperwork done. Here, restraint is the
feature.

With the prompt written, your agent can now read a transcript and
extract what actually happened in it. One last read-through before you
test: say the whole briefing aloud, Priya's habit, and listen for any
sentence you would not say to a person taking over your meeting notes
for a week. If a line only makes sense to you because you wrote it,
it will not make sense to the model either. Next lecture proves the
build, without spending a real AI call to find out.
