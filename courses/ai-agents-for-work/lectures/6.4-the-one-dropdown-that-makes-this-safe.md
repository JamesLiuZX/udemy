@slide statement
kicker: The number that shouldn't be possible
## This entire section's promise, draft only, comes down to two words in one dropdown.

lead: Resource: Draft. Operation: Create. Nothing else in this build can send an email.

@narrate
Add a Gmail node as the last step. It offers a Resource field, and one
of the options is "Draft." Choose it. The Operation field then offers
"Create." Choose that too. You have just built the entire safety
guarantee of this agent into two clicks.

What do those two words buy, in plain Gmail terms? Every chase the
agent writes lands in your drafts folder and nowhere else: no
recipient has seen it, no thread has been started, nothing has left
your account. Priya's Tuesday now contains a drafts folder with two
or three chases waiting, each one a decision she makes with one
read and one click, or one delete. The agent moved the work to the
exact threshold of the irreversible step, and stopped. Everything
before that line is cheap to get wrong. Everything after it costs an
apology. The dropdown is where you chose which side of the line this
agent lives on.


@slide sidenote
kicker: What you did not add
## The option that was sitting right there

::: split
:: main
The same Resource dropdown also offers "Message," with an operation
called "Send." That option exists, one click away, the whole time you
were building this. You did not use it. That absence is the guardrail.
:: aside Why this matters more than the prompt
A prompt can be wrong. A model can misjudge a tone. But a node that was
never wired to send anything cannot send anything, regardless of what
the model decides to write. This is a stronger guarantee than any
instruction, because it does not depend on the model behaving.
:::

note: TODO-IMG screenshots/section-6/n8n-gmail-draft-resource-operation.png (Draft/Create fields)

@narrate
This is the single most important idea in this entire course, and it
shows up here because a follow up chaser is where the temptation to
"just automate the send too" is strongest. Resist it. The two clicks you
just made are worth more than any sentence you could write in a prompt.

Put the guarantee in Section 1.3's language. Everything an agent
reads is, functionally,
part of its instructions, and you cannot fully control what arrives
in a sheet another person edits. The missing Send node is different
in kind: no sentence any input could contain wires a node into your
canvas. Briefings bend under weird input. Wiring does not. That is
why every guardrail in this course that really matters is a thing
that is absent, not a thing that is promised.

Look at that canvas the way Section 1 taught you to: what can this agent

exactly one thing with what it finds: write a draft nobody sees until
Priya opens Gmail herself. Say the audit out loud, both halves, the

@slide callout

::: callout This agent cannot read the inbox, and that is temporary on purpose
It cannot know a client already replied, so it will occasionally

@narrate
You might already be itching to give the agent one more ability:
search the mail, check for a reply, skip the unnecessary chase. Hold
that itch, deliberately. That exact addition, made carelessly, is
Section 8's near miss, and made properly, it is Section 8's lesson.
The version you have built is the version that earns the right to
grow, and the occasional redundant draft is the modest rent you pay,
for now, for an agent whose reach you can recite in one breath.


@slide table
kicker: Two kinds of rule
## Why wiring outranks briefing

| | A briefing rule | A wiring rule |
| --- | --- | --- |
| Lives in | The system message | The canvas itself |
| Enforced by | The model's judgement, each run | The absence of a node, always |
| Bends when | Input gets weird | Never: there is nothing to bend |
| Example here | "Do not mention the premium" | No Send operation exists |

@narrate
Keep both kinds, and know which is which. Briefing rules are cheap,
expressive and right nearly all the time, which makes them perfect
for tone and content. Wiring rules are blunt, binary and absolute,
which makes them the only acceptable form for anything you cannot
afford to have happen even once. The craft of this whole course fits
in one sentence: put each rule in the layer whose failure you could
live with.


@slide bullets
kicker: A habit worth keeping forever
## Verifying a guardrail, not trusting it

1. Open every "send" style node in any agent you build and confirm its actual operation
2. Never assume a job description's promise matches the wiring. Check the dropdown
3. If a workflow could send something, ask why it needs to, before you ask how

@narrate
Make the verifying concrete, and make it a ritual you also run on
other people's work. When you import any template, including this
course's own C01 to C04, the first move is not connecting credentials.
It is a slow lap of the canvas reading every node's Resource and
Operation, asking one question per box: what is the worst this node
as configured can do? A minute per workflow. Trust in this world is
not a feeling, it is an inspection you have actually performed, and
people who inspect templates before running them are the people whose
name never ends up on an email they did not write.

One more place the ritual pays: your own future edits. The riskiest
person in this workflow's life is you in three months, adding "one
small thing" on a busy afternoon. The lap of the canvas is for that
person most of all, and the lap after any edit is the habit that
catches what the edit changed. With the guardrail in place and
verified, next lecture connects this agent to a real inbox and ships
it.
