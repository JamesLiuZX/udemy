@slide definition
kicker: Same habit, third build

::: definition Count it yourself before the agent counts it for you
Five rows, pinned to the Sheets node: Brightwell Manufacturing at
$18,400, renewing 15 September, still open. Four other clients around
it, one already closed.
:::

@narrate
Before you run this agent even once, do the arithmetic in your head. Four
open renewals. A total premium you can add up on one hand. One renewal,
Dunmore Electrical, close enough to its date to flag. That is your
answer key.

Write the key down before the first run, not after, for the same
anchoring reason as Section 4's count-first rule, sharpened by the
fact that these are numbers now: once the agent's total is on screen,
your own addition quietly checks itself against the agent instead of
the sheet. The whole key takes under a minute of mental arithmetic,
and that minute is the trial's entire measuring instrument. An answer
key you wrote after seeing the answers is not a key. It is an echo.


@slide callout
kicker: What a pass actually looks like
::: callout Match the agent's report against your own count, line by line
Right number of open renewals. Right total premium. The right client
named as the one to watch. Anything else, however well written, is a
fail you caught for free, before it reached a director's inbox.
:::

@narrate
Run it against the pinned data and compare. If the numbers match, the
wiring and the judgement are both sound, for this snapshot of the sheet.
That phrase, "for this snapshot," is doing quiet work, and it is worth
sitting with for a second.

Know what a near miss looks like here, because it is subtler than a
wrong answer. The dangerous report is the one where the counts are
right, the total is right, and one detail is quietly off: the correct
number of at-risk renewals but the wrong client named, or a fluent
paragraph in which one figure came from nowhere you can point to.
Fluency is not accuracy, and on a numbers report the check is always
the numbers, never the prose. If any single line cannot be traced to
a cell in the pinned data, that line failed, and the report fails
with it, however well the rest reads.


@slide statement
kicker: The sentence worth remembering
## A spreadsheet row is not a fixed fact. It is whatever is in that cell the moment the agent reads it.

lead: Today, that is exactly what you expect. It will not always be.

@narrate
This pipeline, these five rows, this exact Brightwell line, comes back
later in this course. Not because it changes here, but because
somewhere down the line, someone edits the sheet the agent reads from,
and the agent has no way to know that changed anything. Hold that
thought. Section 7 is where it matters.

The unsettling part is that nothing needs to go wrong for this to
bite. A shared sheet is a living thing: a colleague sorts it to find
their own client, someone inserts a row to log a new account, a
Status value gets typed in lower case by someone in a hurry. Every
one of those is normal, correct use of a spreadsheet, and every one
changes what the agent reads without anyone having made a mistake.
Your pinned test can never cover the ways other people will use a
sheet you share. That is not a reason to distrust the build. It is
the reason the trial runs on the living sheet, for three Mondays,
against your hand count, before trust gets granted.

## What to do now

1. Run the agent against your pinned pipeline and check every number by hand
2. Note which row you would want double checked most, and why
3. Keep this exact pinned data. You will recognise it again
