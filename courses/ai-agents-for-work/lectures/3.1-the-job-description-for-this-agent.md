## Every build in this course starts the same way: the job description first.

lead: Not a wireframe. Not a feature list. The document from Section 1.4.

@narrate
If you skipped straight to this lecture hoping to skip the paperwork,
here is the argument again, briefly, because it matters enough to
repeat. A job description is not bureaucracy for its own sake. It is the
only thing standing between "I connected an inbox" and "I connected an
inbox, on purpose, to do one specific job."

What actually goes wrong when people build first and decide later? The
scope gets negotiated mid-build, with the least cautious person in the
room, which is you at your most excited. The workflow nearly works, and
it would definitely work if it could also read the archive folder, so
that access gets granted "just to try it", and by Friday the agent can
reach four things nobody sat down and chose. Building against a written
spec inverts that. When the build tempts you to widen something, the
document makes the widening a decision instead of a slide, and most of
the time, reading your own ceiling out loud is enough to stop you.


@slide example
kicker: The spec this build follows
::: example Priya's job description for Agent 1
**The job**: flags any email that needs a same-day reply.
**Scope**: reads the Renewals inbox only. Writes nothing.
**Action**: read only. No drafts, no sends.
**Ceiling**: never marks anything as resolved. Flagging only.
**Urgent means**: a client names a deadline, or mentions a payment,
refund or lapsed cover.
**Trial task**: one week, every flag reviewed each morning.
:::

@narrate
You saw this in Section 1. Read it again now with different eyes: every
line in it is about to become a specific decision inside the build.
Scope becomes which node reads what. Action level becomes which nodes
this workflow does not contain. The ceiling becomes the reason the
workflow ends at a flag, not a send.

Two lines deserve a preview of exactly where they land. The "urgent
means" line is not background: in two lectures' time, those words,
almost verbatim, become the instructions pasted into the agent itself.
You already wrote the most important part of the system prompt without
knowing the term. And the trial line is a commitment device: one week,
every flag, each morning, is written down now so that Section 7's
trial has a spec to check against instead of a vibe. A build that
starts this way arrives at its trial with the pass mark already on
paper.


@slide two-col
kicker: Why this exact scope
## What the job description rules out

::: cols
:: card bad
### What Agent 1 will not do
- Send anything, ever
- Touch any inbox but Renewals
- Decide a matter is closed
:: card good
### What Agent 1 will do
- Read one inbox
- Decide what needs today's attention
- Hand that decision to a human, clearly labelled
:::

@narrate
Notice how short that second column is. A narrow job, done reliably, beats
a broad one done shakily. Every agent in this course stays deliberately
narrow, and Agent 1 is the narrowest of the four: it never writes
anything at all.

Both columns become physically checkable in the build, and that is the
part to appreciate. "Touch any inbox but Renewals" is ruled out by one
form field: the trigger will be pointed at one named folder, so the
scope is not a policy the agent follows, it is the only door it was
given a key to. "Send anything, ever" is ruled out by absence: this
workflow will simply contain no node capable of sending, and you can
audit that by looking at the canvas. That is the quiet advantage of
building agents this way. The safety rules are not promises buried in
instructions the model might misread. The important ones are wiring,
and wiring does not have judgement to fail.
