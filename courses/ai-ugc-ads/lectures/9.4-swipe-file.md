@slide statement
kicker: Section 9 · The swipe file
## Wednesday's generation step assumes you already know what to generate. That assumption is usually false, and it's the expensive part.
lead: A swipe file is what turns "generate something new" into "generate the next thing on this list."

@narrate
Section 9.1's Wednesday step says "generate whatever Tuesday's decisions
require." That sentence hides a real gap. Deciding you need a new angle
is not the same as knowing what that angle actually is, and staring at
a blank brief on a Wednesday is where a lot of sprint time quietly goes.

A swipe file closes that gap before it opens. It's a running collection
of angles, hooks, and reference creative, gathered continuously rather
than assembled from scratch under Wednesday's deadline. When Tuesday's
decision says "new angle needed," you're choosing from a list, not
inventing one on the spot.

This isn't a new skill. Section 2.3 already taught you the hook
taxonomy that makes a swipe file worth keeping. This lecture is about
building the habit of feeding it continuously, so that taxonomy has
somewhere real to live between briefs.

Why does this matter enough for its own lecture, rather than a single
line in Section 9.1? Because the gap it closes is invisible until
you're actually staring at it. A sprint that runs perfectly for three
weeks can still stall completely on the fourth, the moment Tuesday
calls for a genuinely new angle and nothing's ready to meet it.

@slide table
kicker: What actually goes in it
## Four categories, gathered as you go

| Category | Where it comes from | What you do with it |
| --- | --- | --- |
| Proven angles | Your own scored winners, per Section 8.5 | Reuse the underlying argument, not the exact cut |
| Hook patterns | Section 2.3's taxonomy, tagged by awareness level | Match to a new product's angle map |
| Competitor and category ads | Ads you notice, anywhere, worth studying | Study the structure, never the claim |
| Cautionary examples | Claims or tells that would fail Section 6's checklist | A reminder of what not to write, kept deliberately |

@narrate
Notice the fourth row. Most swipe files only collect things worth
copying. This one deliberately keeps a few things worth avoiding too,
an overclaimed competitor ad, an obvious AI tell, because remembering
what failure looks like is as useful as remembering what worked.

The first row is the one that compounds fastest. Every winner Section
8.5's scorecard confirms is worth adding here, not just logging and
forgetting. A year into running this sprint, your own proven angles
become the single richest source in the file, richer than anything
borrowed from outside the account.

Tag entries by awareness level as you add them, the same ladder Section
2.2 built. A swipe file sorted this way answers Wednesday's actual
question directly: given this angle map's gaps, what's already sitting
in the file for a cold audience versus a warm one.

The second and third rows work together in a way worth noticing.
Competitor and category ads show you what the wider market is trying.
Your own hook taxonomy tells you which pattern that ad is actually an
instance of. Read together, they turn "I saw an ad I liked" into "that's
a curiosity-gap hook aimed at a cold audience," which is the form
Wednesday's brief actually needs.

@slide code
kicker: The habit, not just the folder
## How this actually gets fed, week to week

```text
EVERY TIME YOU NOTICE SOMETHING (not just Wednesdays):

1. Save it immediately, wherever you keep the file
2. Tag: category, awareness level, why it caught your eye
3. One line only. Detail can wait until Wednesday.

EVERY WEDNESDAY, BEFORE GENERATING ANYTHING NEW:

4. Check the swipe file first for a matching angle
5. Only start from a blank brief if nothing fits
```

@narrate
The first half of this habit happens whenever it happens, on a train,
scrolling a competitor's feed, mid-conversation with a customer.
Capture takes seconds. The one-line tag is deliberate: full detail
later, on Wednesday, when there's actually time to develop it properly.

The second half is what makes Wednesday faster, not just more organised.
Checking the file before opening a blank brief means the default
question becomes "does something here fit" rather than "what should I
make," and the first question is almost always faster to answer.

Notice this doesn't replace Section 2's brief process. It feeds it. A
swipe file entry becomes the seed of a proper brief, run through the
same product truth doc and hook taxonomy as anything else. It just
means that seed already exists on Wednesday morning instead of needing
to be invented under deadline.

Where should you actually keep this? Anywhere you'll genuinely open on
a Wednesday. A shared document, a simple spreadsheet, even a folder of
screenshots with one-line captions. The specific tool matters far less
than whether it's somewhere you'll actually check before reaching for a
blank brief, which is the entire reason this file exists.

@slide callout
kicker: The honest trap

::: callout Be straight about this
A swipe file is for studying structure, never for copying claims. ==A
competitor's exact wording might be a policy violation waiting to
happen, on their account or yours, and borrowing it directly hands you
someone else's risk along with their idea==.
:::

@narrate
One honest trap worth naming, because a well-stocked swipe file makes
it genuinely tempting.

Studying why a competitor's hook works, the structure, the pacing, the
awareness level it's aimed at, is exactly what this file is for.
Copying their actual claim word for word is a different act entirely,
and it skips straight past Section 6's entire pre-flight discipline. You
have no idea whether that claim would survive your own product's
claims boundary, because it was never tested against yours in the first
place.

Keep the two separate in how you tag entries. Note the pattern that
caught your attention, never the exact line, and rebuild the claim from
your own product truth doc every time. The structure is reusable. The
specific words underneath it never are.

This is the same discipline Section 6.2 already built around Harlan's
killed swelling claim, aimed at a new entry point. A borrowed claim
never even reaches a human sign-off gate to catch it, because it looks
like it's already been proven somewhere else. It hasn't. It's only been
proven on a product, an audience, and a legal footing that were never
yours to begin with.

@narrate
Next lecture turns everything this section has built, the sprint, the
economics, this file, into a report someone outside the work can
actually follow.

Before that, start the file today, even with three entries. An angle
you noticed this week, a hook pattern from Section 2.3 you haven't used
yet, one cautionary example. Three entries beats an empty folder the
next time Wednesday needs one.

Revisit it at the end of every sprint, too, not only when you're adding
to it. A swipe file nobody prunes eventually turns into noise, dozens of
half-remembered entries with no clear reason any of them were saved.
Five minutes a week, deciding what's still worth keeping and what's
quietly gone stale, keeps the file genuinely useful rather than just
large.
