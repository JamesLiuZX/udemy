@narrate
Most creative portfolios are a wall of finished ads, arranged to look
impressive. That's proof of production, not proof of the system this
course teaches, and a prospect who's evaluating whether you can find a
winner, not just make one, needs different evidence entirely.

A case study built from Section 9.5's report format is that different
evidence. It shows the objective, the metric that answered it, the
honest ratio across a real batch, and the one creative that actually
won, in that order. That order is the whole point. It proves you
followed a process to the winner, rather than picking your best-looking
output and calling it proof.

Sam's own case study is exactly this, built from his real reports on
Harlan's account, redacted rather than invented. Nothing in it needed
writing from scratch. It already existed, one honest weekly report at a
time, from the moment Section 9.5 taught him to write them.

Why does this matter enough to teach as its own lecture, rather than a
single line saying "reuse your reports"? Because the instinct to build a
portfolio from scratch, polished and written specifically to impress,
is strong, and it's exactly the instinct that produces the highlight
reel this lecture is trying to help you avoid.

@slide table
kicker: What stays and what gets redacted
## Protect the client. Keep the process intact.

| Redact | Keep exactly as reported |
| --- | --- |
| The brand name and identifying product details | The objective, metric, and decision tree used |
| Exact spend figures, if the client requires it | The ratio: how many winners against how much noise |
| Any internal client information | The fatigue and refresh story, if one happened |

@narrate
Notice the right column is where the actual value lives. A prospect
doesn't need to know it was specifically compression socks to trust
the process. They need to see that a real decision tree was applied, a
real ratio resulted, and a real winner survived scrutiny rather than
being declared on day one.

Redacting the left column isn't just good practice with a client's
data, it's also what makes the case study honest to reuse. You're
not claiming credit for someone else's brand success. You're
demonstrating a repeatable process that happened to run on their
account, which is a narrower and more defensible claim.

Get explicit permission before using any client's numbers at all, even
redacted. Some clients are fine with an anonymised case study. Some
aren't, and assuming consent because the brand name is hidden is not
the same as actually having it.

If a client declines, that's not the end of the case study, only a
constraint on how specific it can be. A version that rounds every
number and describes the category rather than naming it still shows
the same process, the same ratio shape, the same honest verdict. The
identifying detail is the least important part of what makes it
convincing.

## The case study, built from what already exists

```text
ONE REDACTED ACCOUNT, ONE SPRINT CYCLE:

1. The objective and metric (from any week's report, 9.5)
2. The batch: count tested, winners, losers, noise
3. The winning angle's verdict, read against 8.2's tree
4. What happened after: fatigue, refresh, or scale, if any
5. The one line that matters: this took a process, not luck
```

@narrate
Five lines, pulled directly from reports you've already written if
you've been running Section 9's sprint honestly. There's no new
document to draft from a blank page here, only a compilation of what
the weekly rhythm already produced.

Line five is the line most competing portfolios can't honestly write.
"This took a process, not luck" only means something if the four lines
above it actually show a process: an objective set in advance, a ratio
that includes noise, a verdict read against a tree rather than a gut
feeling. Claim it without the evidence and it reads as marketing
language. Claim it with the evidence and it's simply true.

Notice, too, that line four is optional for a reason. Not every sprint
cycle you'd want to feature has a fatigue story yet, especially an
early one. A case study that skips a line it genuinely has nothing to
say about is honest. One that invents a fatigue story to fill the
template is exactly the kind of embellishment this whole course has
been built to avoid.

@slide callout
kicker: The honest trap

::: callout Be straight about this
Picking your single best sprint cycle for the case study, quietly
skipping the quieter ones, feels like normal editing. ==It's the same
cherry-picking Section 9.5 already warned against in a report. A
portfolio built this way is a highlight reel wearing a case study's
clothes==.
:::

@narrate
One honest trap worth naming, because a portfolio piece invites it more
than a weekly report does.

A report goes out every week regardless of how it reads. A portfolio
piece gets chosen, which means there's a real decision about which
cycle to feature, and the temptation is to feature the best one you've
ever had rather than a representative one. That's a subtler version of
the same dishonesty Section 9.5 already named, dressed up as normal
editorial judgement.

The fix is the same one that fixed the report. Include the honest ratio
in the case study itself, not just the winning result, even in the
cycle you're most proud of. A prospect who sees noise acknowledged
inside your best example trusts it more, not less, than one shown only
a spotless win.

Would a spotless case study actually survive a follow-up question about
what didn't work? It wouldn't, and a prospect sharp enough to ask that
question is exactly the kind of client worth having. Building the
honest ratio in from the start means that question has an answer ready,
rather than an admission that feels like it's walking something back.

Next lecture turns everything from this section into an actual plan for

Before that, look back through whatever reports you've already written.
If even one sprint cycle has a real ratio and a real verdict in it,
you already have the beginning of a case study. It just needs
redacting, not writing.

Keep this habit going forward, too. Every future sprint cycle is a
potential case study the moment it's reported honestly, not something
to reconstruct later from memory. The best time to write a case study
is the same week the report that becomes it already exists.
