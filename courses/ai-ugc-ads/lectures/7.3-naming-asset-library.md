## Every ad you'll ever make is easy to find the week you made it. This lecture is about month six.
lead: A filename that made sense in the moment tells you nothing once you're staring at your two-hundredth export.

@narrate
Section 5.4 already gave you a naming pattern: brand, angle, version,
placement. That answered a real question, which file goes where. It
never answered a different one, which file actually won, and that second
question is the one that gets expensive to answer badly.

Six months from now, someone, possibly you, is going to need to know
whether the "hour eleven" angle has already been tested, what its result
was, and whether it's worth another variant. If the answer to that lives
only in someone's memory, it's already gone.

Why does this matter more here than in most creative work? Because this
course is built around volume. A brand running a handful of ads a year
can rely on memory just fine. An account running eight ad sets a week,
the way Section 9.1's sprint asks you to, generates more history in a
month than memory can honestly hold onto by month three, let alone
month six.

@slide table
kicker: What a filename alone can't hold
## Two different jobs, one naming system

| Job | What it needs | Where it lives |
| --- | --- | --- |
| Finding the file | Angle, version, placement | The filename itself, from Section 5.4 |
| Knowing what happened | Test date, result, kill or scale decision | A linked record, not the filename |

@narrate
Trying to cram a result into a filename is how you end up with names
nobody can parse a year later. The filename's job stays exactly what
Section 5.4 gave it: find the file fast. A separate, linked record does
the second job: what happened when this ran.

That record doesn't need to be complicated. A single spreadsheet row per
ad set, linked by the same angle and version tags already in the
filename, is enough. The naming convention and the results record are
two halves of one system, not competing standards.

Notice, too, why the link matters more than either half alone. A
filename with no linked record tells you where a file is and nothing
about whether it's worth touching again. A results record with no
consistent filename convention tells you a winner existed once, with no
reliable way back to the actual asset. Neither half does the job by
itself.

@slide code
kicker: B06, the assembled standard
## The naming convention plus the linked record

```text
FILENAME (from Section 5.4)
harlan_houreleven_v1_tiktok.mp4

LINKED RECORD, one row per ad set
Angle: hour-eleven-v1
Tested: [date]
Result: winner / loser / noise
Decision: scaled / killed / retested
```

@narrate
Here's the whole system, assembled. The filename answers "where is it."
The record answers "did it work." Both keyed to the same angle and
version tag, so anyone can move between them in seconds instead of
reconstructing history from memory.

Save this exactly as it is, the same way Section 6.6 asked you to save
the pre-flight checklist unmodified. The value isn't in the specific
spreadsheet columns. It's in having one linked system at all, built
before the volume makes it painful, not after.

Set this up before your next test, not after your fiftieth ad set makes
the backlog feel too large to tackle. Retrofitting a naming system onto
months of untracked history is real work, hours of guessing which file
was which. Building it into the habit from the start costs you almost
nothing, a few extra seconds per ad set, paid the same day you generate
it.

@slide callout
kicker: The honest cost of skipping this

::: callout Be straight about this
Skipping this system costs you nothing today. ==It costs you the exact
question Section 8.4 asks: iterate or new angle. You can't answer that
about a variant if nobody remembers testing its predecessor==.
:::

@narrate
One honest cost, easy to underweight because it doesn't bite for months.

An untracked test doesn't just waste that one test's budget. It quietly
disables a decision you'll need to make later. Section 8.4 asks whether
to iterate on a tired winner or try something new. Answering that
honestly requires knowing what's already been tried, and a memory is a
much worse record than a spreadsheet nobody had to remember to consult.

Think about the actual failure mode this produces if you skip it. Not a
dramatic loss, just a slow one: the same near-identical angle quietly
retested twice, eighteen months apart, because nobody could confirm it
had already run and lost. That's not a hypothetical inefficiency. It's
the single most common way a testing budget gets wasted on established
accounts that never built this habit.

Next lecture is where the numbers this record holds actually get read
properly: at small spend, with real honesty about what a modest sample
size can and can't tell you.

Before that, go set up the record itself, even if it's just one column
added to a spreadsheet you already have. Take whatever's currently
running, name it properly using Section 5.4's convention, and add its
first row: angle, date, and a blank where the result will eventually
go. That single row is the start of a system that gets more valuable
every single week you keep it running.

Ask yourself, honestly, how many of your past tests you could still name
and describe accurately today, off the top of your head. If the number
is lower than you'd like, that's not a personal failing. It's exactly
what this lecture predicted, and exactly what this system exists to
fix, starting now rather than after another six months of untracked
history piles up.
